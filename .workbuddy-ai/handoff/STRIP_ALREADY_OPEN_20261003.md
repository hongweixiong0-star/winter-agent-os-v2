## 三、问题 2：哪个可观察量能证明"读过了"？—— 已经有了一个现成的

画面上带着**大量只有读过详情页才会出现的文字**：

| 可见文字 | 为什么它能当"读过了"的证据 |
|---|---|
| `战斗开始倒计时 07:53:19` | **只有进入活动详情页才会读到倒计时**；横条上没有 |
| `参赛人数: 30/30`（三处） | 参赛人数是详情页的信息 |
| `[DW]凌霄阁` 赛区名 | 赛区是详情页结构 |
| 页签 `1` / `2` | 分页结构 |
| `教学`/`奖励`/`商店`/`战鼓`/`记录` | 活动功能入口清单 |

**这一条同时满足 `event_calendar` 自己写下的两条约束**：

- 它是**当前帧的观察**，不是坐标、不是 PRIOR、不是推断；
- 它**带时间信息**（`07:53:19` 倒计时），但那属于 `EVENT_MINIMUM_GUARANTEE` 那类
  活动时间语义，**不是横条 `start`/`end` 那种"预览"** ——
  横条那条约束是"预览永远不能变成战斗时钟"，而详情页读到的是客户端自己
  在倒计时页上印的字，语义不同，仍需按活动逐个登记，**不能自动采信**。

> **注意这里有个我差点犯的错**：把"读到倒计时"直接当成活动窗口是危险的。
> `read_regular_event_activity_strip` 的注释明确写过
> "a preview must never become a battle clock"。
> 所以：**用倒计时/参赛人数当"已读"标记是安全的（它们证明人到了那个页面），
> 但用它们当 `start`/`end` 不安全。** 这两件事必须分开。

## 四、问题 3：是纯导航还是不可逆？—— 当前动作是纯导航，但页面上有不可逆按钮

- 进入这个详情页本身：**纯导航**（已经在发生，且 V2 没有主动点过横条 ——
  全量账本里 `y ∈ [0.10, 0.17]`（横条带）的点击数是 **0**）；
- 页面上存在的**不可逆/高风险控件**：
  `编队`（带红点，可能消耗）、右侧 `商店`（可能涉及钻石/货币）。

**因此正确形态是**（宪法第 7 条：Safety 与 Liveness 必须分开）：

> **"记录已观测到该活动详情" 与 "执行该页面上的消费动作" 必须分离。**
> 只读观察 → 写 `read_entries` → 债务消 → `due` 收敛；
> `商店` / `编队` 一类动作继续由 Risk Gate 按各自的风险单独判。
>
> 若因为 `商店` 危险就拒绝"进入页面观察"，那等于把"挡住一次"变成"永远 due"，
> 比不做更糟 —— 这正是第五节那三个错误里最容易复发的那个。

## 五、本轮再次确认的三件事（都不是新代码能解决的）

1. **`skills.py` / `verifier.py` 里没有任何横条相关技能**
   ⇒ "打开横条活动"这条能力从零开始，**不能假设它已存在**。
2. **全量账本里点在横条带的步数 = 0**
   ⇒ V2 从没主动点过横条；当前详情页是客户端自己停留/切到的。
3. **两个欠债活动的 `details_observed` 永远是 `null`**
   ⇒ 网格分支管不到它们（它们不是网格行），而详情页那张帧**没有被任何观察器记账**。

**第 3 点是真正的落点**：真相已经在屏幕上了，只是没有一个观察器把它记下来。
所以缺的不是"导航能力"，是**"把已在屏幕上的事实记下来"的那个观察器**。

## 六、缺口最终定形：**识别缺失**，不是记账缺失

上一轮我把缺口写成"`read_entries` 没有写方"。本轮查清了整条链，**那句话只对了一半**，
而且不够准确 —— 真正的断点更早。

### 整条链都在，只在一处断开

| 环节 | 状态 |
|---|---|
| `read_event_detail` 识别器 | 存在（`event_calendar.py:801`） |
| `EVENT_DETAIL` 持久化 | 存在（`event_schedule.py:658-692`，`scope[kind] = snapshot`） |
| 回填网格行 `details_observed` | 存在（685-687 行） |
| 横条活动的 `read_entries` | **无**（因为它们不是网格行 ⇒ `matched` 恒为 `None`） |

**但即使接上，也仍然不收敛**，因为识别器先一步就拒了：

```python
explicit_calendar_detail = (
    "活动详情" in all_text
    or (date_range is not None and any(m in all_text for m in (
        "活动时间", "开始时间", "结束时间", "报名时间", "战斗时间", "开放时间")))
    or (date_range is not None and "前往" in all_text and any(_candidate_title(...)))
)
if not calendar_score_panel and not explicit_calendar_detail:
    return {"kind": "EVENT_DETAIL", "recognized": False, ...}
```

而 `峡谷会战` 详情页上**没有**这些标签——它印的是：

```
战斗开始倒计时 07:53:19
参赛人数: 30/30
赛区：??? / ??? / [DW]凌霄阁
页签 1 / 2
```

**有倒计时，没有"活动时间"字样** ⇒ 识别器答 `recognized=False` ⇒
`record_calendar_snapshot` 根本不会走到 `EVENT_DETAIL` 分支 ⇒
`EVENT_DETAIL` 存储里两个角色记的**都是网格活动**（`盛会商铺`，
`calendar_origin=GRID_ENTRY`），`observed_at` 停在 06:01:57 / 前一天 23:39。
**我 06:06 抓到的那张峡谷会战详情页，从未被记录。**

### 修正上一轮的说法

- 上一轮写：「缺的是把已在屏幕上的事实记下来的**观察器**」—— **对**；
- 上一轮写：「`read_entries` 有读方无写方」—— **字面对但不是根因**。
  即使补上写方，识别器先拒 ⇒ 债务照样消不掉。
  **顺序是：识别 → 持久化 → 记账，三环缺一不可，而现在缺在第一环。**

## 七、下一步（范围已收窄到一个函数）

要改的是 `read_event_detail` 的判据，**不是** `calendar_scan_due`、不是
`advertised_but_unread_activities`、不是 `read_entries`。

但**这一处不能照着"加个关键词"来改**，因为它自己的注释写着：

> A bare date range remains an activity/calendar preview. It is never promoted to a
> battle session or role reservation.

也就是说：**"客户端在某个页面印了倒计时"不足以推出活动窗口**。
要判断 `战斗开始倒计时 07:53:19` 是不是一个可登记的活动时间，
需要的是**页面身份**（这是峡谷会战的详情页）而不是**文本形状**。

所以正确形态是：

1. 先用**当帧可观察**的页面身份确认"这是 `CANYON_CLASH` 的详情页"
   （顶部横条里它是选中态 + 页面标题 `峡谷会战` + 右栏功能入口清单）；
2. 确认之后，**只为"证明已读到"记一个 `details_observed` 式的标记**；
3. **不要**顺手把倒计时写成 `start`/`end` —— 那是另一个决定，需要按活动逐个确认。

**在第 1 步的"页面身份如何可靠判定"有答案之前不写代码。**
本会话已连续三轮改错方向（排序 → 记账 → 假设识别已足够），
根子是同一个：**在没有落地观察过那个页面的情况下改代码**。
