我只证明了"无损 + 是本地追加"。**若其中有重复段落，属知识整理问题，另论。**

## 三、为什么会漏

**数据根 / pin 树的提交不对称** —— 这是本项目一直在踩的那条：
**会话把产物写在数据根（`E:\无尽冬日智能体`），而提交只能在 pin 树做。**
（本会话每一轮的 handoff 都是我**手工 `cp` 到 pin 树**再提交的，就是为这个。）
⇒ `.workbuddy-ai/memory/` 的追加**同样是写在数据根、没有对应的 `cp`+commit 步骤** ⇒ 一路攒了 8 天。

## 四、反面：为什么 `tools/` / `docs/` 是旧的（**未证**）

`tools/` 是 8 ins / 626 del（磁盘旧），`.workbuddy-ai/commander/` 亦然；而 `winter_agent_v2/` 却**一致**。
最自然的猜想是"HEAD 曾**不经检出**地前进，之后只补了 `winter_agent_v2/`"，
但**没有证据**，**本轮没有改它们**（旧的就是旧的工作树，改动风险高于收益；
且它们不在生产链路上，生产只跑 pin 树）。

## 五、能说 / 不能说

- **能说**：① 数据根工作树**按目录各自漂移**，已测；② `.workbuddy-ai/memory/` 有 **10,293 行**
  纯追加未提交，**已保入库 `80172006`**；③ 两棵树一致（`MAINLINE_OK`）。
- **不能说**：① `tools/`/`docs/` 为何旧（**机制未证**）；② 那 10,293 行的内容质量（**未审**）；
  ③ 还有没有别处（`config/` 之外）在"只写数据根、不进库"。

## 六、建议（**未做**）

   数据根完全在盲区）。**但数据根含运行态数据目录**，尺子必须**只对代码/知识目录**定性。
