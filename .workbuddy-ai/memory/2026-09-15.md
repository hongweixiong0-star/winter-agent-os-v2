# 第三轮（2026-09-15 00:50Z 起）：先修「最高失败」的排序口径 —— 否则每轮都会追死问题

## 为什么这比修一个 bug 更值钱
`update_workbuddy_handoff.py` 的 `top_failures` 按**全时段计数**排序，于是 AUTO 块写着：

    CURRENT ROOT CAUSE: SEMANTIC_TARGET_NOT_VERIFIED x112

按天拆开：**09-12: 36 / 09-13: 37 / 09-14: 8 / 09-15: 0**（另 31 条无 `recorded_at`）。
`MARCH_PAGE_NOT_OPEN x59` 更极端：**59 条全部在 09-12 一天**。

⇒ 于是流传着两个错误印象：
1. 「`SEMANTIC_TARGET_NOT_VERIFIED` 是当前头号根因」——今天 0 次，最后一次是 09-14T14:08。
2. 「`START_GATHER` 是 94 次尝试 / 37% 成功率的最差高频技能」——**那 59 次失败全部是 09-12 的
   `MARCH_PAGE_NOT_OPEN`**；09-13 之后它零失败。它被扣上 `degraded` 帽子完全是历史包袱。

本轮差一点就按第 1 条去开工。**这不是报告问题，是决策输入被污染**。

## 改法（`tools/update_workbuddy_handoff.py`）
- `episode_state()` 为每个 failure_type 记录 `recent` / `last_seen` / `dates` / `undated`；
  `recent` 的窗口是**相对最新 episode 时间**的 2 天（`RECENT_WINDOW`），按**完整 ISO 时间戳**比较，
  不是按日历天 —— 否则「某天有一条新的」会把那天 47 小时前的失败也算成 recent。
- `top_failures` 改为 **`key=(-recent, -count)`**：近期优先，全时段计数作次键。
- `CURRENT ROOT CAUSE` 走新的 `failure_rank_line()`：recent=0 时直接输出
  `HISTORICAL, do not treat as the current defect`。
- `04_OPEN_ISSUES` 的机器块也带 `recent=` 与 `last seen`。
- `tests/test_handoff.py` 加 4 项护栏。⚠ **坑：pytest 默认只收集 `Test*` 类**，
  我第一版写成 `class FailureRecencyTests`（无 `Test` 前缀）→ 测试**静默不被收集**（10 passed 而不是 14）。
  已改成模块级函数并把这个坑写进测试 docstring。

### 真根因（**推翻 `0i` 旧记录**）
`0i` 把根因写成"外部编辑器回写过程中被加载"，并加了静态映射护栏 —— **那是错的**：

护栏查的正是这张静态表，所以**永远不可能**发现这个问题。
真根因是**同一帧算两次决策**：
```
runtime.py:387   decision = brain.decide(before, registry)   ← 第 1 次（并据此建后端路由）
Scheduler.tick   decision = brain.decide(world, registry)    ← 第 2 次，执行的是它
runtime.py:595   VERIFIED_ATOMIC[decision.skill](...)        ← 验证器绑第 1 次
runtime.py:612   episode 记 tick.decision                    ← 记录写第 2 次
```
而 **`RuleBrain.decide` 不是纯函数**：`brain.py:362` 置 `stamina_panel_checked=True`

`runtime.py:545` 的注释原文就写着 **"one router decision per step"** —— **代码违反了自己写下的不变量**。

3. `STAMINA_SOURCES_NOT_OPEN` 记在 `OPEN_INTEL` 名下（AUTO 表 `OPEN_INTEL(8)`），污染统计。

### 修法
`Scheduler.tick(world, decision=None)`：传了就用传入的决策，不传则照旧自己算（单测覆盖）。
`runtime.py:556` 改为 `.tick(before, decision)` ⇒ **一步一决策**。

### 没做的事（都是有意的）

- **没把红色变体加进 `BTN_BEAST_DISPATCH` 模板** —— 那只会让我们去点一个必被拒的按钮。
  现在"找到不到"恰好等于"不能点"，反而是对的；只是还没在 `brain.py` 里显式成文。
- **没真机复现**：两轮真机都没走到营地面板。生产单帧（真机帧 + 生产视觉栈）已验证，
  但 `cost_affordable` **没在真机运行中出现过**。

### 方法论教训

1. **"目标未验证"不等于"目标不在"。** 先打 ccoeff 分（带 SEARCH_MARGIN）再下结论 ——
   0.9152 立刻把"控件缺失"改成"外观变了"。我第一次测量**忘记加 SEARCH_MARGIN**，
   结果 scale 1.0 被判 skipped，差点得出"匹配度只有 0.49"的错误结论。
2. **UI 把状态编码进外观时，那是最强的信号源。** 客户端已经在按钮上写明"你付不起"，
   我们却一直在用 OCR 读别处的数字去猜。**先问"客户端自己怎么表达这件事"**，再想怎么识别。
3. **`d=0` 的自匹配又一次出现。** 模板从父帧同一 ROI 裁出 ⇒ 父帧 d=0 说明不了任何事。
   这是我第几次记这条了 —— 但这次它换了个形式：不是"故意自裁自匹配"，而是
   "沿用了现成的 ROI"，效果一样。
4. **不要把"变体"不加区分地加进模板。** 加一个"红色出征按钮"模板会让点击成功，
   然后被客户端拒绝 —— 把一个明确的信号变成一次失败的动作。
   **先问"匹配上了之后我们要做什么"，再决定要不要让它匹配上。**
