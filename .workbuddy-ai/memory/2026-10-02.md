# ⭐ 第四段：观察票（observation ticket）对它的目标永远是 0 —— 又一个「机制已有、条件写反」

## 发现（用代码而非推断回答）

`goal_utility.observation_ticket()` 的门是：

```
status == UNKNOWN  且  evidence["required_observation"] 为真      ← 两道声明门
raw = deadline_pressure + reward_value + daily_loss + event_synergy + development_value
      - resource_cost - risk
if raw <= 0: return 0.0                                          ← 第三道门
return min(300, raw * 0.5)
```

**第三道门是循环的**：一个**从未被观察过**的目标，它的价值项**必然是 0**——
「还没观察过」正是它没有任何已测价值的原因。

`USE_FREE_ARENA_ATTEMPTS` 与 `LABYRINTH_DAILY` = `status=UNKNOWN`、

`reward_value / daily_loss / event_synergy / development_value / resource_cost / risk`
**全部 0.0** ⇒ `raw = 0` ⇒ 票 = 0 ⇒ `utility` 给 `base=-inf` ⇒ `rank()` **把它们丢掉**。

⇒ **这个机制对它所针对的目标完全失效**，而 Codex 自己的注释还写着
「`USE_FREE_ARENA_ATTEMPTS` 这类有 `required_observation` 的 UNKNOWN **现在能进板了**」——

### ① 写给模型的提问，从没送到模型手里

`unknown_advisor.UnknownRequest.question` 是 runtime 亲手写的、指名道姓的一句话：

> 这张屏幕（页面模型读作 MAP…）上，与当前 Goal AVOID_STAMINA_WASTE 相关的控件在哪里？

历史 / 会话，**唯独没给它**。

**修法**：`build_packet` 增加有上限的 `question` 字段（仅非空时携带），`take_request` 把
request 自己的 question 传进去，`SYSTEM_PROMPT` 按其余 packet 段的写法**说明这个字段**。
选择「把字段接活」而不是「删掉死字段」的理由：runtime 已经把
`_unknown_semantic_target` 用 `try/finally` **限定在 advisor 调用内**——那是调用方在表达
「我要什么」，不是给账本用的元数据。

### ② 正确的 id 因为它的标点被拒

`parse_plan` 里唯一被 **id 本身**拒掉的真实 EXECUTE 是：

```

```

**之后的每一道检查原样保留**：本帧没产出的 id 仍被拒；`executable is False` 仍被拒
