# ⭐ 第四段：观察票（observation ticket）对它的目标永远是 0 —— 又一个「机制已有、条件写反」

## 发现（用代码而非推断回答）

`goal_utility.observation_ticket()` 的门是：

```
status == UNKNOWN  且  evidence["required_observation"] 为真      ← 两道声明门
raw = deadline_pressure + reward_value + daily_loss + event_synergy + development_value
      - resource_cost - risk
if raw <= 0: return 0.0                                          ← 第三道门
return min(300, raw * 0.5)
```

**第三道门是循环的**：一个**从未被观察过**的目标，它的价值项**必然是 0**——
「还没观察过」正是它没有任何已测价值的原因。

`USE_FREE_ARENA_ATTEMPTS` 与 `LABYRINTH_DAILY` = `status=UNKNOWN`、

`reward_value / daily_loss / event_synergy / development_value / resource_cost / risk`
**全部 0.0** ⇒ `raw = 0` ⇒ 票 = 0 ⇒ `utility` 给 `base=-inf` ⇒ `rank()` **把它们丢掉**。

⇒ **这个机制对它所针对的目标完全失效**，而 Codex 自己的注释还写着
「`USE_FREE_ARENA_ATTEMPTS` 这类有 `required_observation` 的 UNKNOWN **现在能进板了**」——

### ① 写给模型的提问，从没送到模型手里

`unknown_advisor.UnknownRequest.question` 是 runtime 亲手写的、指名道姓的一句话：

> 这张屏幕（页面模型读作 MAP…）上，与当前 Goal AVOID_STAMINA_WASTE 相关的控件在哪里？
> **当前无法定位的语义目标为 BEAST_SEARCH_TAB。只推进这个目标**，不打开无关功能。
> 请给出定位依据与 proposed_action。

`knowledge_preload`）。`build_packet` 给了 goal / current_page / available_elements /
历史 / 会话，**唯独没给它**。

**修法**：`build_packet` 增加有上限的 `question` 字段（仅非空时携带），`take_request` 把
request 自己的 question 传进去，`SYSTEM_PROMPT` 按其余 packet 段的写法**说明这个字段**。
选择「把字段接活」而不是「删掉死字段」的理由：runtime 已经把
`_unknown_semantic_target` 用 `try/finally` **限定在 advisor 调用内**——那是调用方在表达
「我要什么」，不是给账本用的元数据。

### ② 正确的 id 因为它的标点被拒

`parse_plan` 里唯一被 **id 本身**拒掉的真实 EXECUTE 是：

```

```

模型**认对了**元素，只是把读到的字一起写进了 `target_element_id`。精确串比较把正确答案丢了。

**修法**：先读前导 `E\d+`（`ELEMENT_ID_PREFIX = re.compile(r"^E\d+\b")`），
**之后的每一道检查原样保留**：本帧没产出的 id 仍被拒；`executable is False` 仍被拒
（E21/E24 被 `TEXT_LABEL` 拒就是它干的）；拒绝信息**仍引用模型自己的原串**。

## WB-1002-16-GATHER-FORMATION-ROLE-SCOPE（采集最后一跳；已上线，真机效果未观测）

**工单的前提是错的，而数据纠正了它。** 工单写的是"编队不是角色域的，把它修成角色域"。
实测结论相反：**编队是角色域的、策略已经满足、点击已送达、行军已经发出去了 —— 验证器仍然判它失败。**

**行自带证明，这是最该先看的东西**：

```
before  page=MARCH  marches=[]            march_used=None
after   page=MAP    marches=['MARCHING']  march_used=1
```

两帧之间**出发了一支行军**，而这一行的 `result` 是 `FAILURE`（`executor_backend=MAA` ⇒ 点击已送达）。
运行随后**把整条 搜索→提交→采集→清空 流程又走了一遍**（step17–20）去追第二次。
**⇒ 可复用：判一个 FAILURE，先把它自己的 `state_before`/`state_after` 并排看**
——若两帧之间被试动作真的发生了，那这不是"被拦住了"，而是**假阴性**。

**根因：两个伪造值在一处比较里相遇。** 八个子条件里**七个为真**，唯一为假的是

```
formation.resource_type ("WOOD") == before.resource_target ("MEAT")
```

而 `resource_target` 在该 episode **从第 7 步到第 20 步一直是 MEAT，从未是 WOOD**。WOOD 来自两端：

- `vision.py` 从出征按钮的模板**合成了** `WorldState(page=Page.MARCH, resource_target="WOOD")`。
  画面从没说过 WOOD（编队页头部印的是 **生肉**，而**没有任何声明的读取记录**去读它）；
  同一条 if 链里的兄弟分支只声明自己模板能证明的东西，**只有这一条发明了资源**。
- `_annotate_gather_formation` 把那个值**冻进证据**，兜底用的是 `_active_gather_resource`
  —— **另一个目标的计划记忆**（只在 GATHER_RESOURCE 目标运行时写入，而本 episode 的目标是 ALLIANGE_TIMED_EVENTS）。

**⇒ 可复用：一条永远无法满足的子句，回头查它的两侧是不是都指向同一个来源或都是发明值。**
而且这条子句**短路在角色域判定之前**，所以底下的策略**从未被算过** —— 这也是循环反复盲目清空英雄的原因。

**用真实策略重放记录下来的编队，运行做的事全是对的：**

```
step14 policy(MEAT) -> CLEANUP_REQUIRED remove=[2,3]   它清了 2、3
step15 policy(MEAT) -> CLEANUP_REQUIRED remove=[3]     它清了 3
step16 policy(MEAT) -> READY_WITH_SPECIALIST remove=[] ……然后被拒
```

**修法（保留守卫、只是不再说谎）**：读取器不再发明资源；编队记录在值旁边记**来源**
（`resource_observed` 是帧给了什么，`resource_source` 是 PAGE/PLANNED/NONE）；
计划在**知道计划的那一处**盖章（就是写 `world.resource_target` 的同一处，所以两者不可能再不一致）；
验证器的资源子句只拦**页真的说了且不一致**的情况，否则记 `NOT_STATED_BY_PAGE`。
