## 9. §3/§14/§15 落地：让**鱼饵预算**而不是活动倒计时决定钓鱼的紧迫度（提交 `b2cb6f1`）

### 9.1 先看清真实缺陷所在

上一轮我以为 §3/§15 要新写一个"饵调度器"。查下来发现**缺陷在排序层，且就在既有代码里**：

- `goal_library` 为任何在屏的限时活动发**同一个** `EVENT_MINIMUM_GUARANTEE` 目标，
  并把 `remaining_seconds` 直接取客户端打印的倒计时；
- `deadline_pressure` 把 24h 内的任何倒计时折成加分：`<2h → +10000`、`<6h → +4000`、
  `<12h → +2000`、`<24h → +1000`；
- 钓鱼活动开 **2 天** ⇒ 在原始倒计时下，它**全程**带着 `+1000…+10000`，
  几乎每帧都从当前 Role Session 手里抢走设备 —— 正是 §3/§14 明令禁止的。
  （`fishing_tournament_rules.json` 里 `calendar_window … end 2026-10-01 24:00`。）

⇒ 所以正确做法不是加新调度器，而是**把钓鱼事件的 `remaining_seconds` 换成由饵预算派生的、
有条件的存在**。

### 9.2 条件（`winter_agent_v2/fishing_pressure.py`，纯函数、无 I/O）

| 压力 | 目标携带 |
|---|---|
| `NORMAL` / `UNKNOWN` / `NO_BAIT` | 普通：**无 deadline、无加分**（§3/§14） |
| `CAP_FULL` | 只加 `event_synergy`（`+1500`），**不设 deadline**（§3 A：优先级可升，但不满仓就硬抢设备） |
| `ENDGAME` | 用**实测**倒计时当真 deadline（§15），触发既有硬抢占 |

`status` / `window_closed` / `EXPIRED`/`COMPLETE` **一律不动**——它们说的是活动窗口，
不是"钓鱼多想拿设备"。客户端倒计时仍原样记进 `evidence.client_remaining_seconds`，
两个数字都能审到。

### 9.3 接线（不建第二套调度器）

- `GoalLibrary.discover(..., fishing_pressures=None)`：**可选**参数，不传 = 逐字节同旧行为

## 11.5 诚实标注：一条实测出来的能力边界

**运行中的第一轮会话没有抢占预言机。** `LiveRuntimeSessionHost.yield_verdict` 读 `runtime._scheduler`，
而一个 run 只在**即将派发原子步**时才创建它（`_session_execute_atomic` / 主循环 7386）。
所以：
- 一轮 run 的**第一次会话**、且在它执行任何一步之前，ladder 无法抢占它；
- 一旦会话执行了任意一步（→ `_session_execute_atomic` 建好 scheduler），**后续每个安全点都能被抢占**。

有界（会话有步数/时间预算，最多几秒内自然结束），方向也是安全的那一侧（默认"不放弃设备"），
但这是事实，不是设计意图，所以写进测试模块的文档字符串并在抢占测试里**显式声明前置条件**。

# 14. #44 STILL_PENDING：一个「测量」任务推翻了自己的前提（提交 51895ff）

## 14.1 最重要的方法教训：测量任务可能先要修测量工具

任务的原文是「改变前应先测『连续 STILL_PENDING 的分布』」。我先照着测，结果是**测不出来**——
不是样本少，而是这个分布在生产账本里**根本不存在**。这类信号很强：当一项「读数」任务
给出的数字看起来不对劲（严格读数直接是空的）时，**先去问记录这一层有没有在说真话**，
而不是回头怀疑样本量。本轮如果直接按 reason 反推就定阈值，会得到一个建立在「一个被重载的
字符串」上的设计，而且永远无法事后校验。

## 14.2 顺带修掉的三个更基础的缺陷（都在证据链上，不在业务逻辑上）

1. **outcome 从未被持久化。** `_record_episode` 收下 `session_outcome`，只用它挑一个
   `result`，然后丢掉；`Episode` 没有这个字段。唯一保有真值的 `StepReport.outcome` 被
   append 到 `session_host.step_reports`，而该 list **只写不读**（133 声明、333/335 追加，
   全仓库无消费点）。这是「写了但写进了没人读的地方」的典型：机制都在，只是断了一截。
2. **`STILL_PENDING` 不在折叠的集合里。** `{"PROGRESS","AMBIGUOUS"}` 不含它 ⇒ 落到默认
   `result="FAILURE"` + `failure_type="NO_EXECUTION"`，44 行把「钓还在水里」写成「钓失败了」。
3. **`result` 跨修订不可比。** `fa476b6` 之前 60/60 会话步全是 `FAILURE`（连 adapter 明确
   返回 `SUCCESS` 的 `FISHING_CAST_VERIFIED` 也是）。**仓库自带的两个异常判据全部早于该修复**：
   `VERIFIER_CONFLICT`（`state_truth.py:1532`，面板实测信号）5 pre / 0 post；
   `goal_progress && result=FAILURE` 42 pre / 0 post。也就是说，面板上那个告警完全是缺提交的产物。

## 14.3 数字（快照：账本 10,272 行 / 108 会话步 / 29 会话；HEAD dab79cf）

run 直方图 `1x1, 2x5, 4x1, 5x1, 8x3`（2 与 4 之间有空缺）；最长 8 = `step_budget(10) − 2`；
11 个 run 里 **7 个 resolve**、4 个死在预算上。

步数阈值决策表（关键列是「本会 resolve 的 run」= 误报）：

| N | 触发会话 | 误报 | 误报率 |
|---|---|---|---|
| 2 | 10/11 | 7 | 0.70 |
| 3–4 | 5 | 2 | 0.40 |
| 5 | 4 | 1 | 0.25 |
| **6** | **3** | **0** | **0.00** |

⇒ `session_engine.py:997` 排除 STILL_PENDING 是**必要的误报护栏**，这个设计决策被数据支持。

## 14.4 但决定性的数字是墙钟：0.345 秒

run 内每步中位 **0.0372 s**；最长 run（8 步）合计 **0.345 s**；而被它等待的抛竿步
（`FISHING_CONTROL_SESSION_RAN`）耗时 **8–27 s**，路线的 `time_budget_s` 是 **150 s**。
⇒ 这不是等待，是 **30 ms 忙旋**；10 步预算 0.3 秒烧完，时间预算从未被碰到。
⇒ **「步数」不是物理量**（与机器速度、与有无 sleep 耦合，跨会话不可比）。所以界应按
**距上次被接受进展的墙钟时长**计，而不是按步数。

设计结论：**不要**把 STILL_PENDING 喂进 `LOOP_DETECTED`。检测器的定义是「一个被答复过的
动作没有改变任何东西」，STILL_PENDING 是「还没有答复」——两种事实两种补救，混用会让一个
指标变成两个意思。检测器**已经**复用了四条业务线；钓鱼缺的不是检测器覆盖，是**一个真正的等待**。

根因定位：`session_engine.py:718-731` 里**已有**带界、会 sleep 的 `_wait_for_work`
（计 `state.waits`、有 deadline、有租约检查），只在 `choose_step` 返回 `None` 时可达；
而钓鱼 adapter 返回 `SessionStep(0, STEP_OBSERVE_ONLY, tags={"wait_result": True})`
（`session_adapters.py:464-466`），**无任何延迟** ⇒ 引擎自带的等待从未被走到（实测 `SESSION_WAITS=0`）。

H1（待真机判定）：那三个死在预算上的会话不是「鱼一直没来」，而是「轮询只给了客户端 0.3 秒
渲染」。7/11 个 run 在 1–5 次轮询内就看到结果，说明渲染在这些情况下早已完成。
判定实验：有结果页的那一竿之后把轮询间隔改为 sleep 1s，看第 2–10 次是否出现结果页。

## 14.6 A/B 归因：既有失败要用「回退 + 校验」证明，不能靠推理

`tests/test_backend_provenance.py` 有 2 个失败。做法：`md5sum` 记录 → `git stash push` 只回退
我改的 4 个源码文件 → 重跑 → **同样 2 个失败** → `git stash pop` → 校验。

**踩到的坑**：`core.autocrlf=true`，stash pop 后 git 用 **CRLF** 重写了文件，
于是 `md5sum` 不匹配（内容其实没变）。正确的校验方式是 `git diff --stat` / `--numstat`
（本次 17/21+3/14/14+3 逐位一致）。**md5 在跨 git 操作后不是内容校验器。**

## 14.7 两个工具习惯

* **自适应审计脚本**：脚本对**磁盘上的源码**断言（`assert 'if session_outcome in {...}' in runtime.read_text()`），
  而不是在注释里引用行号。后者会腐烂，前者会在代码改动时变红。
  本次产物 `audit_outcome_persistence.py` 的 `verdict` 五个布尔全部可复现。
* **账本是活的**：本次会话期间它从 10,264 → 10,296 行。所以度量脚本现在把
  `ledger_rows_at_measurement` 写进 JSON。**数字不带宽度的快照就不是证据**（13.1 的同一条延伸）。
