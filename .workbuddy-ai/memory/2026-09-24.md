# 2026-09-24 — UNKNOWN 自动作答链与正式 AUTO 消费闭环

## 一句话结论

UNKNOWN 通道从"能自动记录问题"升级到"能自动提出问题、自动起后台作答作业"：
真正的断点是**网关启动时缺少 bundle 选择变量**，导致每个作答 worker 启动即崩；
修好后又暴露出**服务继承了 agent 工具链环境**（本项目自己造成的污染），
激活了产品的批量删除保护，使 `POST /api/v1/jobs` 全线 500。两者都已修复并提交。

## 事实（可指到文件 / 进程 / commit）

### 一、`session ended` 到底结束了什么（这是本轮最重要的澄清）

网关对一条 job 报：

```
state  : failed
detail : session ended — press enter to restart it
output : null    result: ""
```

这句话**不是**指 WorkBuddy 聊天会话，也**不是**指本项目的 Python：
它是 `reapDeadJobs`（发行包模块 `88381`，`ep="session ended — press enter to restart it"`）
在"job 记录的 pid 已不存在、job 未终态、且未被 park"时写下的，即**该 job 的 worker 进程死了**，
且是在进程退出约 60 秒后才写，所以它只说"worker 死了"，从不说为什么。

**worker 为什么死**：job 自己的日志里有答案。每个 job 一份日志
（`state.json` 的 `logPath`，默认 `~/.codebuddy/logs/job-<shortId>.log`）：

```
Error: Cannot find module '../dist/codebuddy'
    at ... cli/bin/codebuddy:205:13    code: 'MODULE_NOT_FOUND'
```

`cli/bin/codebuddy` 只有三条 bundle 分支，本机 `dist/` 只有其中两个产物：

| 条件 | 装载 |
| --- | --- |
| `CODEBUDDY_FORCE_LITE_WB_BUNDLE=1` | `dist/codebuddy-lite-wb.mjs` |
| `CODEBUDDY_FORCE_HEADLESS_BUNDLE=1` | `dist/codebuddy-headless.js` |
| 两者都没有、argv 也无 `--print/-p/--acp/--bg/...` | `dist/codebuddy.js` ← **本机不存在** |

本机双向复现（同一条 stack）：
`unset 两个变量 → --serve` 崩在 `:205`，`exit 1`；`CODEBUDDY_FORCE_HEADLESS_BUNDLE=1 → --serve` 正常绑定。

**为什么本项目必须自己设**：网关用 `{...process.env}`（**网关自己的环境**）派生每个 worker
（`forkBgSession` → `forkDetached`），只额外加 `CODEBUDDY_JOB_*`，从不加 bundle flag；
而 `GatewayService._spawn` 用 `{**self.env, **plan.env}` 起网关。
所以 worker 装载哪个 bundle，完全由**网关进程的环境**决定。

### 二、修复

1. `winter_agent_v2/gateway_service.py: build_plan()` 增加
   `LaunchPlan.env = {CODEBUDDY_FORCE_HEADLESS_BUNDLE: "1"}`（**追加**，不替换，凭据仍继承）。
   选 headless 而非 lite-wb：worker 是完整的非 TUI agent turn，`--print/--acp/--bg` 都路由到 headless。
2. `winter_agent_v2/unknown_dispatch.py`：
   - 每次 reconcile 记录 `failure_class`：`WORKER_DIED` 只在**有正面证据**时
     （网关的 `session ended`/`parked` 原话，或 `JOB_LOST`），其余记 `NO_ANSWER`；
   - 两套预算分开：`MAX_ATTEMPTS_PER_REQUEST`（问题自己答不出来）
     vs `MAX_WORKER_DEATH_ATTEMPTS`（通道起不来 worker），
     后者不消耗前者，且冷却时间按"连续 worker 死亡数"放大；
   - `health()`：连续 worker 死亡 ≥2 报 `DEGRADED`；
   - `updated_at` 只由 `submitted/reconciled/submit_failed` 推进
     —— 记账行（`reclassified`）不得重置重试时钟（实测被加了 45 分钟罚时）；
   - 帧文件已不存在的请求不再占用唯一的作答槽位。
3. `tools/unknown_reclassify_failures.py`（新增，证据门控的一次性工具）：
   只在该 job 的日志**证明** worker 从未启动时，追加一条引用日志路径的 `reclassified` 行。
   18 条历史 job 里命中 **2 条**（`0c32a4bd`、`b25c1f12`），其余保守判给问题本身。
4. `winter_agent_v2/gateway_service.py: service_environment()`（新增）+
   `GatewayService.__init__` 净化环境：删除 `AGENT_SESSION_MARKERS`
   （`CODEBUDDY_TOOL_CALL_ID`、`CODEBUDDY_SAFE_DELETE_*` 等）——见下。

### 三、本项目自己造成的第二次故障（重要教训）

用 agent shell 重启网关后，网关继承了该 shell 的工具链环境（195 个变量，含
`CODEBUDDY_TOOL_CALL_ID=call_00_…`、`CODEBUDDY_SAFE_DELETE_BULK_*`）。
worker 又继承网关环境 → worker 的 shell 会话里**武装了批量删除保护** →
网关自己回收陈旧 job 锁（89 个路径）被 refus 掉：

```
POST /api/v1/jobs -> HTTP 500 [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
{"count":89,"threshold":50,"scope":"turn","targets":["…\\.locks\\…"]}
```

对照实测：未受污染的网关 58 个环境变量、不含这些；本会话起的网关 195 个、包含它们。

**教训**：长驻服务必须用 `service_environment()` 起点，不能从"agent 工具调用"里继承环境。
产品自己也做了同类清理（`scrubRequestContextFromEnv`）。

## 补充（23:40 UTC）— 最后断点已定位到毫秒级；并确认能力层缺失

### 断点（用 `_probe_lifecycle.py` 0.25 秒采样作业自己的 state.json）

面板启动的网关（配置根 = CLI 默认 `~/.codebuddy`），作业 `7d253d09`：

```
 0.04s submitted
 0.79s worker pid 记录（procStart 已写）
 2.04s broker.json 出现        <- worker 已宣告自己的 attach 管道
 3.05s colleague-inbox/
 3.30s inbox/
 6.57s detail -> 'preparing'
 8.34s WORKER 进程消失
21.88s 网关判 failed / 'session ended — press enter to restart it'
```

**worker 确实越过了启动**（`.workbuddy` 根下的作业整整 45 分钟停在 `starting…`，
说明配置根是真实变量），然后在 **8.34 秒静默退出**：日志只有 183 字节（仅 no-orphans 警告），
**全过程没有发出任何模型请求**。

**用产品自带的 `codebuddy attach <pid>` 挂上客户端后**（作业 `c0df8fa2`）：

```
 6.76s detail -> 'preparing'
 8.27s detail -> 'idle'        <- 越过 8 秒点，变成一个在听消息的 background session
26.79s failed / 'session ended'，result 为空
```

`idle` 是"会话已经起来、在等一条消息"的状态。**worker 不是答不出来，而是没人问它。**
历史上所有真正跑过的作业都带 `broker.json` + `attachSocket`（管道上有人），正是同一件事的反面。

### 能力层（§三 的结论）

`forkBgSession` 给 worker 的就是**网关自己的环境**。实测：

| | 变量数 | 关键项 |
| --- | --- | --- |
| 我们的网关 :8080 | 61 | 只有 `FORCE_HEADLESS_BUNDLE` / 网关口令 / 内网标记，**没有其它 `CODEBUDDY_*`** |
| 应用的单会话边车 | 146 | 多出 86 项：`CODEBUDDY_HOST=workbuddy-desktop`、`CODEBUDDY_HOST_CAPABILITIES`、`CONFIG_DIR=~/.workbuddy`、`WORKBUDDY_PAC_RPC_TOKEN`、产品配置溢出路径，argv 里还有 `--settings/--mcp-config/--prompt-vars-file` |

两个环境里都没有模型凭据：模型访问是应用**为自己 spawn 的会话进程**接上的。
我们自己 fork 的 worker 一样都拿不到。独立佐证（`_probe_headless_turn.py`，不经过作业机制）：
用**网关自己的环境**跑一次 `cli/bin/codebuddy` 的单轮（含 `-p`，两种配置根都试），
150s / 240s **均超时无回复**。

**结论**：在拿到一条不属于 WorkBuddy 会话的、被授权的模型访问通道之前，
UNKNOWN 通道无法自己作答。复制 `WORKBUDDY_PAC_RPC_TOKEN`、借会话 argv 等**一律不做**（用户已明确禁止）。
诚实的选项只有 (a) 为项目申请一个受控的服务凭据，或 (b) 承认作答仍由会话驱动并如实说明。

### 本轮顺带确认的两件事

- 桌面端为每个会话起独立 `--serve` 边车（argv 带 `--settings/--mcp-config`），
  且应用配置文件根是 `~/.workbuddy`；`bin/codebuddy` 默认根是 `~/.codebuddy`。
  网关从"agent shell"启动会把 `CONFIG_DIR` 一起带进去——这解释了此前 `starting…` 的停滞。
- 面板自己重建网关时用的是**面板环境**（61 项），带 `FORCE_HEADLESS_BUNDLE=1`（说明修复已进入生产路径）、
  无工具链污染、无 `CONFIG_DIR`。即：生产路径本身现在是对的，卡点在更下面一层。

## 补充（07:40–08:05 本地 / 23:40–00:05 UTC）— 官方接口核查：两条路径的第一个真实差异

### 核查了哪些官方接口

- 读了官方文档：`codebuddy.ai/docs/zh/cli/http-api`（本地 CLI HTTP API）与
  `open.workbuddy.cn/docs/openapi`（WorkBuddy 开放平台）。
- **本机网关实际是 2.147.0**（`GET /api/v1/info`），`GET /api/openapi.json` 可用，**117 个端点**。
  这纠正了契约文档 §3 的旧结论（"没有可访问的 OpenAPI 文档，只能读 bundle"）。

### 重要澄清：本地 API 的凭据是"网关口令"，不是账号凭据

官方文档明确：`--serve` 默认口令认证，口令是本地生成的，用
`Authorization: Bearer <password>` / `X-Access-Token` / `gateway_session` cookie 携带；
**没有云端账号凭据、没有 API Key、没有 OAuth**，文档也完全不谈计费。
⇒ `CODEBUDDY_GATEWAY_PASSWORD` 只是"本地进程的门钥匙"。
能调通 API（health ok、job 建成、`POST /runs` 返回 202 accepted）**完全不能推出"能调到模型"**。

### 最小真实调用（都走官方接口，未伪造任何东西）

```
GET  /api/v1/sessions/live   -> {"sessionId": null, "writerOccupied": false}   ← 没有活会话
GET  /api/v1/daemon/status   -> {"status": "stopped"}
POST /api/v1/runs  {text:"Reply with exactly: PROBE_OK…"}
                             -> 202 {"runId":"701fd46c-…", "status":"accepted"}
GET  /api/v1/runs/{runId}    -> {"active": true}   210 秒，无结果
POST /api/v1/daemon/start    -> 200 {"status":"running","pid":26076,"endpoint":"http://127.0.0.1:9527"}
POST /api/v1/runs  再来一次   -> 又是 accepted，又是什么都没有，210 秒
POST /api/v1/daemon/stop     -> 已恢复 stopped，无遗留作业
```

**官方 `/runs` 与 `/jobs` 都被接受，但两边都没有可执行的会话**：网关接受了活，却没有活会话、
也没有受它管辖的执行体。在本网关里启动 daemon 也不改变这一点（daemon 继承同一套环境）。

### 两条路径第一个实际不同的环节

| | 桌面端（能用） | 本项目（接受但永不执行） |
| --- | --- | --- |
| 谁启动 | `WorkBuddy.exe` | 本项目的 `GatewayService` |
| 形态 | **每个会话一个边车**：`--serve --port 0 --session-id <会话>` | 一个共享网关：`--serve --port 8080` |
| 额外 argv | `--settings`、`--mcp-config`、`--prompt-vars-file`、`--allowedTools`、`--model`、`--permission-mode fullAccess` | 无 |
| 环境 | 146 项，含 `CODEBUDDY_HOST=workbuddy-desktop`、宿主能力、产品配置溢出、`WORKBUDDY_PAC_RPC_TOKEN`、`CONFIG_DIR=~/.workbuddy` | 61 项：bundle 选择器、网关口令、内网标记——**没有模型/宿主接线** |
| 活会话 | 有（就是你正在对话的那个） | `sessions/live -> null` |
| daemon | 运行中（应用的） | `stopped` |

**第一个真实差异不是某个 flag、模型名、提示词或 worker，而是：应用启动的是"它自己作为宿主的会话"，
本项目启动的是"没有宿主的网关"。** 模型访问跟着"应用托管的会话"走，不跟着本地 API 走 ——
所以在我们自己的网关里无论怎么 fork / attach / 重试都造不出模型访问。
这也解释了 §9.5：worker 走到 `idle` 就停，因为它是一个没有宿主的会话。

### 还缺的那一环（官方路径）

WorkBuddy 开放平台就是为这件事准备的，且与本地网关 API 是**两套东西**：

- 认证：OAuth 2.1 授权码。需注册开发者账号 + 创建第三方应用（拿到 clientId/clientSecret），
  再由**用户本人授权一次**，换 `access_token` / `refresh_token`。
- 对应能力：`POST /openapi/v2/localassistant/message`（scope `user.localassistant.invokable`）
  ——"向 PC 端本地助理发送消息，触发助理执行任务"，配 `GET` 同一路径轮询回复。
  这正是"用户已经能用模型的桌面助理"。
- 积分：平台另有"兑换码/卡券为授权用户发放积分"接口，口径指向**用户自己的 WorkBuddy 账号积分**，
  但文档没有写明具体计量方式，需要以平台侧为准，不能在这里臆断。
- **本机目前完全没有这套授权**：项目与 settings 里都没有任何开放平台应用 / clientId / token。
  必须由用户去创建并授权；不能用网关口令推导，也不能自动开通。
