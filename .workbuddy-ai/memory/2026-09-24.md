# 2026-09-24 — UNKNOWN 自动作答链与正式 AUTO 消费闭环

## 一句话结论

UNKNOWN 通道从"能自动记录问题"升级到"能自动提出问题、自动起后台作答作业"：
真正的断点是**网关启动时缺少 bundle 选择变量**，导致每个作答 worker 启动即崩；
修好后又暴露出**服务继承了 agent 工具链环境**（本项目自己造成的污染），
激活了产品的批量删除保护，使 `POST /api/v1/jobs` 全线 500。两者都已修复并提交。

## 事实（可指到文件 / 进程 / commit）

### 一、`session ended` 到底结束了什么（这是本轮最重要的澄清）

网关对一条 job 报：

```
state  : failed
detail : session ended — press enter to restart it
output : null    result: ""
```

这句话**不是**指 WorkBuddy 聊天会话，也**不是**指本项目的 Python：
它是 `reapDeadJobs`（发行包模块 `88381`，`ep="session ended — press enter to restart it"`）
在"job 记录的 pid 已不存在、job 未终态、且未被 park"时写下的，即**该 job 的 worker 进程死了**，
且是在进程退出约 60 秒后才写，所以它只说"worker 死了"，从不说为什么。

**worker 为什么死**：job 自己的日志里有答案。每个 job 一份日志
（`state.json` 的 `logPath`，默认 `~/.codebuddy/logs/job-<shortId>.log`）：

```
Error: Cannot find module '../dist/codebuddy'
    at ... cli/bin/codebuddy:205:13    code: 'MODULE_NOT_FOUND'
```

`cli/bin/codebuddy` 只有三条 bundle 分支，本机 `dist/` 只有其中两个产物：

| 条件 | 装载 |
| --- | --- |
| `CODEBUDDY_FORCE_LITE_WB_BUNDLE=1` | `dist/codebuddy-lite-wb.mjs` |
| `CODEBUDDY_FORCE_HEADLESS_BUNDLE=1` | `dist/codebuddy-headless.js` |
| 两者都没有、argv 也无 `--print/-p/--acp/--bg/...` | `dist/codebuddy.js` ← **本机不存在** |

本机双向复现（同一条 stack）：
`unset 两个变量 → --serve` 崩在 `:205`，`exit 1`；`CODEBUDDY_FORCE_HEADLESS_BUNDLE=1 → --serve` 正常绑定。

**为什么本项目必须自己设**：网关用 `{...process.env}`（**网关自己的环境**）派生每个 worker
（`forkBgSession` → `forkDetached`），只额外加 `CODEBUDDY_JOB_*`，从不加 bundle flag；
而 `GatewayService._spawn` 用 `{**self.env, **plan.env}` 起网关。
所以 worker 装载哪个 bundle，完全由**网关进程的环境**决定。

### 二、修复

1. `winter_agent_v2/gateway_service.py: build_plan()` 增加
   `LaunchPlan.env = {CODEBUDDY_FORCE_HEADLESS_BUNDLE: "1"}`（**追加**，不替换，凭据仍继承）。
   选 headless 而非 lite-wb：worker 是完整的非 TUI agent turn，`--print/--acp/--bg` 都路由到 headless。
2. `winter_agent_v2/unknown_dispatch.py`：
   - 每次 reconcile 记录 `failure_class`：`WORKER_DIED` 只在**有正面证据**时
     （网关的 `session ended`/`parked` 原话，或 `JOB_LOST`），其余记 `NO_ANSWER`；
   - 两套预算分开：`MAX_ATTEMPTS_PER_REQUEST`（问题自己答不出来）
     vs `MAX_WORKER_DEATH_ATTEMPTS`（通道起不来 worker），
     后者不消耗前者，且冷却时间按"连续 worker 死亡数"放大；
   - `health()`：连续 worker 死亡 ≥2 报 `DEGRADED`；
   - `updated_at` 只由 `submitted/reconciled/submit_failed` 推进
     —— 记账行（`reclassified`）不得重置重试时钟（实测被加了 45 分钟罚时）；
   - 帧文件已不存在的请求不再占用唯一的作答槽位。
3. `tools/unknown_reclassify_failures.py`（新增，证据门控的一次性工具）：
   只在该 job 的日志**证明** worker 从未启动时，追加一条引用日志路径的 `reclassified` 行。
   18 条历史 job 里命中 **2 条**（`0c32a4bd`、`b25c1f12`），其余保守判给问题本身。
4. `winter_agent_v2/gateway_service.py: service_environment()`（新增）+
   `GatewayService.__init__` 净化环境：删除 `AGENT_SESSION_MARKERS`
   （`CODEBUDDY_TOOL_CALL_ID`、`CODEBUDDY_SAFE_DELETE_*` 等）——见下。

### 三、本项目自己造成的第二次故障（重要教训）

用 agent shell 重启网关后，网关继承了该 shell 的工具链环境（195 个变量，含
`CODEBUDDY_TOOL_CALL_ID=call_00_…`、`CODEBUDDY_SAFE_DELETE_BULK_*`）。
worker 又继承网关环境 → worker 的 shell 会话里**武装了批量删除保护** →
网关自己回收陈旧 job 锁（89 个路径）被 refus 掉：

```
POST /api/v1/jobs -> HTTP 500 [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
{"count":89,"threshold":50,"scope":"turn","targets":["…\\.locks\\…"]}
```

对照实测：未受污染的网关 58 个环境变量、不含这些；本会话起的网关 195 个、包含它们。

**教训**：长驻服务必须用 `service_environment()` 起点，不能从"agent 工具调用"里继承环境。
产品自己也做了同类清理（`scrubRequestContextFromEnv`）。

## 补充（19:10 UTC）— 本轮实测到的第四件事：fork 出来的 worker 起得来，但从不开始自己的 turn

修好 bundle 与 env 之后，worker **确实活了**（`a462d931` pid 15028、`9f3b53b8` pid 1788，
日志只有一句无害的 no-orphans 警告，**没有** `MODULE_NOT_FOUND`），但两者都停在网关自己的
`detail: "starting…"`：

- 30 分钟零 IO、CPU 只涨了约 3 秒；
- 到 `28.0.0.40:443` 有 3 条 ESTABLISHED 连接（控制/通知流），但**没有**任何模型请求发出；
- job 目录只有 `state.json` + `tmp/`，**没有** `broker.json` / `inbox/` / `colleague-inbox/`；
- 一次有界探针（`_probe_channel.py`，提示词只有 "Reply with exactly: PROBE_OK"）
  同样卡在 `starting…` 200 秒后被取消 → **与本项目的问句、截图、负载无关**。

**对照历史**（`~/.codebuddy/jobs/*`）非常清楚：

| job | broker.json | attachSocket | 结果 |
| --- | --- | --- | --- |
| `13ffdac6` | 有 | 有 | 约 26 分钟写出答案（唯一一次成功） |
| `06066de6` / `64f2f709` / `d1caa8e7` | 有 | 有 | 45 分钟 ABANDONED（跑满时箱但无产出） |
| `b25c1f12` / `0c32a4bd` | 无 | 无 | 启动即崩（`MODULE_NOT_FOUND`，1197 字节日志） |
| `a462d931` / `9f3b53b8` | 无 | 无 | worker 存活但卡在 `starting…` |

即：**历史上凡真正跑过的作业都带 attach 痕迹（有客户端接入 = `becomeWorkerInPlace` 那条路），
纯 fork 的作业要么死、要么卡。** 这不是本轮引入的——`b25c1f12`、`0c32a4bd` 之前的 ABANDONED
就已经是"跑满 45 分钟无产出"。

**结论（未解决）**：UNKNOWN 通道当前的最后一个断点是"fork 出的 worker 拿不到 turn"，
它使答案永远写不出。需要下一步定位：worker 在 `starting…` 阶段等的是什么
（`CODEBUDDY_JOB_CONTROL_SOCKET` / broker 握手 / attach），
以及为什么桌面端只在部分作业上 attach。

## 补充 — 正式 AUTO 的自动闭环已实测成立（这一段是证据）

19:06:50–19:06:55，**面板自己的时钟**（不是手工命令）一次性做完了 §四 要求的全套：

`in_flight = ['9f3b53b8']`，`pending = 7`。
