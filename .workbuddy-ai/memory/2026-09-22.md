## 根因（两条，缺一不可）

记录 `OPEN_TRAINING_PAGE|NO_GOAL_PROGRESS|BACK`（job 280d1659）等的版本是 `91e3475`，
而树已是 `d5b46c4`：

1. **跨进程版本断言形状不一致**（`escalation_queue.py`）
   - 写入端用的是 `after.head`（纯 sha），比对对手是 episode 的 `repo_revision`（`head+digest`）

     （`e304be3180e1b369` / `e324f8791464cd4b`），因为一跑就会写版本相关文件

   - 14:37→16:09 有 **30+ 次 acquire/release**，每次 "validation run finished"，从不收敛
   - `validation_command` 跑的是**工作树**、从不 checkout 版本
     ⇒ 索要已被超越的 commit **结构上不可能被满足**
   - 修：`_retire_superseded_version()`，记为 `NO_IMPROVEMENT` 并写明两个版本；

## 顺带修的真缺陷：读版本会阻塞写版本

`.git/index.lock` 停留 **40 分钟**且**无任何 git 进程**，`git add` 全部失败
（`Another git process seems to be running in this repository`），而 `git log`/`git status` 正常。

stat cache 去抢 index 锁。两处读取改用 `--no-optional-locks`。

⚠ **诚实边界**：**没有证据指认锁的归属**。实测（`tools/probe_git_index_lock.py`）：
无锁时两种形式都不留锁；**有 stale 锁时两种形式都能成功读**且都不动别人的锁
（只有 `git add` 被挡，rc=128）⇒ 可观测行为**无法区分**两者。
所以本轮删掉的是"进程被杀可能留锁"的窗口，不是一个已证明的肇事者。

## 第二处真缺陷：**空版本记录的租约抖动**（commit 391a7dd）

# 第十二段 — "已到达目标页面却不执行最后一步"：两个真实故障的断点

## 逐步追踪的结论（不是从截图推测）

### 故障 A：挂机收益弹窗
真机链路（11:19–11:21，共 3 次同样失败）：

```
Goal CLAIM_EXPLORATION_IDLE → OPEN_EXPLORATION（EXPLORATION 页，status=CLAIMABLE）
→ EXPLORATION_IDLE_CLAIM 点击 → 客户端弹出「挂机收益」弹窗（真机后帧已确认）
→ verify_exploration_claim_feedback: after.page 必须是 POPUP + popup==EXPLORATION_IDLE_DIALOG
→ 实际读数 page=UNKNOWN / popup=None ⇒ 报 EXPLORATION_IDLE_DIALOG_NOT_PROVEN
→ 没有任何技能能再动它（确认弹窗的技能 required_page=Page.POPUP）
→ 弹窗留在屏幕上，绿色「领取」无人按下。
```

**第一个断点**：`POPUP_EXPLORATION_IDLE_DIALOG` 在模板清单里**存在但 templates=0** ——
唯一识别路径永远不可能命中。而 OCR 把这帧读得很好：
`挂机收益`1.00@(0.501,0.233) / `挂机时间`1.00 / `领取`0.99@(0.501,0.723) / `挂机最多可获得9小时收益。`。
（另：`BTN_EXPLORATION_IDLE_CONFIRM` 的 ROI 中心 (0.50,0.725) 与 OCR 的「领取」(0.501,0.723) 差 2px ⇒ 按钮本来就能定位。）

**修复**：在 OCR 分类器里加一条按**帧上自己的词**识别该弹窗的规则（标题 + 副标题），
与既有的 `REAL_MONEY_OFFER` / `NEW_TROOP_UNLOCK` 两条同类规则并列。
真机帧复算：读数 → `POPUP/EXPLORATION_IDLE_DIALOG`，验证器 → **ok=True**，大脑 → `CONFIRM_EXPLORATION_IDLE_CLAIM`。

### 故障 B：射手营训练页
真机链路（11:23–11:25）：

```
11:23:59 DAILY_ACTIVITY_TARGET OPEN_INFANTRY_TRAINING  HOME→TRAINING
11:24:25 MARKSMAN_CAMP_TRAINING SELECT_TRAINING_CAMP     （换到矛兵营）
11:24:50 SHIELD_CAMP_TRAINING   SELECT_TRAINING_CAMP     （换到射手营）
11:25:16 LANCER_CAMP_TRAINING   BACK                      → HOME，训练按钮始终没被按
```

**第一个断点（比训练判定更早）**：`brain.decide` 里

```python
if (world.page in (Page.TRAINING, Page.RESEARCH)
        and self.current_goal is not None
        and not self._owns_terminal_page(world)):
    return self._leave_terminal_page_once(world)      # ← BACK
```
而 `_owns_terminal_page` 只认 `current_goal == "TRAIN"`；Goal 层早已把训练拆成三个兵营 Goal
（`SHIELD/LANCER/MARKSMAN_CAMP_TRAINING`）⇒ **兵营 Goal 在结构上就不被允许在训练页上做事**。

**第二个断点**：`ocr.py` 训练分支开头无条件写 `{"status":"IN_PROGRESS","queue_available":False}`，
并且把页面**任意** `HH:MM:SS`（含「训练」按钮自己那行预计耗时）当队列倒计时；
而大脑 `TRAIN_TROOPS` 的门槛读的是 `training.get("trainable")` —— 全项目只有**模板路径**会设它。

实测（6 张归档训练页）：
```
原始时间：04:42:00   y 0.815     立即完成 y 0.863 x 0.267     训练 y 0.862 x 0.736
<裸 HH:MM:SS>        y 0.888  x 0.761   ← 就在「训练」按钮内部，是这批 282 个的预计耗时
```
⇒ 判据改成按帧上真实画的东西：`正在训练N位`（batch_count）或**动作栏以上**的倒计时 ⇒ 忙；
只读到「训练」按钮 ⇒ `AVAILABLE/queue_available=True/trainable=True`；两者都没有 ⇒ UNKNOWN（且不写 queue_available）。

**第三个断点**：兵营 Goal 与"页面上开的兵营"不一致时，原来没有门槛 ⇒ 会去训练**别的兵营**。
现按 Goal 自己的兵营判：不是自己的 ⇒ 切页签（有界），绝不在别人的兵营上按训练。

真机帧复算（射手营页 / 矛兵营页）：
```
open=射手营  MARKSMAN→TRAIN_TROOPS   LANCER→SELECT(自己的营)   SHIELD→SELECT   KEEP_TRAINING_PRODUCTIVE→TRAIN_TROOPS
open=矛兵营  LANCER→TRAIN_TROOPS     MARKSMAN/SHIELD→SELECT
```

## 共同根因（指令 §四 的问题）

**两个故障同一类根因，但不是同一段代码**：都是**页面模型没有把帧的真实状态读出来**，
于是大脑没有可发的动作，路线就离开了刚到达的页面。

- A：识别器**缺失**（记录在案却 0 条模板）；
- B：识别器**写死了结论**（无条件 IN_PROGRESS）并把按钮自己的文字当成队列证据，
  且**归属判定**把这个 Goal 排除在页面之外。

⇒ 规则（已写入长期记忆）：**任何"到达页面"的判断，必须同时问"这一页归这个 Goal 吗"，
以及"页面上的每一条数字/时间到底是谁画的"**。

## 本机环境的两个坑（排查脚本必须知道）

1. **`wmic` 不存在**（这台 Windows 已移除）⇒ 任何"数进程"的脚本都不能依赖它。
2. **不能从 bash/python 里 spawn 那个 Windows 命令行宿主**——沙箱直接拒绝

   结果**每次都被拒**、函数永远返回"查不到"、于是**永远不认为有空档**，
   手动重跑才发现它 9 分 34 秒一步没动。
   ⇒ 判空档要改成**纯文件判据**（面板日志标记 + `runtime_snapshot.json` 的 mtime 新鲜度）。

## 定向真机轮的正确做法（这次学到的）

面板的"空档"有两种：**30 秒**（还能干活时）与 **10 分钟**（行军已满时）。
30 秒那种**根本不是空档**——一轮定向要几分钟。判据必须是：
`最后一条"进入下一轮"含"10 分钟后"` + `该行之后没有"自动运行已启动"` + `runtime 快照 >120 秒没更新` +
`剩余时间 ≥300 秒`。

**更关键**：定向轮必须**先取设备租约**（`DeviceLease.request(...)`，`expires_at` 有 TTL）。
`runtime.py` 里 AUTO 本就"**向租约持有者让位**"（holder 非 GAMEPLAY 且不是自己 ⇒ 在原子边界停下）。
第十二段那次 23 秒重叠的真正原因不是"没有守卫"，而是**我没有发出申请**——守卫在，申请缺席。
取到租约后即使面板提前起轮，AUTO 也会自己让位。

## 重新确认的机制（回答"为什么提前切换/放弃"）

`runtime._yield_to_next_goal`：**选中的 Goal 无法执行时，让位给下一个 Goal，而不是停整轮**
（操作者 Rule A：「不能选中任务后才发现无法执行并停止整轮 AUTO」）。
它清掉 `brain.current_goal` 以免下一轮又推出同一个决定。
⇒ 故障 A/B 里"目标换了、页面被丢下"的直接机制就是它——**在先前的读数是错的**前提下，
它把一个"其实能做完"的任务判成不可执行而让位。修读数即可，**不该动 Rule A**。

另：`goal_library.rank` 是**每步重排**，且这是操作者早前指令（§四/§五）明确要求的
（`runtime.py` 3880 行注释：the board is re-ranked here, on every step）。本轮**没有改评分**。

# 第二十二段 — 面板读数"整体差一整行"的根因（已修，提交 a1e4896）

## 根因：面板读数在**裁剪图**坐标里，却按整帧归一化

同一条帧、同一条命令路径：

```
HybridVision.observe(frame)  -> SHIELD 0.2262  LANCER 0.2832  MARKSMAN 0.3402  RESEARCH 0.4285
read_quick_panel(frame)      -> SHIELD 0.427   LANCER 0.484   MARKSMAN 0.541   RESEARCH 0.6283
```

四行**统一差 0.2008**（= 256 px）。不是滚动（滚动不会等距平移），是：

```python
result=self.ocr.recognize(image_path, QUICK_PANEL_ROI)   # ← recognize 会裁剪！
```

`QUICK_PANEL_ROI` 的 `y_norm=0.20` ⇒ 0.20×1280 = **256 px**，正好是那个偏移。
⇒ **点因此落在目标行的上一行**（大熔炉/队列区），页面不变、只有数字变化
（真机 22:09:30 与 22:12:08：`OPEN_TASK_FROM_QUICK_PANEL_*` FAILURE `TRAINING_PAGE_NOT_PROVEN`，`NUMBER_CHANGED`，仍停 HOME）。
⇒ 也解释了为什么 episode 里的行 y **在任何一帧上都对不上**——那是裁剪空间的坐标。

修：新增 `_tokens_in_frame_space(result, roi, frame_size)`，在调用点把 token 框搬回帧坐标（保留 ROI 那次 OCR，
不增加开销）。修复后同一帧：`observe()` = 0.4262/0.4832/0.5402/0.6285，与直读相差 ≤0.001 👍
**真机复验**：23:43:39 那一步 episode 记的行 y 已是 0.4262/0.4832/0.5402/0.6285（帧坐标），
空闲的矛兵行 `badge=PRESENT`，选行也正确。
