## 10:05 队列时钟 + 三处「静默失效」修复（提交 336437f / 21486ce / 8071b00 / 003dae6 / 5ba83b3）

用户 P0：把 **V2发现不会 → Escalation → 消费 → 提交 → WorkBuddy 开发 → 测试 → 真机验证

### 一、队列有消费者，但没有时钟（336437f）

`observe_run` 只挂在 **AUTO 轮次末尾**；一轮是分钟级（实测空闲时 10 分钟），
AUTO 停下/暂停时则永不执行。⇒ `NEW` 的真实含义是「被看到过一次」。
- `EscalationQueueAdapter.pump()`：无 run 上下文的一次消费；与 `observe_run` 共用 `_drain`，
  两个入口无法漂移；`PUMP_STOP_REASON` 不在墙表也不在天气表（否则每 30 秒凭空造候选）。
- `control_panel.QueuePump`：面板常驻守护线程，**随窗口启动而不是随 AUTO**；
  一次失败的 tick 是状态，下次重建适配器；门控跟随操作者意图（STOPPED 才停，暂停不停）。
- `pump.json` 心跳：`passes/submitted/released/reconciled/errors/last_line/written_at/process`。
  **线程里跑的东西从进程外看不见**——文件让「消费者在跑」成为可核查事实，也顺手是看门狗信号。

### 二、超时任务永久占住唯一并发槽（21486ce）

`max_concurrent_jobs=1` 且**从不取消任何 job** ⇒ 排在其后的记录无限期等待。
实测 job 2934e9cd 在 45 分钟时间盒里已 54.7 分钟。时间盒不是新发明——它是工单里
写给 agent 的那句 "timebox: 45 minutes"，此前只是字符串。`EscalationPolicy.job_timebox_minutes`
成为**唯一数字**（提交文案与执行检查同源，接线校验钉住）。
**只在有人等时才回收**：作业超时 + `pending()` 非空，两条都必需。缺第二条就成了
「按点杀掉正在认真干活的 agent」，与「不要中断有效写操作」冲突。取消不破坏任何东西：
`POST /jobs/{id}/stop` 停的是进程，已提交的代码在工作树里，对账看的是树不是退出码。

  来自 view 里它**自己的列表**（它原本既不在 current 也不在 pending_verify，等于看不见）。

### 二、§8/§9/§19：设备租约 = 单一 UI 拥有者（dbf4b8c）

`winter_agent_v2/device_lease.py`：一把锁，不是生命周期。一个文件、一条记录、一个谓词，
**里面不运行任何东西**。
- `acquire` 拒绝第二个 owner 并**点名**（"GAMEPLAY holds it: GATHER"）。拒绝本身就是功能。
- `request` 只记「请求」，不夺取 —— 这才让「等待安全点」成为真状态而不是推断。
- **`release` 第一版并没有真的归还**：已释放的记录留在文件里且 `released_at` 已设，
  `holder()` 继续返回它 ⇒ §15 会变成纸面归还。被「acquire→release→再 acquire」的测试抓到。
- 过期租约不是持有者（§11 崩溃的验证不得锁住 MuMu），窗口显示 `恢复AUTO`。
- `renew` 保持租约**自己的时长**，不会把 60 秒的租约悄悄升成 15 分钟默认值。
- 审计行带全 §19 要求的字段（trace_id/job_id/capability_id/owner/acquired_at/released_at/
  reason/result），追加写，请求与授权不会对不上先后。
- 运行时守卫放在**一轮循环的第一件事**（截图之前），因为那是唯一「没有输入在飞」的时刻；
  stop reason `device_leased_for_development` 属于**非升级条件**（§2 A：设备归验证所有是
  条件不是能力缺口，升级它等于为「有个开发任务在跑」花掉一个开发任务）。
- GUI 增加「设备所有权（Single UI Owner）」行，四个词从租约文件读，不硬编码。
