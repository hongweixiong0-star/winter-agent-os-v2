## 升级队列：AUTO 发现 / 队列限流 / WorkBuddy 异步修（操作者方案）

**架构**：`AUTO → 建单 → Queue（去重/并发/预算/冷却）→ Bridge → WorkBuddy`。
**AUTO 永不同步等 WorkBuddy**：hook 在 `run()` 返回后执行（动作已结束），只做
"对账已结束的 job + 交出 ≤ 并发上限的决定" 然后返回。

**新增（三处最小改动，无第二 Scheduler/Manager/Registry/Orchestrator）**：
- `winter_agent_v2/escalation_queue.py`：状态机 `NEW/QUEUED/SUBMITTED/WORKING/DONE/FAILED/BLOCKED/COOLDOWN`；
  去重键 `capability|failure_type|skill`；`max_concurrent_jobs=1`；修复预算 + 冷却；
  模型阶梯；对账；`EscalationQueueAdapter.observe_run()`（AUTO hook，**永不抛异常**）。

## 首次真机升级闭环 + 两处被实测推翻的结论（务必记住）

### 闭环（无人值守 AUTO 自动完成）

`AUTO 发现 verified_beast_target_not_visible → 分级 UNKNOWN_UI → 解析出 capability
SPEND_STAMINA_ON_BEAST → 建单 → （面板无凭据）QUEUED 继续跑`。
随后用带凭据的真实 AUTO 运行把它派发出去：`[escalation] submitted 1`，job `8fd1dfbf`，
`deepseek-v4.1-flash`（最便宜档，符合默认）。第二轮同一失败自动报
`DEDUP_SKIP ... already has an active escalation (state=WORKING)` ⇒ **去重在真机上成立**。
`live_exit=0`（先前那次 `exit=1` 是 shell 复合命令取值假象，已用 `SystemExit(0/2)` 校准）。

### ❌ 结论一被推翻：`permissionMode: dontAsk` **根本不执行**

四个真机 job、同一 prompt：`dontAsk` **DENIED**、`acceptEdits` **DENIED**、
`auto` **DENIED**、**`bypassPermissions` 真的执行**（`GIT=19964ec PY=42`）。
默认值已改 `bypassPermissions`。

**我先前为什么会搞错（教训）**：早先探针用 `dontAsk` 问 `git rev-parse HEAD`，
拿到了正确的 40 位哈希，我就判定"`dontAsk` 能跑 shell"。它什么都没证明——
`.git/refs/heads/main` 里就是同一个哈希，而 Read 是允许的；后来的 agent 把机制说清了：
`Bash` 直接拒绝，shell 回退被限制在**只读白名单**（`git rev-parse` 通过，
`python`/`pytest`/`git commit` 不通过）。⇒ **我验证了输出，没有验证机制。**
这和 `TOOLING_INTERPRETER_DRIFT` 是同一类错，只是低一层。

### ❌ 结论二：对账**不能按时间窗把改代码归给 agent**

第一次对账把 `TEST_PASS` 记给了 agent（"the tree changed while the agent ran"），
而 agent 自述 "No code was changed" —— **那个 diff 是我自己在派发后编辑
`escalation_queue.py` 造成的**。已修：tree diff 是事实，归因需要 agent 自述**佐证**；
解释里写明"may not be the agent's / corroborating"。并加了 `--correct` 入口把历史那行

同时清掉由此**误产生**的 `RUNTIME_RELOAD_REQUIRED` 标记。
教训：**"窗口内发生了"不等于"它做的"**，这个项目本来就是多处同时编辑
（`run_live.py` 的 `VERIFIER_MAPPING_CORRUPT` 就是为这个加的）。

## CAP-A01 关闭：#25 的根因不是那两个候选，是**判别器装进了会变的等级**

工单禁止在分离两个候选前动手，于是先量。**两个候选都被推翻**：

2. **对话框没被顶掉**：失败步的 **before 帧本身就是「英雄之旅 等级2」**弹窗，
   模板层却判成 `INTEL_BEAST_MISSION / BEAST / level 10` ⇒ **点击是对的，是判型错了**。

### 关键教训：**文字不要用 phash，用 OCR**

"把等级从裁剪里去掉"这个直觉修法**量了，不成立**：候选裁剪 size=16 哈希在
等级2 帧上 **d=0**，在**等级10 帧上 d=131**（兽任务 126 / 悬赏 115）。
标题是**居中**字符串 → 位数一变不变量横移 7–14px，而该尺寸下 dhash 一格只有约 2.6px。
⇒ **图标/页面/按钮用模板，文字用 OCR**。修法落在 `ocr.py::_read_intel_dialog_title`：
按标题文字判型（`INTEL_DIALOG_TITLES` 只收真见过的名字），**认不出就什么都不改**；
顺带把 `vision.py` 里**硬编码的 `mission_level=10`** 换成真实读数（实测 等级2 / 等级20）；
类型不符的 `mission_id` **丢弃**（verifier 比它，留着等于让错的 id 通过检查）。
6 帧 replay 全对；`tests/test_intel_dialog_typing.py` **19 项**。
