# 2026-10-05 — 游荡商人 Skill（用户策略：商店购买规则）

## 背景

用户下达了一条业务策略，优先级高于任何外部资料，按 CONFIRMED 知识处理：
- **游荡商人**：资源换资源 → 买；钻石换统帅经验 → 买；其他钻石商品 → 跳过；只用免费刷新（3/天）。
- **神秘商店**：名称含「英雄组件自选箱」且折扣 50% → 买；有艾格妮丝后免费刷新最多 5 次。
- **联盟商店**：名称含「统帅经验」→ 买。
- 规则没覆盖的情况 → 停下来问用户。

本轮任务：先做游荡商人，为三个商店各写一个 Skill（`VISIT_WANDERING_MERCHANT` /
`VISIT_MYSTERY_SHOP` / `VISIT_ALLIANCE_SHOP`）。**UI 路径必须真机观察，不允许写死坐标。**

## 交付物

- `winter_agent_v2/shop_visit.py` — 生产模块（读取器 + 策略 + 访问者 + 购买校验）
- `tools/run_shop_wandering.py` — 实机驱动（`--buy` / `--refresh`，日志落盘）
- `tests/test_shop_visit_reading.py` — 50 条 hermetic 测试，全绿
- `knowledge/skills/VISIT_WANDERING_MERCHANT.json` — 沉淀的 Skill

## 真机测出来的 UI 路径

- 入口：HOME 底栏第 4 项「商店」（y≈1258）
- 页签条：游荡商人 / 神秘商店 / 竞技商店 / 统帅市，y≥0.93H
- 卡片：3 列 × 2 行；每张卡 = 图标 / 剩余：N / 价格胶囊（货币是个图标）。**卡片上不印商品名。**
- **名字与价格都只能从「确定购买」浮层读**：点卡片本体 → 浮层里同时有商品名和带货币图标的当前价。
- 点击分层（`tools/shop_tap_map.py` 实测，同一张卡）：
  锚点 +0/+20/+40/+60/+80 **全部**打开购买浮层；−45/−65/−85 **全部**打开只读 tooltip。
- tooltip 用**点商人立绘 (360,250)** 关闭（实测），**因此卡片循环里完全不再用返回键**。
- 价格按钮＝橙色大按钮，实测 bbox [222,795,276,71]（16,066–16,373 px）。

## 本轮找到并修掉的真问题（全部有实测支撑）

0. **购买是两次点击，不是一次。** 点「确定购买」的橙色价格按钮**不买东西**，它弹出客户端自己的
   追问「购买确认 / 您是否要花费16钻石?」，再点那个橙色按钮才成交。第一次实现里，第一次点击后
   「确定购买」确实消失了，于是判定成功 —— **而钻石一个都没少**。是钱包校验把它抓出来的。
   现在第二步只在「客户端自己写出的金额 == 我们据以决策的金额」时才点；
   「今日不再提示」**故意不勾**（那会拆掉客户端自己的确认）。
   另外：一次被中断的流程会把「购买确认」留在屏幕上，`enter()` 现在会用自己的 ✕ 关掉它，
   **绝不碰它的按钮**。
1. **`merge_fragments` 会把 `N万` 价格整条删掉。** 它用 `[\d,，]+` 选出「要拼接的」token，然后又
   用同一个选择重建返回值 → 不是纯数字串的 token 全部消失。`read_cards` 把这个返回值当作
   全部数字来源，于是**被删掉的恰好是「资源换资源」那几张卡——正是策略要买的**。表现是
   「6 张卡只读到 4 张」，而没读到的两张是唯一该买的。已修，并在真实帧上钉住。
2. **价格按钮靠排除法选不出来。** 整帧 OCR 把数量滑杆读成 `1`（1 字符被过滤），grid 那一遍
   把同一批像素读成 `00`（2 字符保留），在另一行撞上真价格 → `PRICE_BUTTON_AMBIGUOUS`，
   6 张里错 2 张。改成**用橙色定位按钮本体，取按钮内的数字**，该类失败整体消失。
3. **tooltip 的「拥有数量」行被当成商品名。** OCR 在小字号下把 `拥有数量` 读成 `有数量`，
   停用词没拦住，而「最长中文 token」的 tie-break 选中了 `有数量：286,010,314`。
   （顺便加了 `label：数字` 一律不是商品名的规则——商品名里确实有数字，`5,000点英雄经验`。）
4. **钻石价在橙色按钮上被读成资源**（蓝色占比只有 0.21）→ 决策被反转。改成**绝对蓝色像素数**
   （阈值 150；实测 0 vs 570–1048）。
5. **卡片会因为「列表价没读到」被整张丢掉。** 列表价只用来打日志，判定用的是浮层里的实时价 ——
   所以丢卡等于丢掉一张本来可以完整评估的卡（实测：02:19 那轮报「读到 5 张」，漏的正是 r1c0）。
   现在保留，价格标记为未读到。
6. **免费刷新 3/天 的计数器从未生效。** `run_shop_wandering` 只在
   `report.get("refreshed")` 为真时累加，而 `visit` 从来不设这个键 → 用户策略里的上限形同虚设。
7. **证据被覆盖**：`see()` 的文件名不含轮次，第 2 轮的 `40_card_r0c2_buy0_0` 覆盖了第 1 轮的，
   回头读证据就重建出了错误的盘面。已按轮次加前缀。
8. **日志丢失**：一次长跑被 `tail` 管道 + 中途终止，帧留下了、判断理由全没了。现在日志写进
   证据目录 `run.log`。

## 实测结论

- **商店会自己换货**：同一个槽位在 3 分钟内先后是「建造加速 @ 铁33,000」「煤 @ 铁10,000」
  「木材 @ 💎100」，而商人自己的倒计时还剩 22 分钟。**所以决策必须用浮层里的实时价格，
  不能用卡列表里读到的价格。** 多轮实测都印证了这一点（列表写 7,500资源，浮层是 600💎）。
- 那张蓝色 Exp 瓶子是「5,000点英雄经验」，**不是统帅经验**。按图标猜就会花钻石买错东西。
  真正该买的是那个刻着 `10` 的金色六边形：**「10点统帅经验」**。
- 点击打开浮层**不稳定**：最坏的一张卡连着 9 次点击都没打开（同一偏移上另外几张卡是好的），
  所以阶梯要重试、并且第二轮要**重新定位锚点**。
- 打开浮层最稳的区带：锚点 +0 … +80 全部成功；−45/−65/−85 会打开只读 tooltip。
- 只读 tooltip 用**点商人立绘 (360,250)** 关闭 —— 于是卡片循环里**完全不用返回键**（backs=0）。

# 第二轮（04:00–04:45）：点击分层重新测、两个真 bug、一次全绿跑批

## 1. 旧的「点击分层」结论是错的，已用新仪器重测

上一轮记录的两条互相矛盾（`shop_tap_probe.py` 说图标开 tooltip、价格胶囊什么都不做；
`shop_tap_map.py` 说 +0..+80 全开购买浮层）。**两份各只测了一张卡，所以都没错也都不全。**

新写了 `tools/shop_zone_map.py`：在一张卡上从锚点 −110 走到 +110，逐点记录「打开了什么」，
**资源卡和钻石卡各测一张**。判定用 OpenCV（橙色按钮 / 大块变化），所以只有真命中才付 OCR 的代价。
另外它有一条**硬安全闸**：每次点击前先看当前帧有没有橙色价格按钮，有就先关掉 —— 这样点击
**永远不可能落到价格按钮上**。

两张卡的结果**完全一致，而且边界很利**：

```
锚点 −110 .. −30   → 只读 tooltip（拥有数量）
锚点 −10           → 一张卡什么都不发生，另一张开购买浮层（边界）
锚点 +0  .. +80    → 确定购买，两张卡的每一个偏移都成功
锚点 +100 及以外   → 什么都不发生（卡已经结束）
```

所以上一轮那条「(360,250) 点商人立绘关 tooltip、卡片循环里完全不用返回键」是**基于错的分层**：
真正进入 tooltip 区的是**锚点上方**（−110..−30），而购买路径从来不去那里。
实测全绿那轮 `backs=1`（只为进场），卡片循环 0 次返回键。

## 2. 真 bug：金色六边形图标被当成了「价格按钮」

`orange_price_button` 原来只卡「面积 ≥ 3000 px」。而本轮的盘面里 r1c0 是 **19💎 的统帅经验**，
它的图标是**金色六边形**，实测 `bbox=[101,788,75,62]`、`3116 px` —— **刚好越过 3000 的门槛**。

后果不是"没认出按钮"，而是**反向的**：探测脚本问"现在有没有浮层？"得到"有"，
于是它去关一个**根本不存在的对话框**，按返回键**直接退出了商店**，整轮探测报废。

按钮和图标靠**形状**分开，不是靠面积：

| | bbox | px | 宽/高 |
|---|---|---|---|
| 真按钮（5 帧实测） | 276×71 | 15,802–16,637 | **3.89** |
| 金色六边形图标 | 75×62 | 3,116 | **1.21** |

改成 `px ≥ 8000 且 宽 ≥ 2×高`。钉了三条测试：真帧（该盘面必须返回 None）、
合成方块（100×100、10000 px、形状不对 → 必须 None）、合成真按钮（必须仍是 `[222,795,276,71]`）。
**注意：它多发的正是策略要买的那个道具。**

## 3. 真 bug：第二次确认按钮靠「找数字」找不到

04:13 那轮：r1c0 = 10点统帅经验 19💎 → BUY → 客户端自己的追问**读对了**（「您是否要花费19钻石?」，
金额匹配）→ 然后报 `CONFIRM_BUTTON_NOT_FOUND`，**一钻石没花**。

原因：`confirm` 找第二次按钮用的是「在橙色框里找一个数字 token」—— 而**这正是
`read_button_price` 当初被写出来要替掉的做法**（橙底白字的数字会读错）。改掉了：
`confirm` 现在**用按钮自己的橙色定位**（该对话框上只有一个橙色按钮，实测
`bbox=[222,755,276,71]`，中心 `[360,791]`）。按钮上的数字只作**佐证**：
**读出来和金额不一致 → 停手**；读不出来 → 不拦（客户端自己的句子已经核过金额了）。

## 4. 「点了没反应」不是几何问题 —— 已用计数证明

同一个坐标 `(361,897)`：03:29 连点 12 次毫无反应，03:53 的探测里 +0..+80 全部一次成功。
两张卡在两个不同的轮次各失败过一次，而它们的邻居卡用同样的偏移都正常。

新增的 `taps_refused` 计数（`_tap_xy` 原来**把 `ad.click` 的返回值丢掉了**）给出了答案：
**全绿那轮 `taps_refused=0`** —— 每一次点击都发出去了，**是客户端自己忽略了它**。
所以这是客户端的瞬时状态，不是坐标或宿主的问题。对策两条：
- 阶梯**覆盖**整个实测区带（+0/+15/+30/+45/+60/+80），而不是抽 3 个点；
- 覆盖面变大之所以负担得起，是因为**浮层判定改成纯 OpenCV**（原始截图 + 橙色按钮，
  不 OCR）：一次落空从 ~20 秒降到 ~2 秒。

同时把**每次点击的绝对坐标写进 run.log** —— 只看证据帧永远回答不了"它到底点在哪"。

## 8. 缺口变化

- ✅ 打开浮层的可靠性缺口：阶梯覆盖全区带 + 纯 OpenCV 判定之后，全绿那轮 0 次失败。

- ❌ **「资源换资源 → 买」仍然没有一次真机成交证据。** 全绿那轮盘面里 6 张全是钻石商品。
  04:27 之后的追捕跑批仍在继续找。判定链已经在真机上出现过（03:53 的
  `木材 (安全) @ 10万` 被读成资源价）。

- ❌ 神秘商店 / 联盟商店还没开始。
