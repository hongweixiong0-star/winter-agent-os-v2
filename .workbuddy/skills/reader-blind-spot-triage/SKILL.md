# 读取器盲区排查（episode 记失败，但帧上明明画着）

## 为什么有这条技能

2026-09-23 一夜里同一个模式出现四次，每次都要从零绕一圈才知道是读取器的问题而不是客户端的问题
（`16:42:30` / `18:54:27` / `18:43:51` 三次 FAILURE、以及 `17:54:28`）：

- `PANEL_ROW_TASK_BAR_NOT_PROVEN` / `INFANTRY_CAMP_HIGHLIGHT_NOT_PROVEN` 这些失败名**听起来像客户端没做到**，
  但帧上是做到了的；
- 而一旦误判成"客户端没做到"，就会去做**路由改动**——那是改错地方。

**规律**：这个项目里"读取器比客户端更常出错"。任何"到达判据不满足"的失败，先怀疑读取器。

## 流程（按顺序，不要跳）

1. **先看图**。把该 episode 的 `after_screenshot` 直接打开（必要时裁切放大），
   确认客户端**到底**画了什么。不要用"时间接近的另一条记录"代替看图。
   （帧的归属用 `tools/frame_owner.py`，见 `frame-evidence-joins` 技能。）
2. **用当前读取器重读那一帧**：
   ```python
   from winter_agent_v2.ocr import HybridVision, OCRService, RapidOCRBackend, ResilientOCRBackend
   vis.observe(Path(frame))   # 打印 page / training / quick_panel
   ```
   - 若现在读得出 ⇒ 缺陷**已修**，那条 episode 是历史，不要据此改代码；
   - 若现在仍读不出 ⇒ 活缺陷，继续。
3. **找出是哪一层拒的**，逐层问，**不要跳层**：
   - **门模板**：这类读取都有一个便宜的模板门（如 `CAMP_ACTION_BAR_GATE`）。
     直接量原始相关分：`cv2.matchTemplate(frame, gate_img, TM_CCOEFF_NORMED)` 取最大值，
     与阈值比较（本项目 `distance = round((1-score)*64)`，默认 `max_distance = 6`）。
     **0.65 左右的常数几乎总是"模板不在这一帧上"，不是"匹配得差"。**
   - **OCR 词表 + y 带**：把 OCR token 逐条按 band 打印出来（文本、中心归一坐标、置信度、
     是否落在 band 内、是否在词表内）。**词读到了但被 band 拒掉**是最隐蔽的一种。
   - **名称/前置校验**：如 `camp` 必须非空（词表 → 营地名）。
4. **问"这些常量是在哪种布局/渲染上量的"**——这是最常见的根因。
   用一个控件在**每种已知渲染**上的实际坐标/图标去打分，做交叉表：
   ```
   crop 自 A 布局的图标 -> A 1.000 | B 0.969 | C 0.651
   crop 自 B 布局的图标 -> A 0.969 | B 1.000 | C 0.585
   ```
   跨布局 ≥0.95 的控件才能当门；只会命中一种的，必须**每种布局各一条记录**
   （`find()` 对同一 semantic 有多条记录时任一条命中即算命中）。
5. **改最小的一处，并让工具自己证明**：本项目每个注册工具都有 `--check`
   （must-match / must-not-match 两组）。先跑它，要求 **miss = 0 且假阳性 = 0**，再提交。
   顺手检查**`--check` 的清单本身对不对**：拿"帧自己记录的状态"分类，
   而不是按技能名或日期——本项目已出现"同一技能早上结束在 A 渲染、晚上结束在 B 渲染"，
   于是清单把判对的帧报成 miss。
6. **可读词表绝不顺带扩**：词表就是"词 → 可点的点"。花钱控件（`立即完成`、`加速`、带钻石数的）
   即使与可读词同排同带，也**不得**入表，要在代码里写明原因。

## 第五步之后：若是"点了没反应"，去核**落点**本身

失败名里带 `..._NOT_PROVEN` 且帧上控件明明存在时，除了上面前四步，还要查**这一下到底点在哪儿**：

1. 从 `learning/executor_backend.jsonl` 取那一步的 `tap_point`（账本比 episode 记得全）；
2. 在**同一帧**上量出该控件的真实范围（逐像素剖一行最快：把 x 从控件左侧到面板外的 RGB 打出来，
   本体颜色与污染物一眼可分）；
3. 把账本里的 `tap_point` 叠到图上（画十字）看是否落在控件内。

实测（2026-09-23，`#98`）：快捷面板行箭头的 `arrow_norm.x` 报 0.56–0.67，而按钮本体只占 0.533–0.59
（青色 `(76,198,244)`），因为扫描带右沿 0.80 伸出面板外 155px，而 `min..max` 加"取最宽一行"**优先**选中
被城市蓝色污染的那一行。账本对照证实：用 `arrow_norm` 的三次 tap 全失败、落在按钮内的一次成功。

**改这类代码前必须**：先有一个**不依赖原判据**的定位器（本项目：按钮内的白色雪佛龙 / 面板卡片几何），
否则任何阈值都只是把猜的位置挪一挪。取值规则决定 tap 坐标——**没有独立依据就不改**。

**修下来的形态**（#98 的落法，可复用）：控件内部那个**不透明的图形**（白箭头、徽标旁的字形）通常
比控件的"颜色区域"可靠得多——
- 它由客户端画在控件里，不与背景混合；
- 用"三通道 ≥245"这类阈值就能把被面板压暗的城市（实测最亮 200-227）挡在外面；
- 再把颜色扫描**限制在这个图形周围 ±N 像素**（N 由实测：图形 396-416 在按钮 384-425 内 ⇒ N=12），
  于是原判据仍在使用，但**再也不可能伸到控件外**；
- 图形**不存在**时不要回退到猜测点：那正是"客户端没画这个控件"的证据（如 已完成 行画的是绿勾），
  返回"无点"让调用方拒绝，比给一个坏坐标安全。

## 第六步：读数与画面不符时，问"这个 token 是不是**这个界面**画的"

#99（2026-09-23）是这一类：面板行的 `label` 被读成 `梦境寻忆`，而面板上那行明明是 `科技研究/空闲中`。

- 本项目大量界面是**覆盖层**（快捷面板画在城市之上、弹窗画在页面之上），被覆盖的那一层**仍在画自己的文字**，
  且常常与覆盖层**同高**。任何"按 y 取一段 token"的装配都会把两层的文字混成一行。
- 所以装配一段读数时，每一个 token 都要过一遍**归属判据**：它是否落在该界面自己的列/带内
  （本项目用既有常量 `QUICK_PANEL_COLUMN_MAX_X_NORM` 判面板左缘；实测带 0.10-0.34，而城市活动栏在 0.77）。
- 症状特征：**行的 `label`、`status`、`source_word` 里至少一个与画面不符**，而 `y_norm` 又落在正确的高度
  ——那说明 y 锚点对、文字取自别处。
- 验证方式：把该帧**全部** OCR token 连同它们的 y 打出来，找那颗文字的**真实 x**；
  若它在覆盖层之外，"这行是它"就不成立（本帧：`梦境寻忆` 只出现在 x 0.769）。
- 合成对照也便宜：在真机帧上注入一颗诱饵 token（正确高度、越界的 x），它**不得**成为那一行。

## 反面清单（本项目已付过代价）

- ❌ 用"有某个视觉特征"当**到达/身份判据**：金环（#92）会自己闪、白气泡（#95 补充）是通用提示框
  且内容随对象变。**特征存在 ≠ 对象是它**；判据要落在**对象自己的文字或图标**上。
- ❌ 只在一种渲染上量一个常量（band / 模板 / 阈值）就当通用。
- ❌ 从别的页面的同名控件照搬固定坐标；坐标必须来自当帧（把手、行按钮、环心、气泡都是按帧定位的）。
- ❌ 把"读了/生成了 Goal"当作"执行成功"。

## 交付时要写清的三件事

1. 缺陷是**读取器**还是**客户端**（附"当前读取器重读"的结果）；
2. 常量原来量在哪种渲染上、漏了哪种（附逐词/逐像素表）；
3. 修完的 `--check` 结果（miss 数、假阳性数），以及**仍未在真机观察到的部分**。

## 5. "读不到"有两种：词不在帧上，和词被并进了更长的 token（2026-09-23）

**案例**：`加成总览` 的「实力详情」按钮，14 帧 `SEMANTIC_TARGET_NOT_VERIFIED`。字读者报"帧上没有这个词"，
但我把帧裁开一看，**按钮清清楚楚画在那里**。原始 OCR 的 25 个 token 里就有它 —— 读作
**`三实力详情`**（conf 0.901，中心与按钮实际中心差 3px）：客户端在那颗蓝色药丸上同时画了 ≡ 图标和名字，
**OCR 把两者合成一个 token**，而精确匹配要求整个 token 等于声明词，于是什么也找不到。

**判据（照这个顺序查，别猜）**：
1. 先看**原始 OCR token 全表**（不是只看读取器的返回值）——词是否以"被包含"的形式存在？
2. 若在：这是"读取器口径"问题，不是"控件不在"问题。**不要**因此把默认改成模糊匹配：
   那个默认是实测来的（`城镇` 曾命中 `我的城镇` —— 另一个控件的标签）。
3. 正确形状是**按记录声明**（本项目：词典 `ocr_merged`，全词典只有被实测到会合并的那一条为真），
   把放宽的范围钉在"我们量过会合并"的那一条上，并写一条测试钉住"没声明的记录仍不接受包含匹配"。

**负向对照怎么做**：同一个词在**其他屏**上必须 0 命中（本项目：18 屏含 8 种其他弹窗、HOME/MAP/TRAINING/UNKNOWN
全部 0），并给出**覆盖率**（本项目 231/245 = 94.3%，读不到的 14 帧仍会诚实失败 —— 这是路线的边界，不是缺陷）。

**顺带一条通用做法**：要问"还有哪些控件有同类问题"，**按失败记录里被点名的控件分组**
（本项目：`TAP_SEMANTIC` + `SEMANTIC_TARGET_NOT_VERIFIED` 按 `action.target` 计数，418 条），
比逐个猜快得多，而且修复前后可以直接对比同一张表（本项目修复后 `BTN_CLOSE` 在该弹窗上的 23 次归零）。
