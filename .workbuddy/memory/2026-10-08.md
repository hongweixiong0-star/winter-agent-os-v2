   会回退反量化 → 无收益甚至更慢。**在这张卡上 NVFP4 是负收益选项**；正确方向是 FP8/Q5_K_M。

## 补 1：MuMu 不是"不如 MAA"，是分层

1. **升级只有一个消费方**：`escalation_queue.py` 里唯一的派发是 `self.bridge.submit(...)`（退役通道），
   唯一开关是 `_automatic_submission_block_reason()` 读 `config/v2.json` 的 `workbuddy_channel.*`。

2. **`capability_gate.py` 不是那堵墙**：它有出口 ——
   `BLOCKED_PROBE_MINUTES = 180`、`NO_PROGRESS_PROBE_MINUTES = 30`，
   docstring 写着 *"Re-entry is never '30 seconds later' … so a broken path is neither retried in a

   ⇒ 所有线索收敛到一件事：**让 P0-E 发生一次。**
3. **`ui_collection.build_element_table` 只有两个来源、且都以印刷文字为键**
   （`composite_controls` = 印刷标签+上方控件；`grounding_regions` = 每个 OCR 文本）。
   ⇒ **无印刷文字的图标控件两个来源都产不出来**（读代码确认，不只是观察）。
4. **但 `parse_plan` 对点名 id 的 EXECUTE 要求 `target_text` 非空**
   （`PLAN_TARGET_HAS_NO_PRINTED_TEXT`）—— **合同本身假定"元素 = 有印刷文字的控件"。**

### 所以现在把无字图标塞进元素表并标 `executable: True` 是错的

模型会点它，然后被解析器以"没有印刷文字"拒掉 ——
**这正是今天刚修掉的"提供给你、然后又拒绝你"缺陷换位置再犯一次。**

### 两条自洽的路（都要真机校准，不能顺手改）

- **(a) 只告知、不进表**：把该页已注册的无字控件（`entry_badges` 有 7 条，带 `page` 与锚点；
  `BTN_OPEN_MAIL` 在其中，且语义层实测可解析 score 14）作为 `relevant_knowledge` 告诉模型，

  （MAIL 页它就是这么给出 `一键已读&领取` 并被接地到距生产语义中心 9 px 的）。
  优点：不动元素语义、不动合同、不动解析器。
- **(b) 进表且给 `text`**：用注册表自己的名字（`entry_badges` 行有 `label: "邮件"`）当 `text`。

**推荐 (a)**：改动面最小、与刚打开的 proposal 通道同向、不触碰"坐标不是知识"和"只提供不拒绝"两条不变量。

## 补 29：投机解码有没有用 —— 有上限，且实测无增益（`bd5bf0ef`）

### 先算上限，再动手（这一步决定了值不值得试）

|---|---|---|
| 基线 | 33.1 s | — |

- **不需要草稿模型的 `ngram-simple`**：生成 **22.9 tok/s** vs 基线 22.4–24.3 ⇒ **无增益**；

1. **`draft-mtp` 这条最自然的路被"加载器"堵住**：模型**自带 MTP 头**

## 补 30：核显／独显／CPU 各被谁用了 —— 采样回答，不靠猜（`816645f8`）

在一次真实调用期间（5047 token 提示、37 s）每 0.5 s 采样一次：

| 算力 | 用上了吗 | 实测 |
|---|---|---|
| **CPU**（Ryzen 7 7840H） | **是** | `-cmoe` 专家张量全在内存；日志 `n_threads = 8`；调用期间中位 **35%**、峰值 87%（16 逻辑核） |
| **独显**（RTX 4060, 8 GB） | **是，且三方共用** | llama.cpp CUDA0；GPU 利用率 11%/**56%**/99%（min/中位/max）；显存 5276–5398 / 8188 |
| **核显**（Radeon 780M） | **没有，而且两边都用不上** | 见下 |

### 核显不是"忘了用"，是两条独立的路都堵着

1. **llama.cpp 看不见它**：这个构建是纯 CUDA，`llama-server.exe --list-devices` **只打一行**
   `CUDA0: NVIDIA GeForce RTX 4060 Laptop GPU`。（`--version` 也没暴露 Vulkan 后端。）
2. **MuMu 也看不见它**：实例日志自己写着
   `"Adapters":["NVIDIA GeForce RTX 4060 Laptop GPU"]`、
   `"Renderer":"MuMu GL (NVIDIA GeForce RTX 4060 Laptop GPU Direct3D11 vs_5_0 ps_5_0)"`
   ⇒ **枚举到的适配器只有一个**，渲染就在上面。
3. **而且"改系统首选项"这条已经用掉了**：`HKCU\...\DirectX\UserGpuPreferences` 里
   **MuMu 每一个可执行文件都已是 `GpuPreference=1`（节能＝优先核显）**，它照样跑独显
   ⇒ **这个旋钮不是没拧，是拧了没用。**

### 更有价值的一层读法：两边都没打满

GPU 中位 **56%**（有 44% 时间在空等）、CPU 中位 **35%**（多数核闲着）。
⇒ **成本在"CPU 专家段 ↔ GPU 段"的交接，不在任何一侧的算力。**
这条把另外两个实测串起来了：**把专家层挪到 GPU 无收益**（容量不是瓶颈），
**批量档案的 2.2× 本身就是"交接收益"**——更大的 ubatch ＝更少的块 ＝更少的 CPU↔GPU 往返。
⇒ 也解释了为什么"富余显存"不是它看起来的那个杠杆。

**结论**：不要为核显折腾。真要动，只能换一个带 Vulkan 后端的 llama.cpp 构建，
而 780M 走系统内存（比显存慢得多），且当前瓶颈是交接而非容量 ⇒ 预期收益低。

流程：`816645f8` → `CLEAN_OUTSIDE_DATA` → `MAINLINE_OK`（仅文档，无行为变更）。
