## 一个字段的缺省，把六个屏幕变成永远答不出的黑洞（`864ea4b6`）

### 线索：基准里剩下 3 次被拒，其中一个的措辞自相矛盾

`tools/benchmark_gui_unknown.py` 7 个用例，修完登记表后仍红 3 条：

```
case 4  PLAN_TARGET_IS_NOT_A_CONTROL: E7  is TEXT_LABEL
case 5  PLAN_TARGET_IS_NOT_A_CONTROL: E1  is COMPOSITE_CONTROL     ← 「是个控件」却被拒
case 6  PLAN_TARGET_IS_NOT_A_CONTROL: E14 is TEXT_LABEL
```

**case 5 那句话自己打自己**：`COMPOSITE_CONTROL` 按 §2 就是可点击的那一类。

### 真因：同一个身份的两个字段，**缺省方向相反**

```python
kind = str(box.get("element_kind") or "")
if kind:
    entry["kind"] = kind
    entry["executable"] = bool(box.get("element_executable"))
```

- `element_kind` **缺** ⇒ 元素不带 `kind`、不带 `executable`；而守卫判的是
  `element.get("executable") is False` ⇒ **"没类型"被当成"可以用"**。
- `element_executable` **缺** ⇒ `bool(None)` = False ⇒ **同一条记录的另一半缺省把一切都拒掉**。
**一个身份、两个缺省、方向相反。**

**实测**（`learning/unknown_requests/sweepcase_*.json`）：

```
case 01  5 框  带 element_executable 的：0   kinds {TEXT_LABEL: 5}
case 02  5 框  0                             {TEXT_LABEL: 5}
case 03  5 框  0                             {TEXT_LABEL: 5}
case 04  7 框  0                             {TEXT_LABEL: 7}
case 05  40 框 0                             {COMPOSITE_CONTROL: 1, TEXT_LABEL: 39}
case 06  32 框 0                             {COMPOSITE_CONTROL: 1, TEXT_LABEL: 31}
```

六条记录**每一个框都有 kind、没有一条有 flag** ⇒ 那些屏的**每个元素**递给模型时都是"不是控件"，
于是**任何提案都只能被拒**。其中两条屏**真的持有已登记复合控件**，模型**点对了名字**：


**被拒时的消息还把它的 kind 原样念了出来。**

这正是守卫自己注释里说"绝不允许存在"的永久 UNKNOWN 黑洞——**它不是被某个决定造成的，是被一个缺省造成的。**

## 反套话规则的前提可以被**静默**丢掉：记录"这次到底用了哪种回复约束"（`003b45e` / `d1240c1`）

### 线索：那份 143 字 / 三句话的 reason 与 `maxLength: 120` 矛盾

上一节留下一个没解释的事：历史上唯一那份 `EXECUTE` 被 `PLAN_REASON_TOO_LONG` 拒了。
我去看它到底写了什么：

```
"Goal is KEEP_BUILDING_PRODUCTIVE. The screen shows the Wall at level 8 with an
 'Upgrade' button (E6). Clicking this is a ..."        ← 三句话、远超 120 字
```

而 `ui_planner` 的 schema 里写着 `"reason": {"maxLength": 120}`。
**两者不可能同时为真**，除非那次调用**根本没有 schema 在约束**。

### 查证：llama.cpp 到底支不支持 `maxLength`（外部一手资料）

`llama.cpp/grammars/README.md`（官方仓库）：

> Supported schema features include ... **minLength / maxLength** ...
> 例子：`maxLength: 100` → `item-name ::= "\"" char{1,100} "\""`

**支持，而且在 grammar 里真的限制了生成。** ⇒ 那条 reason 只可能是在 **schema 不在场**时生成的。
而"schema 会不在场"的路径就在代码里：`_post` 抛 `_RejectedKey` ⇒ 恢复逻辑把
`json_schema` 换成 `json_object`，再不行就把 `response_format` 整个删掉。
**而台账里没有任何字段说这次到底用了哪一种。**

### 修法（纯遥测，不改行为）

`GUIModelCall` 增加 `reply_constraint ∈ {schema, json_object, none}`：按**实际发出的 payload** 记，
降级时同步更新，**失败的调用也记**（一次传输失败不该让我们忘记它当时在要什么）。

### 证据

- 6 条新测试；删掉写这个字段的那一行 ⇒ **6 条全红**；A/B 六个相关套件 **7 failed → 1 failed**，
  差异正好这 6 条。
- **没有**放宽 `reason_violation`：那条规则的理由（"截断的解释仍然花了生成它的 token"）成立，
  要修的是"它的前提被静默丢掉"，不是规则本身。

## 为 A 写的补救，被执行在 B 的抱怨上：静默丢掉 grammar 的第二条路（`ca3f2b8`）

### 代码原样

```python
except _RejectedKey as exc:
    if payload.get("response_format", {}).get("type") == "json_schema":   # ← 不看 exc.key
        payload["response_format"] = {"type": "json_object"}
        constraint = "json_object"
    ...
    if exc.key == "temperature":        # ← 只有这一句是按键判的
        payload.pop("temperature", None)
```

而 `_post` 只会为**两个键**抛这个异常（只有报错文本里点名了才抛）：

```python
if exc.code in (400, 422) and "response_format" in lowered: raise _RejectedKey("response_format")
if exc.code in (400, 422) and "temperature" in lowered:     raise _RejectedKey("temperature")
```

⇒ **服务器抱怨 `temperature` 的那一次，会把 grammar 一起丢掉**：没有报错、请求依然合法、
回复照常返回，只是**约束没了**。而上一节刚量过：约束没了 ⇒ `reason` 会写过 120 字 ⇒
`PLAN_REASON_TOO_LONG` ⇒ 正确的动作被丢掉（历史上唯一那份 EXECUTE 就是这样死的）。

**修法**：每一条补救都只作用在服务器**点名**的那个键上（`if exc.key == "response_format"` /
`elif exc.key == "temperature"`）。

### 证据

- 新增 2 条测试：**被拒的 temperature 不得动回复约束**，以及**镜像**（被拒的 response_format
  不得动 `temperature` 这个采样器设置）——镜像那条是为了防止我把作用域**收得过头**。
- 咬合证明：把无条件分支放回去 ⇒ **恰好红 1 条**（就是 temperature 那条，消息是
  "removing temperature must not touch the reply constraint"），镜像那条仍然绿。
- A/B 六个模型客户端相关套件：**1 failed / 186 passed → 187 passed**（那 1 条就是新测试）。

### 记下但没做

每个键仍然只补救**一次**：两个键都被拒的构建会让整次调用失败，而不是连续降级两次。
扩成多次重试是在这条路径上加延迟（项目量过：UNKNOWN 步里 ~10 s 是生成），
因此**记成具名问题**，不塞进这次的作用域修复里。

流程：`ca3f2b8` → `CLEAN_OUTSIDE_DATA` → `MAINLINE_OK`。
仍未验证：AUTO 仍被操作者暂停、模型服务仍退出，**自改动以来没有任何真实调用走过这条分支**。

## 实时量到的第一个真缺陷：**跨刻度比较**把真进展记成了"没进展"（`6beb141c`）

### 现场怎么发现的

看新 pin 下的这一轮，`CLEAR_INTEL` 17 步、**每步 SUCCESS**，路线是真实工作：

```
OPEN_INTEL → SELECT_INTEL_PIN → OPEN_INTEL_BEAST_TARGET → INTEL_BEAST_START_MARCH → DISPATCH_INTEL_BEAST
OPEN_INTEL → DISMISS_INTEL_GENERIC_REWARD → SELECT_INTEL_PIN → OPEN_INTEL_HERO_JOURNEY_TARGET
           → INTEL_HERO_START_MARCH → INTEL_HERO_DISPATCH
```

而 `goal_progress` = **False 9 / None 8 / True 0**，随后该 goal 拿到
`NO_GOAL_PROGRESS` 让步、streak 4 —— **"因为报不出进展而被降权"，正是
`_observation_meter` 的注释说它存在就是为了消灭的那件事。**

### 六行复现（用真函数）

```
remembered value: -8.0   remembered kind: distance    ← 数值与种类来自**不同的 tick**
progress_moved(after = 没读计数的那帧) -> False        ← "动作落地了、目标没动"
同一帧，若种类保持 observation      -> None            ← 诚实的答案
真进展（重新读板、少一个 pin）        -> True
```

机制：`_remember_goal_meters` 把**数值**与**种类**分别写，数值只在有 meter 时覆盖、种类只要有就覆盖，
于是两者可以来自不同帧；而 `progress_moved` 的守卫**只查当前种类、从不查记住的那个数值的刻度**。
⇒ `1.0 < -8.0` = False。

修法：证据刻度一旦见过就在本轮胜出（弱刻度不许覆盖它）；刻度变了就**丢掉**记下的数值
（新刻度的第一次读数是"第一次读数"，`progress_moved` 本来就答 None）。
没有 observation meter 的 goal 保持原来的 distance 比较，**什么都没拿走**。

证据：4 条测试驱动**真的** `LiveRuntime._remember_goal_meters` 与真的 `progress_moved`；
把旧写法放回 ⇒ 红 2 条（另外 2 条是**旧代码在该方向也成立**的性质，我在提交里写明了）；
A/B 六个套件 **11 failed → 9 failed**，其余 9 条逐字节相同。
