### UI-Venus-2-9B 在 8GB 卡上的真实数字（2026-10-01 实测，工具已落地）

**记这些是因为它们全部反直觉，且都是可复现的实测，不是推断。**

**① 32K 几乎不要显存。** UI-Venus-2 是**混合线性注意力**模型。`-lv 4` 缓冲账本在
`-ngl 16 -c 32768` 下给出：`CPU KV 272.00 MiB` / `CUDA0 KV 272.00 MiB` / `CUDA0 RS 23.03 MiB`，
不是同尺寸均匀注意力模型该有的 1.5 GiB。**模型自身 `n_ctx_train = 262144`**，32768 离上限很远。
所以「上下文变大所以要降 -ngl」这个推理链在本机是**错的**，-ngl 与上下文完全解耦。

**② 拉满最慢，不是最快。** 真实数据包、`-c 32768`、f16 KV、n=3，延迟 p50：
`ngl24 16878 / 26 18209 / 28 18902 / 30 17041 / 31 21011 / 32 21183 / 33 39935 / 99 59325 (ms)`。
**10 个档位全部启动成功、全部作答、0 次 CUDA OOM。** 33 层不是失败而是变慢：只剩 70 MiB，
WDDM 把溢出换页到系统内存，GPU 干等。拐点**只有一层宽**（32 层 21183 ms，33 层 39935 ms），
可用下限约剩余 100–200 MiB。生产取 `-ngl 30 / f16`（17041 ms，剩余 213–265 MiB）。

**③ 提示词管不住输出长度，schema 能。** 一条 plan 约 147 输出 token，解码仅 **14–16 tok/s**，
所以生成就是延迟本体。字段称重：`reason 41 / bbox 29 / expected 22 / action 18 / semantic_target 15
/ confidence 8 / decision 7 / goal 6`。SYSTEM_PROMPT 规则 9 已记录"把提示词写得更强硬无效"
（p50 11.5s→12.4s）——**llama.cpp 会真的强制 `maxLength` 与 `additionalProperties`**
（同一调用换成 `maxLength:30` 的 schema：147 token → 23 token）。契约在
`ui_planner.response_schema()`，且 bbox **只在元素表为空时才索要**（无条件索要时，一个 REPLAN
步白花 29 token）。
**诚实结论：保留 `expected`/`action`（校验器和解析器要读）后，实测只有 80→73 token ≈ 6%，
不是早期探针给出的 2–3×。** 真正的大头是 `expected`（去掉它实测 42 token / 2757 ms，生成快 38%），
但那要动校验器。

**④ 延迟要按「提示处理 vs 生成」分开看，不能只看总量。**
`冷包 6374ms = 提示 6277ms (2091 tok @ 333 tok/s) + 生成 0`；
`同包重发 218ms = 提示 117ms`（前缀缓存命中，`prompt_n=4`）；
`max_tokens=400 10478ms = 提示 119ms + 生成 10269ms`。
**图片固定占 1024 token**（带图 `prompt_n 2091` vs 不带图 `1014`，差额 1077），
由 `--image-min/max-tokens 1024` 钉死，而 llama.cpp 警告 grounding 任务低于 1024 不可靠。
生产每步都是新画面 ⇒ **约 6.3 s 提示处理是每步复发的**，不是一次性。
前缀缓存对**系统提示**有效（跨不同 packet 也复用），对**新画面**无效。

**⑤ `-ub` 加大反而慢 2.4 倍。** `-b 2048 -ub 2048` 实测 141 tok/s / 63 tok/s，
而 `-b 512 -ub 512` 是 333 tok/s。大微批的计算缓冲在 ngl 30 下放不下，触发换页。

**⑥ thinking 必须显式关掉。** 不带 `chat_template_kwargs={"enable_thinking": false}` 裸调时，
模型把整个 token 预算烧在 `reasoning_content` 里、`content` 返回**空**（`finish_reason=length`），
看起来像模型坏了。生产客户端已带此参数。

**⑦ 设备影响该怎么量。** `tools/profile_device_impact.py`（新）：MAA 截图 p95 是信号，
**ADB 往返是噪声**——它计时的是 adb.exe 进程启动，实测在无负载变化时自己从 24.5 ms 飘到 163 ms
（3.7×）。只测 MAA 的结论：`ngl16 21.02 ms`（不挂模型基线 21.30 ms，**无统计差异**）、
`ngl20 24.91`、`ngl18 28.73`（单次最坏 **24636 ms**）、`ngl24 29.77–31.90`。
生产档位 30 在中间，**这是有意折中**：更多 offload 让模型更快、让截图尾巴更差，两个测量方向相反。

**验收口径**：`MODEL_CONTEXT_MAX=32768` / `MAX_INPUT_BUDGET=28672`（=32768−4096 输出预留）/
`OUTPUT_RESERVE=4096`，`winter_agent_v2/context_budget.py` 是这三个数唯一的算术恒等式来源，
`launch_gui_model_server.CONTEXT` 从它导入而不是再写一遍。

### 读者类的系统性失败模式：把「读不到」实现成 `None`（2026-10-02 实测，已上线）

**这是本项目最容易反复踩的一类**，比"读错"危险得多：读错会被下游判据说穿；**读成 `None` 会被当成
"客观没看到"，然后升级成一次模型调用**（`BEAST_SEARCH_TAB_NOT_PROVEN` → 问 UI-Venus →
该画面唯一诚实答案是 REPLAN → 同一身份 7h 被问 9 次）。**`None` 不是中性值。**

**实测样例**（`ocr.py selected_tab_from_live_labels`）：判定阈值 `0.03` **宽于它所读的几何** ——
选择框画在页签正中，真括号对中心距自身标签约 **1 px**；伪描边对中心距相邻标签 **15 px**。
40 帧分离 15.3 倍，旧锁在伪值之上 ⇒ 两个 kind 同时命中 ⇒ 拒绝猜 ⇒ `None`。

**两条可复用规矩**：
1. **改判定阈值前，先在 ≥40 帧真实归档上量「真值距离」与「伪值距离」的分离度**；分离不够就别动常量。
   取阈值放在间隙的**几何中点**（本例 `0.005` = 高于最差真值 4.8× / 低于最优伪值 4.2×）。
2. **优先选「收紧」而不是「放宽」，因为收紧可证单调**：接受集是子集，而函数只在单元素集上返回
   ⇒ 只可能 `X → None` 或 `None → X`，**永远不可能 `X → Y`**。
   **这条论证才是"读者类改动可以不先跑真机就上线"的依据**，比任何单帧读数都硬。

**两条读数据时的坑**：
- **`repo_revision` 是逐 episode 的**，别拿某条旧 episode 的 revision 推断"进程卡在旧代码"；
  实测每次 repin **1–10 分钟**内被下次重启继承（RESTART 很频繁，repin 后 1 分钟即可见新版本）。
- episode 判定字段是 **`result` / `verifier_ok` / `session_outcome` / `observed_change` / `failure_type`**，
  不是 `verification.passed`；按后者读会得到"今日 0 失败"的假结论。

### 「不可归因」几乎从不是缺功能，而是生产者有、消费者没有（2026-10-02 实测）

**判据（可复用）**：怀疑某类失败"说不清为什么"时，先 grep 那个原因的**写入符号**，再看它的**读取方**。
若读取方全是 `tools/device_*.py` 一类手工诊断脚本 ⇒ **这是接线缺口**。
实例：`executor_router.last_recognition_error` 每次识别失败都算出完整词表，只有四个手写脚本在读；
`_unknown_navigation_target` 的 7 个守卫一律只 `return None`。
结果：当日 **53 条 `SEMANTIC_TARGET_NOT_VERIFIED`（92 失败里最大一块）零条带原因**。

**同样用 AST 量，别用眼估**：`VERIFIED_ATOMIC` 140 个验证器里 **18 个是两参 lambda、结构上就无法携带
evidence**（`SUBMIT_GIANT_BEAST_SEARCH`、训练营一族 9 个、`VERIFY_GATHERING`、`COLLECT_MY_REWARDS_ROW`）。

**两条纪律**：
1. **先证伪再动手。** 47 条巨兽搜索失败看似"又读不到"，用失败步骤**自己的 after 帧**过生产视觉后
   发现**根本没画卡片** ⇒ 验证器是诚实的，那是地图可用性不是代码缺陷。**证伪省下一整轮错修。**
2. **诊断值里出现 `OR` 就是把两个事实揉成一个，不能拿来分流工作。** 本轮新字段的第一条 live 读数带回
   `..._OR_TRANSIENT_PAGE`，必须拆成两个码；**第一条真实读数就是最好的验收**。

**未达标项要写清类型**：本单"同一 failure_type 下 >1 取值"在两个观测窗口都没出现（只有 1 个取值），
原因是信息量大的码挂在导航类技能上而窗口内没发生导航 miss ⇒ **是时序问题、不是接线问题**；
下一轮应直接读账本看一整天分布，而不是再开观测窗。

**live 验证的门控**：只认可 `repo_revision` 等于部署版本的行；实测 repin 后**约 2 分钟**被下次重启继承。

### 先配对再下结论：设计好的恢复会被记成 FAILURE（2026-10-02 实测）

**最强的一条判据**：把一条失败与「同一技能紧随其后的成功」配对，比输入是否相同。
本轮 12 步训练营里 **每条失败都在 4–5 秒后被同技能、同营地、同坐标的成功接住** ⇒
坐标不是差异量；客户端**教学手势吃掉第一次点击**，第二次才落到建筑上，有界重试就是为它存在的。
**失败若在数秒内被同技能同输入的成功接住，那是设计好的恢复，不是缺陷。**

**三条配套规矩**：
1. **判「升级/告警是误报」要按记录时间点当时的证据，不是今天的证据。** 本轮那条
   「2308 分钟无验证 episode」看似误报，复现输入后是真报 —— 两条验证证据都在单子开出**之后一天**。
2. **文档与实现的矛盾本身就是缺陷，代价已经付过。** 取点器 docstring 说「按当前帧光环测量身体目标」，
   代码却是 `tap_x = ring_x`；这条矛盾让两轮在单帧上挪过同一个坐标并回退。
   **契约与代码不一致时，按数据修一方，并把测量写进那个模块**，让第三次改动必须用数据说话。
3. **「包里有未跟踪模块」要按导入解析判，不是按存在性判。** 扫全部已跟踪源文件的第一方 import，
   看是否都落在已跟踪文件上（本轮 **406 个源文件全过**）⇒ 发布树导入完整。
   （但仓库里**包与 tools 下躺着 687 个未跟踪 .py**，属卫生问题。）

**验证点击坐标永远画出来看**（本项目既有规矩，本轮再次靠它定位机制）。
**提交信息含引号时用 `git commit -F <文件>`**，不要用 `-m '...'`。

### 失败簇的两个定型判据（2026-10-02 两次实测，一次判真一次判伪）

**第一步永远是配对**：把一条失败与「同一技能紧随其后的那一步」比。
* 数秒后被**同技能、同输入**的成功接住 ⇒ **设计好的恢复**，不是缺陷（训练营首点：6/6 都如此；
  该坐标已被两轮改过并回退）。
* **0 条**被接住（其余是"下一步也失败"或"是 episode 最后一步"）⇒ 真缺陷（资源页签：21/21）。

**第二步看恢复路径的门**：如果**错误路径需要「缺失的那个量」才能恢复**，这个失败就没有任何恢复。
实例：`RESOURCE_DYNAMIC` 解析需要 `resource_tab_offset`，而"格子屏幕外 → 滚动页签带"的恢复分支
**也被同一个 offset 门住** ⇒ 既不能点也不能滚，0.11 s 内被拒、`state_after` 为空、连拒两次。
**排查时专门 grep「门条件里出现失败所缺少的那个值」。**

**修完必须写清"它不保证什么"**：把那次的"立即拒绝"改成"最多滚 N 次再拒绝"**并不保证结果**——
依赖滚动后目标进入视野、识别成功。**把不保证的事写进结论**，否则下一轮会把"已修"读成"已解决"。

**live 验证的固定动作**：只认 `repo_revision` 等于部署版本的行；实测 repin 后约 **2 分钟**上线。
若窗口内目标技能一次都没出现，结论要写**"效果未观测"**并列出可判信号，**不要写"已验证"**。

### 守卫家族的 N-1 漏项（2026-10-02，第三次同类）

**症状形态**：N 条同类分支里 N-1 条有守卫、1 条没有，而那 1 条正是后加的。
实例：`brain.py` 里 11 条"某目标需要城镇 HUD → `OPEN_HOME`"分支，9 条先关搜索面板、2 条没有
（`FISHING`/`BUILDING`，都是后加的）。当日 `OPEN_HOME` 从地图被发 69 次，成功 59 条全
`resource_search_open=False`、失败 10 条全 `=True`，**完全分离无重叠** ⇒ **决策缺守卫，不是识别问题**。

**为什么长期没被发现（本轮真正的教训）**：钉这条不变量的测试**早就存在**，但它的清单是
**照着"有守卫的分支"写的**，不是照着**"发出决策的分支"**写的。它的 docstring 甚至写着
"三有守卫、四没有，本表钉住全部七个"—— 后加的两条从没进过表。

> **规则：当同一个守卫要覆盖一个家族时，测试必须从「发出该决策的分支」枚举，
> 不能从「已有守卫的分支」枚举。** 更强做法是从被测对象自身发现家族
> （问它"哪些 route 会发出这个决策"），并**断言扫描确实找到了人**——
> 空扫描会空过自己的循环，这是本项目反复踩的坑。

**判"决策缺守卫"而不是"识别坏了"的判据**：判别量与结果**完全分离**（如 59/59 vs 10/10）
说明目标本身就取决于那个条件；再看失败与验证器是否诚实（本例：门确实没画在帧上，
`after_screenshot` 为空，从未到设备）⇒ 该修决策，不该碰识别或阈值。

**归因器"我加了为什么不生效"**：先看执行器**实际绑定的** resolver，不是看函数在不在。
实例：ADB 侧的 `recognition_error` 记录器在 MAA 路径上完全无效，因为
`build_router` 把 MAA 执行器的 resolver 绑成 `lambda: router.maa_resolver(...)`，
**从不经过 runtime 的 `resolve`**。自洽证据：空理由的 11 条**恰好全是"有 MAA 节点"的技能**；
没有节点的技能会退回 `adb_resolver`，所以它们带码。

**观测到结果 ≠ 能归因到机制**：可以写"结果被观测到"，同时写"机制未观测"，
并给出该机制自己的信号（本例：若滚动分支触发，应有 SWIPE 行 + 页签从野兽三件变材料四件）。

### 记录器/守卫的写入检查（2026-10-02 三次实测后的定型动作）

**顺序**：① 看**执行器实际绑定的 resolver**（`build_router:257` 的 lambda 就绕开了 runtime 的
`resolve`，所以我刚加的记录器在 MAA 路径上完全看不见）；② 逐条找 `return None` **不写字段**的分支
（MAA 侧三处：默认的模板路径、`frame is None`、fallback 分支）；
③ **先看下一层有没有已经算好的富结果对象**——`match_template` 未命中时也返回带 `error` 与真实
`score` 的 `RecognitionOutcome`，而调用方只读了 `center_norm()`。**别自己发明词表。**

**码要带数字不只是名字**：`MAA_TEMPLATE:NO_MATCH:score=0.6150:gate=0.7/0.75`。
「离门限 0.615 vs 0.70」与「模板根本没加载」是**两个修法**；后者只说明重载裁剪。

**值语义必须与"它被写进每一行（含成功行）"一致** ⇒ **解析成功即清空**，
否则成功行会带着失败理由。**但既有测试钉住的例外要保留，不要顺手整理掉**
（LIST_DYNAMIC 回退成功时保留 `NO_ROWS`，那是"节点在漂移"的信号）。
**判断谁对：看是否有 commit 记录过那次收窄；有则测试滞后，改测试并注明；无则是真回归。**

**窗口零失败时的措辞**：部署后 8 分钟 20 条 episode **全 SUCCESS** ⇒ 写**"未观测"**，
并列三条可判信号；**不要写"已验证"**。

**不扰动生产的取舍**：取 MAA 模板真实分数需要**第二个 tasker**，会与 AUTO **争 ADB**
（本项目已实测这种争用有害）⇒ 把该测量留给部署后的账本，**并把"我故意没测"写进结果**。
