## WB-1002-33：SCHEDULED 一族的 meter 是常数，结构上永远无法报告推进（00:15，commit 23b327e，已 repin）

**`b073f33` 还未被真机继承时，我从账本里找到了本轮最有价值的缺陷。**

**全量实测：哪些目标真出现过 `goal_progress == True`**
| 次数 | 目标 |
|---|---|
| 1366 | `DISCOVER_EVENT_CALENDAR` |
| 54 / 53 / 16 / 13 / 9 / 7 / 6 | `CLAIM_EXPLORATION_IDLE` / `AVOID_STAMINA_WASTE` / `MAIL_ROUTINE` / `DAILY_ACTIVITY_TARGET` / 三个训练营 |
| **0** | **每一个 `SCHEDULED_*`** |

**⇒ 度量本身没坏，是这一族喂不进去。**
`progress_moved` 只比 `now.distance < previous`（`goal_library.py:2429`），
而 `_append_scheduled_activities` 两个分支都写死 `distance=1.0`（**2017 与 2053 行**）
⇒ **`1.0 < 1.0` 恒为 False**。

**这比"数字不好看"严重得多**：`False` 会 `no_progress_streak += 1`（`runtime.py:9734`），
而 streak 喂给 fairness bonus ⇒ **一个结构上无法报告推进的目标，
因为它没做过的事而被逐步降权。** 66 次带票选中就是这么来的。

**修法**：`_observation_meter` 用**当前帧读取器已经产出的** evidence 给这一族一个能动的读数
（`calendar_observation` 出现 / `availability_state` 离开 `AWAITING_LIVE_CLIENT_READING`），
是**等级（0.0 已广告 / 0.5 日历已读 / 1.0 实时条件已给）不是分数**，
且只作用于 `SCHEDULED_*`，其他族 `distance` 一律不动。

**两个只有"跑两个状态"才能发现的错**：
1. **两个 meter 方向相反**。`distance` 是剩余代价（越小越近，`<` 是推进）；
   我的等级是阅读深度（越大越多，`>` 是推进）。
   共用一个比较符会把"首次被读到"报成**无推进**——正是这个 meter 要消除的那个失败。
2. **尺度防护不能用"值是否在集合里"**。导航距离 `1.0` **也在** `{0.0,0.5,1.0}` 里
   ⇒ 用旧 writer 读过这些目标的 run，**第一步就会把它们全报成推进**。
   **必须按"kind"而不是按值区分**。现在 writer 在数字旁记 `_METER_KINDS`，
   读到异种尺度的值一律返回 `None`（未测量，而非无推进）。

> **通则：一个度量在某族目标上恒为常数时，先问"这个常数诚实吗"，再问"谁能动它"。**
> **常数不是测量。** 诚实的常数（尚不可观测的行）仍然有害：它让 `no_progress_streak`
> 单向累加，等于**因为相机没在看而惩罚目标**。
> **判据：`grep` 某个字段的 meter 定义，看它是不是字面量；字面量 ⇒ 这一族结构上无法推进。**
> **配套：两个 meter 可能在相反方向（剩余量 vs 深度），共用比较符必错其一。
> 而且"值在集合里"不能区分尺度（1.0 两边都有），要按 kind 记。**

**验收**：`invariant_review 10 PASS/0 FAIL/4 UNMEASURED`、`problems=0`、新测试 14/14。
严谨 A/B（标记两侧验证 mine=7 / HEAD=0）：**HEAD 9 failed、我的版本 9 failed、
NET NEW 空、FIXED 空** ⇒ 那 9 个仍是上一轮确认过的既有调度路线漂移。

**可判信号（下一轮直接读）**：
① 新版本 episode 的 `goal_progress_by_id` 里 `SCHEDULED_*` 出现 **`true`**（此前恒 false/None）；

## WB-1002-35（诊断轮）：11.5% 的调度决策是"孤儿"——决策了但没有执行（00:45）

**为什么分支仍观测不到？找到了一个此前从未量化的记账缺口。**

**发现过程**：15:59:30 决策 `DISCOVER_QUICK_PANEL_TASKS` → 15:59:35 产生 episode；
**随后 15:59:38 / :41 / :45 三次 SCHEDULED 决策，全部没有 episode**，直到 16:03 才恢复。
逐条查证：这段空档 = **角色切换**（`1063040265` → `1061663148`，耗时 3.5 分钟），
前 4 次决策的 `role_id` 是**旧角色**。

**全量量化（最近 600 次决策）**：
```
30 秒内无对应 episode 的决策：69/600 = 11.5%
孤儿决策的 chosen 分布：
  SCHEDULED_BEAR_HUNT 8 / KEEP_TRAINING_PRODUCTIVE 7 / SCHEDULED_BROTHERS_IN_ARMS 5
  SCHEDULED_OFFICER_PROJECT 4 / SCHEDULED_FORTRESS_CONTEST 4 / ... / LABYRINTH_DAILY 3
```
⇒ **SCHEDULED 族是孤儿决策的最大来源。**

> **通则（新增，价值很高）：`decisions.jsonl` 记录"Scheduler 选了什么"，
> `episodes.jsonl` 记录"实际执行了什么"——两者之间没有第三本账说明差额去哪了。**
> **"决策了但没执行"是静默的**：决策账本看起来一切正常（它确实选了），
> episode 账本看起来也正常（它确实没记录），**没有任何一处写着"这次没做"。**
>
> **判据（可复用，5 行）**：对每条 decision，取其后 6 条 episode 的 `goal_id`，
> 若 `chosen` 不在其中 ⇒ 孤儿决策。**孤儿率是一个此前不存在的健康指标。**
> **孤儿集中在某一族目标 ⇒ 该族实际上处于"被选中但无法执行"状态，
> 而 scheduler 的公平性账本会把每次选中都记成 `selected`，看起来很公平。**
>
> **这解释了本轮所有"观测不到"**：分支在 brain 层是对的，
> 但 11.5% 的决策在到达 brain 之前就散了，且**散得最多的正是它要修的那一族**。

**未修，本轮只诊断**：正确修法涉及角色切换与调度边界（`_selectable` 之后、
`decide` 之前的那一步），属于架构改动，**必须先查清那一步的现有契约**，
不能顺手加一行日志或补一个 episode。**下一步应先回答：
"角色切换窗口内，Scheduler 有没有被允许做出选择？"**

### 根因定位：`_note_the_choice` 在 `brain.decide` 之前记账（`runtime.py:8666` vs `:8690`）

```python
board = self.goal_library.rank(...)
best_goal = board[0][0] if board else None
self._note_the_choice(board, before)        # ← 8666：写决策 + selected += 1 + last_selected_at
...
self._sync_brain_goal(best_goal, gate)
...
decision = self.brain.decide(before, self.registry)   # ← 8690：这一步之后才可能有动作
```

⇒ **`decide` 返回 `SAFE_STOP`、或中途 `finish()`、或角色切换时，
这次"选中"永远没有 episode，但公平性账本已经记成"公平选中"。**

**为什么这是真缺陷而不是记账洁癖**：
1. `fairness_bonus` 用 `selected`/`offered`/`no_progress_streak` 算等待补偿 ⇒
   **一次从未执行的"选中"会累积等待补偿**，让那个目标越来越容易被选中，
   **而它依然不会执行** ⇒ 正反馈。
2. 面板与 `decisions.jsonl` 看起来完全正常（"它确实选了"），
   `episodes.jsonl` 也正常（"它确实没记录"）⇒ **没有任何一处写着"这次没做"**。
3. 孤儿集中度极高：600 次决策里 69 次孤儿，**其中绝大多数是 `SCHEDULED_*`**
   —— 正是最需要被观察、也最容易被"选中但不动"的一族。

**正确的修法方向（尚未实施，属架构改动）**：
不是"补一个 SAFE_STOP 的 episode"，而是**把"选中"与"承诺执行"分开记账**：
- `offered` 仍然每步累加（它记录"上过板"，是对的）；
- `selected` 应当在**动作真的被发出**时才累加，而不是在 `rank` 返回时；
- `decisions.jsonl` 可以继续记录"选了什么"（那是 Scheduler 的事实），
  但**必须能区分"选了并执行"与"选了但没执行"**。

**实施前必须先查清现有契约**：`selected` 有没有别的消费者、
`last_selected_at` 是否被面板/等待补偿之外的东西依赖。
**不能顺手改**——本轮连栽两次的教训就是"以为懂了就去改"。

### 修正上一条：不是"正反馈"，是"永远等不满"（查过消费者之后）

我先前推断"`selected += 1` 累积等待补偿 ⇒ 正反馈"。**查源码后不成立，必须修正**：

```
fairness_bonus(row, ...)   只读 row.last_selected_at
selected                   只有 as_json / from_json 用它（纯序列化）
offered                    只有 _note_the_choice 写
```

**所以空选的真正代价是**：`last_selected_at` 在**空选时也被刷新**
⇒ **一个目标每次被"选中"（哪怕什么都没做）都重新开始计时**
⇒ `FAIRNESS_OVERDUE_MINUTES` 的等待补偿**永远攒不满**
⇒ **越常被空选的目标，越永远等不到补偿。**

> **通则（记账时序，通用）**：任何"等待时长"型补偿，它的**计时起点**必须由
> **承诺兑现**刷新，而不是由"决定"刷新。
> **决定 ≠ 承诺执行**；用决定刷新计时器，等于**每次尝试都把等待清零**，
> 而"尝试很多次却一次没成"正是最需要补偿的情况。
>
> **判据（可复用）**：改任何 `*_at` / `*_count` 字段的写入时机前，
> 先 `grep` 它的**全部**消费者，确认没有别的东西依赖旧时机。
> 本轮我先推断再查证，**推断错了**——写记忆时必须写查证后的版本。

**修法方向随之收窄**（仍属架构改动，未实施）：
把 `last_selected_at` 的刷新从 `_note_the_choice`（选中时）
移到**动作真的被发出**之后。`offered` 保持不动（它记录"上过板"，本来就对），
`selected` 的语义需重新定义（"被承诺执行"而非"被 rank 选中"）。
**注意 `_logged_goal` 去重逻辑（`if str(chosen_goal.goal_id) == self._logged_goal: return`）
会跳过重复目标的日志——若要记录"选了但没执行"，这条早退也要一起看。**

## WB-1002-36（诊断轮·续）：孤儿决策的根因 = `SAFE_STOP` 结构上不写 episode（00:55）

**上轮量到 11.5% 孤儿，本轮定位到具体一行。**

### 排除过的三个候选（都错了，记下来省下轮次）
- ❌ **run 间隙**：`_logged_goal` 是 run-scoped，但 `auto_uptime` 显示
  **15:58:00 结束、16:02:36 才结束** ⇒ 那三次在 run **之内**。

- ❌ `_deferral_replan` / `_stop_instead_of_looking_again`：离线重放证明都不生效。
- ❌ `trace_id` 判 run 边界：**生产 episode 的 `trace_id` 为空串**，不能用。

### 真根因
`brain` 返回 `SAFE_STOP` → `runtime.py:8975` 处理 → `self._runtime(...); return finish(reason)`。
**`_runtime` 记录 agent 状态，但它不是 `_record_episode`** ⇒ 不写 episode。
全量 10,343 条 episode 里 **`SAFE_STOP` 出现 0 次、`WAIT` 0 次**。

`runtime.py:9040` 的注释明说 *"A refusal is not an ending: it ends the TASK, not the CYCLE"*
——**早年的缺陷是它结束了整个 cycle，那已修**；
**但"拒绝不留任何行"从来没被处理**，于是两本账无法对账。


```
05:25-05:58  FAILURE ×2 → SUCCESS ×1
23:35-23:37  FAILURE ×2
23:38-23:40  SUCCESS ×5     ← 连续一段
```

**同一版本（`8e57cad9`）内既有 5 连成功也有失败；`951abbdd` 时代 132 次里 125 成功 0 次 NO_MATCH。**
**⇒ 这不是"某个模板天生不稳定"，而是"某些时段整段不稳定"。**
