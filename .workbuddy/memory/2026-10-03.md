## WB-1002-33：SCHEDULED 一族的 meter 是常数，结构上永远无法报告推进（00:15，commit 23b327e，已 repin）

**`b073f33` 还未被真机继承时，我从账本里找到了本轮最有价值的缺陷。**

**全量实测：哪些目标真出现过 `goal_progress == True`**
| 次数 | 目标 |
|---|---|
| 1366 | `DISCOVER_EVENT_CALENDAR` |
| 54 / 53 / 16 / 13 / 9 / 7 / 6 | `CLAIM_EXPLORATION_IDLE` / `AVOID_STAMINA_WASTE` / `MAIL_ROUTINE` / `DAILY_ACTIVITY_TARGET` / 三个训练营 |
| **0** | **每一个 `SCHEDULED_*`** |

**⇒ 度量本身没坏，是这一族喂不进去。**
`progress_moved` 只比 `now.distance < previous`（`goal_library.py:2429`），
而 `_append_scheduled_activities` 两个分支都写死 `distance=1.0`（**2017 与 2053 行**）
⇒ **`1.0 < 1.0` 恒为 False**。

**这比"数字不好看"严重得多**：`False` 会 `no_progress_streak += 1`（`runtime.py:9734`），
而 streak 喂给 fairness bonus ⇒ **一个结构上无法报告推进的目标，
因为它没做过的事而被逐步降权。** 66 次带票选中就是这么来的。

**修法**：`_observation_meter` 用**当前帧读取器已经产出的** evidence 给这一族一个能动的读数
（`calendar_observation` 出现 / `availability_state` 离开 `AWAITING_LIVE_CLIENT_READING`），
是**等级（0.0 已广告 / 0.5 日历已读 / 1.0 实时条件已给）不是分数**，
且只作用于 `SCHEDULED_*`，其他族 `distance` 一律不动。

**两个只有"跑两个状态"才能发现的错**：
1. **两个 meter 方向相反**。`distance` 是剩余代价（越小越近，`<` 是推进）；
   我的等级是阅读深度（越大越多，`>` 是推进）。
   共用一个比较符会把"首次被读到"报成**无推进**——正是这个 meter 要消除的那个失败。
2. **尺度防护不能用"值是否在集合里"**。导航距离 `1.0` **也在** `{0.0,0.5,1.0}` 里
   ⇒ 用旧 writer 读过这些目标的 run，**第一步就会把它们全报成推进**。
   **必须按"kind"而不是按值区分**。现在 writer 在数字旁记 `_METER_KINDS`，
   读到异种尺度的值一律返回 `None`（未测量，而非无推进）。

> **通则：一个度量在某族目标上恒为常数时，先问"这个常数诚实吗"，再问"谁能动它"。**
> **常数不是测量。** 诚实的常数（尚不可观测的行）仍然有害：它让 `no_progress_streak`
> 单向累加，等于**因为相机没在看而惩罚目标**。
> **判据：`grep` 某个字段的 meter 定义，看它是不是字面量；字面量 ⇒ 这一族结构上无法推进。**
> **配套：两个 meter 可能在相反方向（剩余量 vs 深度），共用比较符必错其一。
> 而且"值在集合里"不能区分尺度（1.0 两边都有），要按 kind 记。**

**验收**：`invariant_review 10 PASS/0 FAIL/4 UNMEASURED`、`problems=0`、新测试 14/14。
严谨 A/B（标记两侧验证 mine=7 / HEAD=0）：**HEAD 9 failed、我的版本 9 failed、
NET NEW 空、FIXED 空** ⇒ 那 9 个仍是上一轮确认过的既有调度路线漂移。

**可判信号（下一轮直接读）**：
① 新版本 episode 的 `goal_progress_by_id` 里 `SCHEDULED_*` 出现 **`true`**（此前恒 false/None）；
② `no_progress_streak` 不再对这些目标单向累加；
③ `decision_reason` 出现 `event_route_goal_leaves_a_page_it_cannot_act_on`（上轮那批）。

## WB-1002-34：投影不是观察者，不该持票（00:25，commit efd0872，已 repin）

**先读信号**：`b073f33` 已继承 8 条 episode，但**没有一个 SCHEDULED 目标**
（`AVOID_STAMINA_WASTE` 4 / 面板类 3 / `PET_TREASURE` 1）⇒ **新分支没被触发是正常的，不是缺陷。**
**"信号未出现"要先确认"场景是否出现过"，否则会误判成修复失败。**

**本轮缺陷（有票、却永远不会被执行）**：
```
ALLIANCE_TIMED_EVENTS   status=UNKNOWN  route=None  skills=()  ticket=50.0
```
四件事**单独都对，合起来就是黑洞**。它是 **provider 投影**：
`available_skills=()` + `execution_owner="EXISTING_EVENT_GOALS"`，
其 docstring 自称 *"a provider record, never a second execution instance"*；
而本盘上 `linked_goal_ids=[]` ⇒ **连归属目标都不在**。
⇒ **被定价、被排序、然后在选择边界被拒**（`route_for(...) is None`），
叙述为"priced as observable but has no route"。

**为什么 WB-1002-24 的 `SCHEDULED_` 前缀规则覆盖不到它**：
那是给**日历行**的，而这个 id 是**手写的 provider 记录**，前缀不匹配。
⇒ **同一族缺陷的第三个入口，前缀规则只能覆盖"按规则生成"的那些。**

**修法刻意不是"再给一个 route"**：给 route 会让投影变成可执行，
而它自己的 evidence 说它不该执行。**错的是票**——票是"会有人去读"的承诺，这里没人能去。
`observation_ticket` 现在对**任何声明了 `execution_owner` 的行**返回 0，
**判据取自行自己的字段**（不是这里硬编码目标名表）⇒ 未来的投影只要自报家门就能被识别。

**`linked_goal_ids` 刻意不参与判据**：归属目标在场时，投影仍然不是"会读的人"，
**读的是归属目标**，观察属于归属目标自己的行。

**修后全盘实测，零误伤**（这张表是本轮最重要的产出）：
| 目标 | ticket | route | 说明 |
|---|---|---|---|
| 20 个 `SCHEDULED_*` | 50.0 | EVENT | 不变 |
| `ALLIANCE_TIMED_EVENTS` | **0.0** | None | **本次修复** |
| `USE_FREE_ARENA_ATTEMPTS` | **50.0** | None | **绝不能被静音的真观察目标** |
| `LABYRINTH_DAILY` | **50.0** | None | 同上 |

> **通则（新增）**："无 route 的行"要分成两类，处置**相反**：
> ① **真观察目标**（`USE_FREE_ARENA_ATTEMPTS`）⇒ 必须**持票**，否则就是"未定价且不可见"的黑洞；
> ② **投影/记账行**（`ALLIANCE_TIMED_EVENTS`）⇒ 必须**不持票**，否则是"有人会去读"的空承诺。
> **判据：看 `evidence.execution_owner`——有它就是记账行。**
> **把两类一起静音或一起放行，都会制造 §5 禁止的黑洞。**

**验收**：`invariant_review 10 PASS/0 FAIL/4 UNMEASURED`、`problems=0`、新测试 4/4。
A/B 标记两侧验证（mine=1 / HEAD=0）：**两侧均 0 failed、NET NEW 空**。

**可判信号**：① `goal_state` 里 `ALLIANCE_TIMED_EVENTS` 仍在板上但不再被选中；
② `decisions.jsonl` 里 `ALLIANCE_TIMED_EVENTS` 的 `observation-ticket` 消失（此前 38 次）；
③ 上一轮的 `goal_progress_by_id` 里 `SCHEDULED_*` 出现 `true`。
