### 核查了哪些官方接口

- 读了官方文档：`codebuddy.ai/docs/zh/cli/http-api`（本地 CLI HTTP API）与
  `open.workbuddy.cn/docs/openapi`（WorkBuddy 开放平台）。
- **本机网关实际是 2.147.0**（`GET /api/v1/info`），`GET /api/openapi.json` 可用，**117 个端点**。
  这纠正了契约文档 §3 的旧结论（"没有可访问的 OpenAPI 文档，只能读 bundle"）。

### 重要澄清：本地 API 的凭据是"网关口令"，不是账号凭据

官方文档明确：`--serve` 默认口令认证，口令是本地生成的，用
`Authorization: Bearer <password>` / `X-Access-Token` / `gateway_session` cookie 携带；
**没有云端账号凭据、没有 API Key、没有 OAuth**，文档也完全不谈计费。
⇒ `CODEBUDDY_GATEWAY_PASSWORD` 只是"本地进程的门钥匙"。
能调通 API（health ok、job 建成、`POST /runs` 返回 202 accepted）**完全不能推出"能调到模型"**。

**官方 `/runs` 与 `/jobs` 都被接受，但两边都没有可执行的会话**：网关接受了活，却没有活会话、
也没有受它管辖的执行体。在本网关里启动 daemon 也不改变这一点（daemon 继承同一套环境）。

### 两条路径第一个实际不同的环节

| | 桌面端（能用） | 本项目（接受但永不执行） |
| --- | --- | --- |
| 谁启动 | `WorkBuddy.exe` | 本项目的 `GatewayService` |
| 形态 | **每个会话一个边车**：`--serve --port 0 --session-id <会话>` | 一个共享网关：`--serve --port 8080` |
| 额外 argv | `--settings`、`--mcp-config`、`--prompt-vars-file`、`--allowedTools`、`--model`、`--permission-mode fullAccess` | 无 |
| 环境 | 146 项，含 `CODEBUDDY_HOST=workbuddy-desktop`、宿主能力、产品配置溢出、`WORKBUDDY_PAC_RPC_TOKEN`、`CONFIG_DIR=~/.workbuddy` | 61 项：bundle 选择器、网关口令、内网标记——**没有模型/宿主接线** |
| 活会话 | 有（就是你正在对话的那个） | `sessions/live -> null` |
| daemon | 运行中（应用的） | `stopped` |

**第一个真实差异不是某个 flag、模型名、提示词或 worker，而是：应用启动的是"它自己作为宿主的会话"，
本项目启动的是"没有宿主的网关"。** 模型访问跟着"应用托管的会话"走，不跟着本地 API 走 ——
所以在我们自己的网关里无论怎么 fork / attach / 重试都造不出模型访问。
这也解释了 §9.5：worker 走到 `idle` 就停，因为它是一个没有宿主的会话。

### 还缺的那一环（官方路径）

WorkBuddy 开放平台就是为这件事准备的，且与本地网关 API 是**两套东西**：

- 认证：OAuth 2.1 授权码。需注册开发者账号 + 创建第三方应用（拿到 clientId/clientSecret），
  再由**用户本人授权一次**，换 `access_token` / `refresh_token`。
- 对应能力：`POST /openapi/v2/localassistant/message`（scope `user.localassistant.invokable`）
  ——"向 PC 端本地助理发送消息，触发助理执行任务"，配 `GET` 同一路径轮询回复。
  这正是"用户已经能用模型的桌面助理"。
- 积分：平台另有"兑换码/卡券为授权用户发放积分"接口，口径指向**用户自己的 WorkBuddy 账号积分**，
  但文档没有写明具体计量方式，需要以平台侧为准，不能在这里臆断。
- **本机目前完全没有这套授权**：项目与 settings 里都没有任何开放平台应用 / clientId / token。
  必须由用户去创建并授权；不能用网关口令推导，也不能自动开通。
