## 契约工单（`fb629a9`）：黑窗真因 + WorkBuddy「异常」真因

### 一、黑窗：**审计出来的，不是猜的**

ADB 早就在每个调用点都传了 `CREATE_NO_WINDOW` —— **根因不在这里**。真凶两处：

1. **`state_truth._head()`**：每次**刷新**都跑 `git rev-parse HEAD`，**完全没有 creationflags**。
   `report()` 每次都调它 ⇒ 面板每隔几秒闪一次黑窗。
2. **`panel_restart.py`**：`tasklist` / shell 探针没有 flags，而**面板启动路径**会调它
   （一窗一时钟检查）；另外**无控制台的父进程**启动控制台子进程时，Windows 会**新分配**一个控制台
   —— 这就是 `preflight.py` 里 `adb connect` 闪窗的原因。

**修法**：新建 `winter_agent_v2/winproc.py`，**全项目唯一启动后台进程的地方**：
`CREATE_NO_WINDOW` **加** `STARTF_USESHOWWINDOW`/`SW_HIDE`（后半对才有控制台的父进程有效）、
`shell=False`（只有一个 `run_shell`）、输出 PIPE/DEVNULL **绝不继承**、
`spawn_detached` 给服务用（独立进程组 + 日志 + PID）、`kill_tree`/`alive`/`port_owner`。
`V2_SHOW_BACKGROUND_CONSOLES=1` 是唯一看控制台的方式，默认关。

**顺带量到第二个真缺陷**：本环境给 Python 自己设了 UTF-8 默认，而控制台工具按 OEM 代码页输出 ——
`netstat -ano` 直接抛 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xbb`，
**诊断恰好在出问题的时候失败**。封装现在固定 `encoding` + `errors="replace"`。

**守卫**：`check_wiring` 用 AST 扫包与 `tools/`，任何不带 flags 的 `subprocess.*`/`os.system` 直接红，
另有一份**带理由的**一次性工具白名单（23 个，逐名列出）。

### 二、WorkBuddy「异常」：**词是推的，网关是真的下线了**

实测：`127.0.0.1:8080` **拒绝连接**，`netstat` 里**没有监听者、没有 owner pid** ⇒ 服务没在跑。
全项目**没有任何代码启动它**（`codebuddy --serve` 由人工启动），所以操作者担心的
「probe 失败→再启一个→下一轮再启」这条链**在代码里不存在**。
我**没有**给 GUI 加启动器：面板偷偷拉起一个 agent host 比一个状态格大得多。

## 2026-09-18 深夜（四）— 版本身份两处根证据修复（提交 f5344f5）

§A **路径不是内容**：旧 digest = staged diff + unstaged diff + untracked **manifest**，
manifest 只有路径没有字节，所以「改了一个未跟踪文件的内容」得到同一版本——而未跟踪文件
正是开发 agent 交付新模板/知识文件的方式。

新模块 `winter_agent_v2/version_identity.py`，**刻意只用标准库**（它必须在 runtime 被 import
之前运行）：
- clean tree → 完整 commit SHA
- dirty tree → 完整 SHA + sha256 over 排序后的 (status, path, content-hash)，仅覆盖
  **version-relevant** 脏路径；目录逐文件展开；删除贡献 DELETE 标记；未跟踪文件贡献字节。

路径策略两面都写死（两种失效模式方向相反）：
include `winter_agent_v2/ · config/ · knowledge/ · dataset/candidate/ · tools/run_live.py ·
tools/preflight.py`；exclude `learning/ · evidence/ · dataset/raw/ · dataset/truth_audit/ ·
docs/ · .git/ · .workbuddy · out_* · __pycache__ · *.pyc`。
把整个脏树都 hash 会让版本每写一条 Episode/一张截图就漂移，于是「同一版本跑过」永远不可观察。
tools/ 按文件而不是按目录白名单，理由相同：GUI 不属于一次 live cycle 加载的东西。

**新测试抓到的缺陷**：git 会把未跟踪**目录**折叠成一条（`?? dataset/`），而
`is_version_relevant("dataset/")` 答 False → 里面真正相关的文件永远不会被看到。
现在展开未跟踪项，并带剪枝，绝不深入 `learning/`、`evidence/`、`dataset/raw/`。

`escalation_queue.repo_revision` 改为委托这一份实现，不再留第二份可能漂移的副本。

§B **磁盘不是正在运行的东西**：`tools/run_live.py` 在模块层 import 15 个 `winter_agent_v2` 模块，
却在 `main()` 第 129 行才读 revision —— 描述的是 import **之后**的磁盘。若一个 Job 在一轮中途
完成，它的新 revision 会被记到「跑的是旧代码」的 Episode 上。现在在 `sys.path` 设置之后、
runtime import **之前**冻结 `PROCESS_CODE_REVISION`，Episode 取该冻结值；并删掉那个已具误导性的
`repo_revision` import，让「现读磁盘」这件事不再随手可用。冻结幂等，后续代码无法中途改口。
既有 `VERIFIER_MAPPING_CORRUPT` 守卫（源码树在加载期间被改写）原样保留，仍覆盖 import 窗口。

Episode **只保留 `repo_revision` 一个字段**，没有加 `process_code_revision` 孪生字段：它现在

## 2026-09-18 深夜（九）— §4 封掉旧的 LIVE_VERIFIED 捷径（提交 8c4cf08）

审计目标就是 `reconcile_outcome` 的**第一个分支**：只要存在 verifier_ok 且 revision 不同于派发时刻的

## 2026-09-18 深夜（十八）— §9 STATE_CONFLICT：把「自相矛盾的四种方式」命名出来（提交 be453cd）

规则不是「这些不常见」——**四条里有三条是同一张截图里实测到的**——而是：一个页面同时握着两个

```
REUSE_WITHOUT_VERIFICATION       生产复用已记录，却没有 LIVE VERIFIED 的 episode
TRACE_DISAGREEMENT               两个区域给出不同的当前 trace
LOST_JOB_SHOWN_AS_VERIFYING      JOB_LOST 被显示成「验证中」
RELEASED_LEASE_SHOWN_AS_HOLDER   已释放的租约被显示成当前 holder
```

每条 finding 都带**两个值**加一句「哪一个还不可信」——把「不许静默挑一个答案」变成机械可查的东西。
**合法情形保持安静**，否则检查会变成噪音：先验证后复用、租约确实被持有、丢失的 job 显示为丢失，
都报零条。

它是检查器不是存储：每个值都来自已有的选择器或工件，**包括 `current_development_trace`**——因为
正是「两个各自挑选的当前 trace」造成了它现在要抓的分歧。**§7 必须先落地这个才有可能**：在它之前
根本没有唯一的 trace 可供比较。

开发页新增「一致性」格，起始值是 **未检查（等待首次刷新）** 而不是「一致」——理由和顶栏从「未确认」
起步一样：**没比较过任何东西的页面不得声称一致**。检查自身失败会报告「检查失败 <type>」而不是留白。

真机核实：四条规则各自在矛盾对上触发、在合法情形静默。178 项相关测试全绿，check_wiring problems: 0，
**并且把窗口跑起来看了 30 秒无崩溃**（检查器就在它的刷新路径上）。

## P0 HOTFIX：Acceptance Seed 的两个派发语义漏洞（commit b3ce423）

**两个"缺失"而不是"错误"的缺陷，所以整套测试全绿也看不见。**

1. **seed origin 从未作为值存在**。`preload()` 在两个派发点都硬编码 `origin="bootstrap"`，
   而 `acceptance_seed_allowed` 的"同时只允许一个种子"是靠**数 origin == bootstrap_seed 的记录**
   实现的——守卫在读一个谁都没写过的字段，所以永远不可能触发。
   现在 origin 由 arm reason 算一次、所有点（两个知识分支）共用，理由随 created 行进台账。

2. **候选策略不存在**。`BootstrapPlan.actionable` 只是 `not in_flight`，`select()` 没有种子过滤，
   于是那张一次性票可以落到任何可行动行上。实测它选了 `TROOP_SELECT`（CAP-G09）——它的 `unlocked`
   读作 OBSERVED，**只是因为 `_sibling_observed("G")` 在同族里找到了 `RECALL_MARCH`**；
   它自己 `current_role_available=UNKNOWN`、没有任何自己的工件。**族不是能力。**

   新增 `seed_eligible()`：硬门 = risk T0/T1、real_money NONE_ALLOWED、永久禁止动作
   （**按 token 子集匹配——`STATE_TRANSFER` 是两个 token，单 token 相等比较等于什么都没拦**）、
   以及**必须有它自己的可用性证据**，走命名阶梯
   `CATALOG_OBSERVED_AVAILABLE > LIVE_SKILL_EVIDENCE > PAGE_ASSET_MEASURED`。
   族/分类推断不算证据 → `TROOP_SELECT` 记 `SEED_NOT_CURRENTLY_OBSERVED` 跳过，**不是 BLOCKED**。
   操作员写成"优先"的（requires_march / requires_stamina / Verifier）留在 `seed_order_key()` 排序，
   不做门——把偏好当门会在唯一合法候选恰好要行军时拒绝种子。

3. **选择只能有一个权威**：`preload()` 在没传 plan 时取 `candidates[0]`，完全绕过 `select()`——
   CLI 正是这样派出了 TROOP_SELECT。现在改用同一个 selector、同一个 mode。
