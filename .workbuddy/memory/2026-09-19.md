

## 2026-09-19 凌晨 — 清理 playwright-cli 插件的 23 个失效占用标记

用户截图弹出 Windows「启动 `genie-trash\win32-x64.exe` … 时失败 0x800700e8」。定位：
`.workbuddy/plugins/cache/.../playwright-cli/0.1.0/.in_use/` 下 25 个以 pid 命名的占用标记，
其中 **23 个对应进程已死**（26312 等）。WorkBuddy 试图用自带的回收站助手 genie-trash 清理它们，
而**启动 genie-trash 本身就失败**：`0x800700e8` = ERROR_NO_DATA，在创建进程场景里通常意味着
交给子进程的 stdio 管道已关闭。

处理：**逐个重新核实存活**（pid 会被复用，不能沿用几分钟前的读数）→ 只移动已死的 23 个 →
移到 `%LOCALAPPDATA%\WinterAgentV2\quarantine_plugin_markers_20260919_001438\` 并写 manifest，
**移动而非删除**，可随时搬回。保留 2 个仍存活的：25028(WorkBuddy.exe)、3192(ChatGPT.exe)。
结果：23/23 移动、0 失败；`.in_use` 现仅剩这两个。

**根因与我有关**：那 23 个死 pid 里有 4088/5184/6232/7892/9576/3468 等，正是本会话为验证
「面板能否存活」而反复启动、又被宿主回收或被我 terminate 的进程。**被强杀的进程没有机会删掉自己写的
占用标记**，于是攒成残骸，再由 WorkBuddy 的清理去扫，而清理本身又失败 → 周期性弹窗。

**可复用的教训**：在这个环境里频繁起停短命进程（尤其加载了插件的），会在
`plugins/cache/**/.in_use/` 累积死标记，进而触发桌面端弹窗。这类标记**可以作为噪音忽略**，
但若弹窗扰人，清理方法是「核实 pid 已死 → 移动而非删除」。别把「启动失败」当成产品故障。

## 2026-09-19 凌晨（四）— 冷启动死锁：一次性验收种子 + 自动关闭机制（提交 3aca9c4）

**死锁说清楚**：预载器在主循环被证明之前不得派发，而主循环没有被证明就无法被证明——因为需要先有东西
走一遍。实测：`current_development_trace() = None`、记录全终态（COOLDOWN 2 / DONE 9 / FAILED 3）、
`version_active`/`live_verified`/`production_reuse` 全 0。**没有输入 → 永远无法被证明 → 第一条 trace
永远不会派发**；而「等随机 Runtime Gap」把验收变成抽奖。

`acceptance_seed_allowed(root)` 就是这个例外，刻意做窄：
- 检查顺序：**真实 P0 阶梯优先** → 种子 → 操作员 override。种子是**产品机制**，不是人工决定，
  所以不需要任何人改 `config/bootstrap_arm.json`、不需要手工造 Gap、不需要往台账插假记录。
- 每个条件都从**工件**读出（不是参数传入），因此不在场的人也能复现这个答案，调用方也无法
  「声称条件成立」来拿到想要的结论：无 production_reuse、无未完成 trace、无 WORKING/SUBMITTED/
  NEW/QUEUED、无第二个 bootstrap_seed、无设备租约、操作员 RUNNING、生产窗口活着（pump 心跳新鲜）、
  网关 HEALTHY。
- **会自我关闭**：一旦台账出现真实 `production_reuse`，立即写
  `learning/knowledge_bootstrap/MAIN_LOOP_PROVEN_ONCE.json` 并永久停止接受种子——**靠证据而不是标志位**，
  标志位会在重启中丢失。「活过自己成功的例外」就不再是例外。

操作者 13 条里**有两条明确不在本函数检查**并已具名，避免被误当成已强制：风险等级 T0/T1 与永久禁令
是**候选**的属性，在**选择阶段**强制。本函数回答「现在允许不允许开种子」，选择器回答「这个能力是否合法」。
把候选规则放这里，会让它们看起来被检查了，而其实还没有任何候选被看过。


trace」，比现在更糟。操作者 §一 明确把「正式GUI在线」列为种子条件，我不放宽它。

**结论**：种子派发被单一条件阻塞；解它需要一次真实的 GUI 启动（我能起的进程会被宿主回收，

## 03:40 已验证：Acceptance Seed 只能武装"一次派发"，够不到 production_reuse

我已经把上一条里的推断变成了**可复现证据**（不是读代码猜的）：

| 探测 | 结果 |
|---|---|
| `arm_state('.')` | `(False,'NOT_ARMED_MAIN_LOOP_P0','…P0-A=PARTIAL, P0-B=PROVEN, P0-C=PROVEN, P0-D=NOT PROVEN, P0-E=PARTIAL, P0-F=NOT PROVEN')` |
| 复制真实台账 + 把种子记录改成终结（`reconciled/DONE`）后 `acceptance_seed_allowed` | `False` —「上一个 bootstrap_seed（…，状态 DONE）已终结但未产生 production_reuse：不得静默补发第二条…若确需新种子，需先写入显式替换关系」 |
| 同状态 `arm_state` | 仍 `False / NOT_ARMED_MAIN_LOOP_P0` |
| 用真实输入调 `preload_gate(armed=False,…)` | `allowed=False, reason=NOT_ARMED_MAIN_LOOP_P0` |

## 21:0x–21:4x — 面板弹窗 `0x800700e8` 的根因（操作者贴图提问）

操作者贴了一张 Windows 弹窗：`[出现错误 2147942632 (0x800700e8) (启动"git log "--format=%h %cI" -40"时)]`。

**根因链（全部有证据，非推测）**：
1. `0x800700E8` = Win32 错误 **232 = ERROR_NO_DATA**（管道正在被关闭）。
2. 该 argv 全仓**只有一条代码路径**：`tools/unattended_closure.py::heads()`；而 `tools/control_panel.py:1433` `import unattended_closure` 并在**刷新路径**上调用 `heads()`。
3. 面板跑在 **无控制台的 `pythonw`** 下，而 `heads()` 是面板可达范围内**唯一**既不传 `creationflags` 也不传 `startupinfo` 的调用点 ⇒ Windows 给 Git-for-Windows shim 挂控制台并启动失败（弹窗标题正是 shim 目录 `C:\Program Files\Git\cmd`）。
4. `heads()` **按设计吞掉 OSError** 并返回 `[]` ⇒ `build()` 会对着一次**确实提交过**的提交写 "no commit landed after the submission"。失败是静默的。

**为什么 `check_wiring` 报 `problems: 0`**（这才是真正值得记的一点）：`unattended_closure.py` 被列在 `HUMAN_TERMINAL_TOOLS` 白名单里，理由写的是 "operator-run closure ladder"。该豁免的**前提**是"人只在终端里手跑"，而这正是"允许它不隐藏控制台"的依据 —— 但面板会 import 它，前提是假的，于是规则**恰好在需要它的地方失效**。已删除该条目，并新增 `reached_tools()`：**去检查前提本身**（被代码 import 的豁免工具 = 问题）。

**验证方式（可复用）**：证明"守卫真的会咬"—— 写一个临时文件放旧的裸 `subprocess.run`，`unhidden_process_calls()` 立刻点名它（`tools/out_probe_guard_bite.py:6`），这同时就是"豁免才是遮蔽源"的直接证据。新测试 `tests/test_closure_git_runs_hidden.py` 把两半都钉住：回退修复 → **5/8 变红**；恢复 → 8/8 绿。
