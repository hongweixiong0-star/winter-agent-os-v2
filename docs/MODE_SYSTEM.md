- 性质：**核心架构规范**

## 一、总原则

系统运行分两种模式，互斥，不能同时开：

- **Auto 模式**：系统在游戏里跑，WorkBuddy 不用机器
- **Manual 模式**：机器完全归 WorkBuddy，Auto 暂停

模式状态必须持久化。切换必须原子化。

---

## 二、Auto 模式（运行模式）

目的：让系统在游戏里跑。
使用者：用户。
WorkBuddy 状态：休息，不做任何开发。

**允许**

- 执行已知 Skill
- 遇到 UNKNOWN 走本地 UI-Venus
- 失败后退避、冷却、重试
- 状态回写
- 调度执行

**禁止**

- 改代码
- 改规则
- 改架构
- 联网
- 问用户技术问题
- 做真机实验

**输出**：游戏任务完成率。

---

## 三、Manual 模式（开发者模式）

目的：让系统变强。
使用者：WorkBuddy。
Auto 状态：暂停。

**机器归属**

Manual 模式下，机器完全归 WorkBuddy。

- MuMu、ADB、游戏画面、截图、输入——全部归它
- 不"蹭"机时，不"等"窗口，不"申请"暂停
- 想看哪个页面就看哪个页面
- 想点哪里就点哪里（在安全边界内）

**允许**

- 改代码
- 加 Skill
- 修 Verifier
- 联网搜索
- 写文档、审规则
- commit、repin、重启
- 自由真机探索
- 反复试错
- 自由观察任何页面

**禁止**

- 真钱支付
- 未经授权花钻石
- 不可逆高价值操作
- 改用户明确策略（零氪、钓鱼普通饵）
- 绕过 Risk Gate

**输出**：更好的系统（新 Skill、修复、规则）。

---

## 四、模式切换：三种触发

### 触发 1：用户强制切到 Manual

用户说"切 Manual"：

- Auto 等到安全点
- 暂停 Auto
- 机器归 WorkBuddy
- **WorkBuddy 不得自动退出 Manual，直到用户说切回**

### 触发 2：用户强制切到 Auto

用户说"切 Auto"：

- WorkBuddy 立即停止开发
- 完成收尾（见第七节）
- Auto 恢复
- **WorkBuddy 不得自动切回 Manual，直到用户说切换**

### 触发 3：WorkBuddy 自主切换

WorkBuddy 可以自己判断是否需要切到 Manual。自主切换必须满足三个条件：

**条件 1：有明确理由**

切到 Manual 的理由必须是：

- 需要真机实验验证一个具体功能
- 需要观察一个具体页面/路径
- 需要跑一个具体的新 Skill
- 需要调试一个具体的失败

不能是："我想开发" / "我觉得该做点什么" / 没有具体目标的探索。

**条件 2：登记切换**

切换前必须记录：切换理由（一句话）／预计时长／完成标准（做到什么算完）。

**条件 3：自主回切**

切到 Manual 后，必须自动切回 Auto。触发回切：

- 完成标准达成 → 立即切回
- 达到预计时长 → 触发"决策点"（见第五节）
- 遇到阻塞 → 切回并报告

---

## 五、自主切换的时长与决策点

"预计时长"**不是**"强制回切点"。它是必须做决策的阈值。

到达预计时长时，WorkBuddy 必须二选一：

**选项 A：暂停并回切**

- 保存当前进度
- 记录状态到 `docs/HANDOFF.md`
- commit 现有工作
- 回切到 Auto
- 下次再切回来继续

**选项 B：申请延长**

- 说明为什么还需要更多时间
- 给出新的预计时长
- 更新切换登记
- 继续工作

**不允许**：到了时长假装没到／不记录进度直接继续／无限延长不回切。

---

## 六、机时分配（仅适用于 Auto 模式）

机时分配**只在 Auto 模式下生效**。Manual 模式下机器完全归 WorkBuddy，机时分配作废。

**机制 1：Auto 空闲时自动让出**

- Auto 连续 30 秒无可执行任务 → 让出机时
- WorkBuddy 可做短实验（< 1 分钟）
- 做完立即还回机时

**机制 2：定时实验窗口**

- 每隔 1 小时给 WorkBuddy 5 分钟固定窗口
- 不管 Auto 有没有空闲，窗口都保留
- 用于中实验（1-5 分钟）

**机制 3：自主切换到 Manual**

- 需要长实验（> 5 分钟）时
- WorkBuddy 直接切到 Manual
- 走自主切换流程（第四、五节）

| 实验类型 | 时长 | 用哪种机制 |
|---|---|---|
| 短实验 | < 1 分钟 | 机制 1 |
| 中实验 | 1-5 分钟 | 机制 2 |
| 长实验 | > 5 分钟 | 机制 3（自主切 Manual） |

注意：**用户强制切 Manual 时，以上机制全部作废**——机器直接归 WorkBuddy。

---

## 七、切换的原子性与收尾

**切换必须原子化**

切换动作本身是一次事务：

- 中间不执行任何游戏操作
- 中间不执行任何代码改动
- 要么完全切过去，要么不切

如果切换中崩溃：模式状态是持久化的 → 重启后根据持久化状态恢复 →
**不允许"半 Auto 半 Manual"的状态**。

**从 Manual 切回 Auto 的收尾**

情况 1：**本轮有代码改动**。必须完成：

1. 当前工作 commit
2. repin
3. 验证生产能启动（`--check-only` 通过）
4. 报告：做了什么、验证了没有、还有什么没做完

**不完成收尾，不允许回切。**

情况 2：**本轮无代码改动（纯观察）**。允许直接回切。但必须记录：观察到了什么／下一步打算做什么。

## 八、搜索规则

搜索是 Manual 模式下**唯一的硬约束**。

**开发新功能时：硬门**

进入实现前必须先产出搜索产物：

```
=== 搜索产物 ===
任务/问题：<一句话描述>
搜索关键词：<搜了什么>
搜索结果：<搜到了什么，来源在哪>
假设：<基于搜索，我认为应该怎么做>
不确定性：<哪些还没搞清>
=== 结束 ===
```

**没有搜索产物 → 不允许进入实现。**

**调试阶段：软门**

遇到问题时鼓励搜索，但不强制。因为有些问题搜不到（比如具体游戏 UI 的临时状态）。

**搜不到也是搜索结果**：记录"搜了 X，没找到"／基于当前真机观察形成假设／继续调试。

**不允许**：搜不到就卡住不动／搜不到就直接问用户。

**打转判定**：如果同一个问题上试了 3 次还没进展、且没有输出过搜索产物 →
立即停止试，先去搜索。

## 九、控制台显示

控制台必须显示：

```
当前模式：Auto / Manual
机器状态：系统运行中 / WorkBuddy 开发中
切换发起方：用户 / WorkBuddy
切换理由：<一句话>
已持续：<时长>
预计剩余：<时长，如果已知>
回切条件：<完成标准 或 到达预计时长>
```

用户一眼能看到当前是谁在用机器、为什么、还要多久。

## 十、优先级规则

当规则冲突时，按以下优先级：

1. **用户强制指令**（用户说切哪个就是哪个）
2. **安全边界**（真钱、不可逆、用户明确策略）
3. **机器模式一致性**（不能同时开）
4. **WorkBuddy 自主判断**（未与用户指令冲突时）
5. 流程优化

关键点：

- 用户强制切 Manual 后，WorkBuddy **不许自主回切**——哪怕任务完成了
- 用户强制切 Auto 后，WorkBuddy **不许自主切回 Manual**——哪怕开发做到一半
- 自主切换只在用户没有明确指令时才生效

---

## 十一、WorkBuddy 的职责

- 在 Auto 模式下：休息，让系统自己跑
- 在 Manual 模式下：开发、搜索、验证、提交
- 切换由用户决定时：服从，不自动反切
- 用户不在且无明确指令时：**默认留在 Auto**
- 需要切 Manual 时：自主判断、登记理由、按时收尾
- 在 Manual 模式下：机器完全归你，自由探索

**核心原则**

Auto 模式：系统玩游戏，WorkBuddy 不动。
Manual 模式：机器归 WorkBuddy，自由探索、搜索、验证、开发。

自主权 = **自己判断 + 自己负责 + 自己收尾**。不是"自己决定就不管了"。

---

## 十二、禁止清单

**模式相关**

- 两种模式同时开
- 切换时不保存状态
- 切换时留未提交的代码
- 在 Auto 模式下改代码
- 在 Manual 模式下执行不可逆操作
- 用户强制切 Manual 后自主回切
- 用户强制切 Auto 后自主切回 Manual
- 无理由切到 Manual
- 到时长不决策、不记录、继续工作
- 回切时生产起不来

**搜索相关**

- 开发新功能跳过搜索
- 搜不到就卡住
- 搜不到就直接问用户

---

## 十三、异常与恢复

**模式切换中崩溃**

1. 重启后读持久化的模式状态
2. 如果是 Manual 且未收尾 → 继续收尾
3. 如果是 Auto → 继续运行
4. 记录崩溃原因到日志

**Manual 模式长时间未回切**

如果 WorkBuddy 在 Manual 模式超过预计时长 **10 倍**：

- 控制台必须**高亮警告**
- 用户可以选择强制切 Auto
- WorkBuddy 收到强制切 Auto 后**必须服从**

**Auto 模式长时间无任务**

如果 Auto 连续 **10 分钟**无可执行任务：

- 控制台显示"系统空闲"
- 提示用户可以切 Manual 让 WorkBuddy 开发
- 但**不自动切**（保持用户主动权）

### 实现侧的裁决（规范里两处没有直说，落地时必须定）

**裁决 A：`Manual` 有两种，规矩相反 —— 这是本轮最要紧的一条。**

- **用户强制的 Manual（§4 触发 1）**：WorkBuddy **完全不能**自己切回，哪怕收尾四项全做完、
  哪怕它认为任务已完成。只有用户能解锁。
- **WorkBuddy 自主切的 Manual（§4 触发 3）**：它**必须**自己切回（条件 3），收尾门管的就是这一种。

**这条最初实现错了**，而且是靠端到端冒烟跑（不是靠单测）发现的：当时 WorkBuddy 做完收尾就把
用户强制的 Manual 交还了 —— 正好违反 §4 触发 1 与 §10 的"哪怕任务完成了"。
现在由 `user_latch` 区分两种 Manual；`--by` 是"声明的发言者"并写入历史。

**裁决 B：§7 的收尾门 vs §10 的用户优先 —— 门保留，但给一条有记录的否决路径。**

§7 写"不完成收尾，不允许回切"，§10 把用户强制指令排在第 1 位，两者冲突。
读法：§10 第 2 级是**安全边界**、§12 又把"切换时留未提交的代码""回切时生产起不来"列为硬禁止，
所以收尾门**不是**纯流程要求，不能被静默跳过；但它可以被用户**明确否决**。
落地：默认拒绝并一次列全所有未完成项（不是每次只报一条）；用户可用 `--force` 否决，
否决会以 `OVERRIDDEN BY USER: …` 写入历史轨迹，指名跳过了什么。
"用户坚持"于是是**有案可查的事实**，而不是隐形绕过。

**裁决 C：用户重申当前模式也要留下标记。**
"切 Auto"时机器本来就在 Auto，曾经被当成无操作直接返回 —— 于是闩锁没上，WorkBuddy
下一个 tick 就能把机器拿走。现在用户的重申照记（`re-affirmed by user`），
但**不重置 `started_at`**：否则反复重发命令就能把 §5 的决策点变成不可测。
