# Winter Agent OS V2 — 真机优先开发流程

- 配套文档：`MASTER_RULES.md`（→ `.workbuddy-ai/rules/`）、`MODE_SYSTEM.md`
- 作用：定义从"遇到新东西"到"完成"的完整开发流程
- 性质：**核心开发规范**
- 来源：操作者 2026-10-06 原文照录。改动前先看 §八 与 `PRINCIPLES.md §72`。

## 一、总原则

开发不是"写完再试"，是"**先试再写**"。

```
搜索 → 真机试 → 观察 → 写代码 → 真机验证 → 完成
```

关键：**真机验证不在最后，从第一步就在碰真机。**

核心逻辑：

- 先搞清**事实**（搜索 + 真机观察）
- 再写代码（基于事实，不是假设）
- 最后验证（真机跑通才算完成）

## 二、完整流程

### 第 1 步：搜索

开发任何新功能前，第一步永远是搜索。

**搜索什么**

任务层面：这个任务/活动是什么／规则是什么／怎么玩、走什么流程／花不花钱、有没有不可逆操作。

UI 层面：游戏里看到的图标是什么／它在哪个位置、周围有什么／点击后会发生什么／有没有使用限制。

**搜索来源**（不限范围）：游戏官网、公告、活动说明；官方论坛、客服文档；社区攻略、Wiki；
视频平台实机演示；GitHub 同类项目；玩家讨论。

**搜索产出** 必须产出：

```
=== 搜索产物 ===
任务/问题：<一句话描述>
搜索关键词：<搜了什么>
搜索结果：<搜到了什么，来源在哪>
假设：<基于搜索，我认为应该怎么做>
不确定性：<哪些还没搞清>
=== 结束 ===
```

**没有搜索产物 → 不允许进入下一步。**

### 第 2 步：真机试

带着搜索形成的假设，去真机验证。

**为什么必须真机试**：游戏里看到的和搜到的不一定一样 —— 版本可能不同／账号状态可能不同／
UI 可能有变化／可能有弹窗遮挡。**搜索只是假设，真机才是事实。**

**单步探索能力**：WorkBuddy 需要能"**单步执行任意动作**"，**不依赖预先写好的 Skill**。

允许的探索动作：在某个坐标点击／滑动／返回／打开某个页面／关闭弹窗／读取当前页面／截图观察。

**探索纪律**

- 探索前：说明探索目的（我想搞清什么）、说明探索范围（允许点到哪里、不允许点到哪里）
- 探索中：每一步之后观察真实结果；结果和预期不符 → 停下来分析；出现意外状态 → 记录并尝试恢复
- 探索后：记录观察到的 UI 路径／控件位置／状态变化／意外情况

**探索边界**

允许：打开任何安全入口／关闭任何弹窗／观察任何页面／滚动、返回、切换标签／反复试错。

禁止：真钱支付／未经授权花钻石／不可逆高价值操作／改用户明确策略／覆盖已有生产状态。

### 第 3 步：观察

真机试的时候，记录所有看到的。

**观察什么**

- UI 层面：图标样子（颜色、形状、图案）／位置（顶部/底部/侧边/中央）／有没有红点、数字、倒计时／
  周围有什么其他 UI／点击后发生了什么
- 流程层面：从哪个页面进入／经过哪些步骤／到达哪个页面／有没有弹窗干扰／有没有加载等待
- 状态层面：页面状态变化／控件状态变化／数值变化／队列变化

**关键：看到的必须联网搜索补充。** 游戏里往往只显示一个图标，没有文字、没有说明。
看到 UI 后，必须联网搜索，才能知道它是什么。

```
真机看到：屏幕右侧竖排有一个红色礼盒图标
搜索关键词：
  - "无尽冬日 右侧 礼盒 图标"
  - "无尽冬日 超值活动 入口"
搜到结果：
  - 这是"超值活动"入口
  - 每天可以领免费礼包
  - 有时需要钻石购买其他礼包
```

**为什么必须搜**：光看图标无法判断功能；点错可能触发不可逆操作；只有搜索才能知道它是什么。

**搜不到怎么办**：换关键词再搜（用图标特征、位置、周围文字）→ 搜视频演示 → 搜社区讨论 →
实在搜不到 → 标记 `UNKNOWN_UI`。

**不搜索 = 瞎猜 = 点错 = 可能出事。**

### 第 4 步：写代码

基于观察结果写代码，不是基于猜测。

- 控件位置来自真机，**不硬编码**
- 流程来自实际路径，不靠想象
- Verifier 来自实际状态变化
- **引用 UI 知识库，不重复定义**

**Skill 与 UI 知识库的关系** —— Skill 引用知识库：

```
VISIT_WANDERING_MERCHANT:
  入口 = ICON_WANDERING_MERCHANT（来自知识库）
  路径 = 知识库记录的路径
  验证 = 知识库记录的状态变化
```

**UI 变化时，只改知识库，不用改所有 Skill。**

### 第 5 步：真机验证

写完代码立刻真机验证，**不先跑离线测试**。

```
1. 写代码
2. 真机跑一次（第一次碰真机就在这）
3. 看结果
4. 失败 → 回到第 2 步（真机试）
5. 成功 → 沉淀
```

**不是**：写代码 → 离线测试 → 真机验证（才第一次碰真机）。

**验证失败怎么办**

不允许：改代码后直接再跑，不分析／跑一次失败就放弃。

正确：看真机实际输出 → 对比预期 → 定位差异原因 → 修正 → 重跑。

### 第 6 步：完成

**完成 = 真机跑通 + Verifier 确认。**

不是：代码写完 ❌／单元测试通过 ❌／离线回放通过 ❌
是：真机执行成功 ✅／Verifier 确认 ✅

**沉淀**（成功后必须）：

1. 记录证据（Episode、截图、Verifier 结果）
2. 更新 UI 知识库
3. commit
4. 如果是新 Skill，注册到 Skill Registry
5. 更新 Capability Coverage

**验证复用**：第二次遇到同一场景 → 直接走已学会的 Skill，**不搜索、不调模型**。

## 三、UI 知识库

每次探索发现的 UI，都必须记录。**不记录 = 下次还要重新探索 = 浪费机时。**

### 记录格式（每种 UI 至少包含）

| # | 字段 | 内容 |
|---:|---|---|
| 1 | 名称 | 语义名称（`PAGE_TRAINING`、`BTN_CLAIM_ALL`） |
| 2 | 类别 | 页面 / 面板 / 按钮 / 图标 / 弹窗 / 列表 |
| 3 | 位置 | 所属页面、屏幕相对位置 |
| 4 | 外观特征 | 图标、文字、颜色、形状 |
| 5 | 作用 | 干什么的、点了会怎样 |
| 6 | 触发条件 | 什么时候出现 |
| 7 | 进入/离开方式 | 从哪进来、点哪出去 |
| 8 | 使用限制 | 每日次数、冷却、条件 |
| 9 | 花费 | 免费 / 花钻石 / 花道具 / 不可逆 |
| 10 | 状态 | 正常态 / 禁用态 / 高亮态 / 红点态 |
| 11 | 来源 | 真机观察（哪次）+ 联网搜索（哪个资料） |
| 12 | 可信度 | CONFIRMED / OBSERVED / CANDIDATE / UNKNOWN_UI |

### 存放结构

```
knowledge/ui/
  pages/    PAGE_HOME.md, PAGE_TRAINING.md, ...
  panels/   PANEL_BUILDING_QUEUE.md, ...
  controls/ BTN_CLAIM_ALL.md, ICON_EVENT_GIFT.md, ...
  popups/   POPUP_SESSION_DISCONNECTED.md, ...
```

### 与 UI-Venus 的关系

```
运行时遇到 UI：
1. 先查知识库
2. 找到 → 直接用，不调模型
3. 找不到 → 调 UI-Venus 识别
4. UI-Venus 识别后 → 走"看见 → 搜索 → 理解 → 记录"补充

知识库 = 长期记忆
UI-Venus = 临时大脑
```

**知识库越全，UI-Venus 调用越少，系统越快。**

## 四、与离线测试的关系

离线测试仍然有用，但**位置变了**。

- 旧位置（已废弃）：`写代码 → 离线测试 → 真机验证`（离线测试是**验收**）
- 新位置：`真机探索 → 写代码 → 真机验证 → 离线测试`（离线测试是**回归保护**）

说明：第一次遇到 → 真机探索 + 写代码 + 真机验证；跑通后 → 加离线测试保护已跑通的功能；
以后改动 → 先跑离线测试看有没有破坏，再真机验证。

**离线测试是保护层，不是验收层。**

---

## 五、搜索的完整规则

**允许搜索的场景**：开发任何新功能、新任务、新活动之前／遇到不认识的 UI／遇到报错不知道原因／
遇到游戏机制不懂／遇到数值判断不确定／遇到 Verifier 判定不准／遇到工具库用法不会／
遇到任何"我不确定"的情况。

**禁止搜索的场景**：Runtime AUTO 执行期／UI-Venus 推理期／MAA 执行期／Fishing Realtime 路径。

**搜索优先级**

```
1. 当前真机 fresh 观察（最高）
2. 近期真实 Episode + Verifier
3. 项目内 CONFIRMED Knowledge
4. 项目内 OBSERVED Knowledge
5. 官方文档 / 公告
6. 社区攻略
7. 视频演示
8. 模型推测（最低）
```

**外部资料只是假设，必须真机验证才能落地。**

**搜索的硬门**

- 开发新功能前没搜索 → 不允许进入实现
- 有搜索产物但没有实际搜索记录 → 视为没搜
- 搜了但没形成假设 → 不算完成搜索

**打转判定**：同一个问题上试了 3 次还没进展、且没有输出过搜索产物 → 立即停止试，先去搜索。

## 六、禁止清单

**开发流程**：写完一堆代码才第一次碰真机／离线测试通过就以为完成／
没有真机观察就凭猜测写坐标／绕过探索直接写完整流程／搜完就写 Skill，不真机验证。

**UI 理解**：看到一个 UI 就直接使用，不搜不查／凭图标样子猜测功能／搜到结果不记录／
记录不带来源／把搜索来的当成真机验证过的／搜不到就放弃记录／搜不到就凭猜测使用。

**完成标准**：代码写完当完成／单元测试通过当完成／离线回放通过当完成。

---

## 七、完成定义

一个功能完成 = **真机跑通 + Verifier 确认**。

```
搜索 → 真机试 → 观察 → 写代码 → 真机验证 → 完成
                                    ↓
                              离线测试（保护）
```

真机验证是**必须**的；离线测试是**补充**的；两者不能互相替代。
**停在"离线测试通过" = 未完成。**

## 核心总结

| | |
|---|---|
| 旧流程 | 搜索 → 写代码 → 离线测试 → 真机验证 → 完成 |
| **新流程** | **搜索 → 真机试 → 观察 → 写代码 → 真机验证 → 完成** |

区别：真机验证**前移**了；观察 + 搜索是写代码的**前提**；离线测试从"验收"变成"保护"；
完成 = **真机跑通**。

一句话：**先搞清事实（搜索 + 真机），再写代码，最后真机验证。不是先写再试。**

# 落地进度与第 1、3 步的实测结论

> 2026-10-06，主线 `codex/production-pin-recovery`。以下结论都是**量出来的**，不是估的。

## 第 1 步：有没有单步探索能力 —— **原来没有；`066dcce0` 之后有了**

**实测**：`tools/` 下 **325 个 `.py`**，其中 **161 个**是一次性探针
（`cq_*` / `probe_*` / `observe_*` / `device_*l4*` / `bear_*` / `fishing_explore*`）。

**没有**任何工具能"执行任意一个动作"。最接近的三个都不满足：

| 工具 | 实际能力 | 差了哪一层 |
|---|---|---|
| `tools/probe_live_operation.py` | ""One operation, one id, every frame timed…"" —— 按 `--goal` + `--label` 执行**一个具名操作**并逐帧计时 | 仍要事先知道要操作的那个**标签**，不是任意动作 |
| `tools/device_l4_session.py` | 把 Tests A / A2 / B / C / D / D2 **写死在脚本里**的验收会话 | 要改脚本才能换动作 |
| `tools/device_l4_session_v2.py` | 同样是写死的 5 步流程 | 同上 |

**旁证（很有说服力）**：2026-10-05 那一整轮会话里，为了"走到巨熊页签"我**自己新写了 5 个临时脚本**
（`_bear_read_under_lease.py`、`_bear_reach_tab.py`、`_bear_open_tab.py`、`_bear_tab_template_tap.py`、
`_bear_strip_walk.py`）。**每一次"想单步看一眼"的代价都是再写一个脚本** —— 这正是第 2 步要消掉的成本。

## 第 2 步：探索工具 —— **已做**（提交 `066dcce0`）

`tools/explore_step.py`：**一次调用 = 一个动作 + 一次观察 + 一条证据。**

```
explore_step.py --purpose ... --scope ... --observe
explore_step.py --purpose ... --scope ... --tap 0.669 0.173
explore_step.py --purpose ... --scope ... --tap-text 取消
explore_step.py --purpose ... --scope ... --swipe 0.72 0.09 0.21 0.09 --duration-ms 420
explore_step.py --purpose ... --scope ... --back
```

**设备通路一行新代码都没有**：输入走项目自己的 `Executor` + 自己的 MAA adapter + 自己的
`DeviceLease`（与 `tools/probe_live_operation.py` 同三个对象），因为坐标闸门记着"全树只有两个
代码点能 tap，这个数字不得增长"。`HIGH_RISK_WORDS` 是 **import** 的（那个模块写着"两份风险词表
就是两套风险规则"），`--tap-text` 的定位走 `ui_collection.grounding_regions`（与既有探针的
`find_label` 同一个调用）。

**新增的是纪律被命令行强制、而不是靠记**：`--purpose` / `--scope` **必填**、一次只允许一个动作、
**非 Manual 模式直接拒绝**（§二 把探索归 Manual，§五 禁止在 Runtime 执行期做）。

**真机验证过**（不只是单测）：`--observe` 读到城市 HUD 并落证据行；`--tap-text 背包` 在 MAA 上
`executed=True`、页面 `HOME -> ALLIANCE`；`--back` 把客户端恢复到 `ALLIANCE -> HOME`，
**没让它留在改动后的状态**。证据行落在 `learning/exploration_log.jsonl`，帧落在
`dataset/exploration/<run_id>/`。`tests/test_the_exploration_step_tool.py` 9 passed；
坐标闸门仍 `0 violations, 0 rulings`。

**用它自己的过程中抓到两个缺陷，都留了记录**：

1. `lease.acquire()` 返回 `(record, reason)` **元组** —— 我第一版对结果做真值判断，元组恒真，
   **会把"拿不到租约"读成成功**。
2. 风险闸门一开始对所有输入生效，于是**下一次调用（一个用来恢复客户端的 `--back`）因为联盟 HUD 上有
   "加速"二字被拒绝** —— 等于工具没法离开一个页面，却没换来任何安全。现在是**按动作分档**：
   导航永不筛；裸坐标按整帧筛（它说不出下面是什么）；具名文字按**它自己的词**筛。
   §32 那句"这是暂时不能做，还是整个都不该做"同样适用于**守卫**，不只是过滤器。

| 8 **使用限制** | 无对应字段 | ❌ **缺** |
| 9 **花费** | 只有 `risk` / `risk_basis`，**不是花费** | ❌ **缺** |
| 10 状态 | `states` / `status` / `last_seen` / `last_verified` + `entry_badges.json`（红点） | ✅ |
| 11 **来源** | `source` / `evidence_refs` / `verification` / `semantic_evidence.json`（244 帧语料） | ⚠️ 有**真机**来源，**没有联网搜索来源** |
| 12 **可信度** | `status` / `verification` / `semantic_evidence.json` 的 `confirmed`/`unconfirmed` | ⚠️ **只有 2 档**，规范要 4 档（CONFIRMED/OBSERVED/CANDIDATE/UNKNOWN_UI） |

**结构差异**：规范要 `pages/ panels/ controls/ popups/` 的**逐元素 markdown**；
项目实际是**按语义分片的 JSON**（`semantic_dictionary` / `page_transitions` / `navigation_matrix` /
`entry_badges` / `generic_semantics`）。

**结构差异不是缺陷**：项目自己已经吃过"两套词汇"的亏（见 `rules/README.md §3` 与
`docs/RULES_AUDIT_2026-10-05.md` 的冲突 C3/C4）。**建议不新建 markdown 目录**，
而是把规范的第 8/9/11/12 四项**加进现有 JSON 的 schema**——否则同一个 UI 会有两份记录，
而"哪份是真的"正是本项目反复出问题的形状。

## 一处需要在动手前先裁决的规范冲突（第 2 步会撞上）

**本规范 §二 允许"在某个坐标点击"作为探索动作**；
而 **宪法 A（`OPERATIONAL §24.2`）硬禁止"固定像素坐标点击"，并写明"也不得作为识别失败时的备用方案"**，
且自标"不设置生产点击例外"。

**读法**：宪法 A 的适用范围写作"全部**生产执行路径**"，而探索不是生产路径。
所以两者可以并存，边界是：

- **探索工具里允许坐标点击**（本规范 §二明说允许，且 §六禁止的是"没有真机观察就凭猜测写坐标"）；
- **生产路径仍然一律禁止**，且坐标台账不得回流成生产点击目标（宪法 A §24.4）；
- 探索得到的坐标**只能进知识库当"观察记录"**，不能当作生产定位依据。

`tools/check_coordinate_hardcoding.py` 只扫 20 个生产模块、不扫 `tools/`，与这个读法一致。
**但这一条是我推导的，不是操作者明说的** —— 落地第 2 步之前应当由操作者确认。
