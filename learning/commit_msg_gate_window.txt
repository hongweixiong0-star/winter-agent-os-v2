fix(gate): the no-progress rule could only ever see one goal, and that was the read

_The gate's window is the whole of its memory: a goal whose attempts fall outside it is not
"not stalled", it is invisible, and no rule in the module can say anything about it._

`capability_gate._episode_tail` seeked back `limit * 4096` bytes and its own comment called
4 KiB "a generous upper bound" for an episode.  Measured 2026-10-08 on the live ledger
(136.8 MB, 10,110 rows): the mean row is **13,508 B**, 3.3x the claimed bound.  So
`EPISODE_TAIL=400` returned **138 rows** -- 1 h 50 m, all of it `AVOID_STAMINA_WASTE`.
`CapabilityGate.load` asked for 400 rows, got 138, and nothing downstream could tell.

What that cost, measured, not argued: `attempted` held **1** of the 24 goals that had really
run, `streaks` held 1 entry, and no-progress -- the one rule that exists to stop AUTO
re-entering a path that is not advancing -- could fire only for whichever goal happened to
dominate the tail.  The 34-alternation `SUBMIT_RESOURCE_SEARCH` <-> `BACK` loop that burned
6.5 minutes under `KEEP_MARCHES_PRODUCTIVE` from 00:42:25 on 2026-10-08 could not be
deferred, because `KEEP_MARCHES_PRODUCTIVE` was not in the window at all.

**The read.**  It now grows backwards in 1 MiB chunks until it really has `limit` rows, is
older than the window, or reaches the start of the file.  Chunks are joined once at the end:
prepending each chunk onto the buffer copies the whole buffer every step, which measured
1.7 s for a 54 MB read against 0.27 s spent parsing it -- most of the cost of the read was
the read.  Now 0.56-0.72 s.  Growing rather than guessing is the standard shape for this
problem; there is no stdlib helper for it.

**The window.**  `EPISODE_WINDOW_HOURS = 24`, checked as the read grows, so the read stops at
the window rather than at a row count that approximates it.  24 h is not a round number, it
is where the answer stops changing: replayed over the same ledger
(`E:/experiments/gate_window_replay.py`), 6 h reaches 15 goals and defers 5; 24 h reaches 24
goals and defers 9; 72 h reaches the same 24 and defers the same 9.  The row cap (4,000) and
the byte cap (64 MB) remain as cost bounds, and both can only ever make the window *smaller*
-- a cap must not be able to invent a deferral, and neither can.  `load` now passes the
gate's own `moment` into the read, so the boundary and the rows it bounds share one clock.

**The blast radius, measured before shipping.**  The 8 goals newly reachable with a
reachable streak are `KEEP_BUILDING_PRODUCTIVE` (93), `KEEP_TRAINING_PRODUCTIVE` (32),
`SCROLL_QUICK_PANEL_TASKS` (31), `SCHEDULED_FISHING_TOURNAMENT` (20), `DAILY_ACTIVITY_TARGET`
(14), `KEEP_MARCHES_PRODUCTIVE` (8), `OBSERVE_FISHING_STATE` (5), `HERO_RECRUIT_ADVANCED` (4).
A streak is not a block: `_probe_anchor` measures from the goal's own newest attempt, so a
deferral whose last attempt is older than the 30-minute probe window is re-admitted
immediately.  Measured at 12:54Z, with AUTO idle for hours, **only `AVOID_STAMINA_WASTE` is
actually blocked** (last attempt 0.2 min earlier); the other eight had already lapsed
(3.5-6.8 h).  So this does not park eight goals; it makes each of them deferrable while it is
being actively attempted and repeatedly not advancing, which is the intent.

**The recorded hazard was checked, not assumed.**  `.workbuddy-ai/memory/MEMORY.md` (2026-09-18)
records a *false* no-progress streak from the beast route's episodes being filed under
`KEEP_MARCHES_PRODUCTIVE` while the goal was deferred, and says "改它会动到全项目覆盖率与所有
streak 数字，本轮只报告不擅动".  Widening the window raises those stakes, so it was measured:
`SCAN_MAP_FOR_BEAST` now files 175/175 rows under `AVOID_STAMINA_WASTE`, 0 under
`KEEP_MARCHES_PRODUCTIVE` -- the misattribution that hazard names is gone.  Every one of the 8
newly reachable goals was then read row by row, and each is a genuine wall (a meter that has
never once read `True`, or a route that is pure navigation): none is a measurement artifact of
the window.

**Proof.**  `tests/test_the_gate_reads_the_window_it_claims.py`, 14 tests, and the bite is
shown rather than claimed: running the new tests' own fixtures through the old reader out of
git `HEAD` (`E:/experiments/window_reader_ab.py`) gives 266 rows where the test demands 400
(1,000 x 6,000 B) and 40 where it demands 50 (50 x 40,000 B) -- both would have failed.  The
early stop is pinned by an equivalence test (the stop must return exactly what reading
everything and filtering returns), and that test's bite is shown too: a read that stops after
one 1 MiB chunk -- the same class of mistake as the byte guess being replaced -- returns 170
rows where the reference is 721 (`E:/experiments/early_stop_bite.py`).  End to end on the live
ledger: old window -> 1 goal attempted, 1 deferral; new window -> 24 goals, 9.  A/B on the
touched suites: `test_capability_gate.py`, `test_queue_pump.py`,
`test_runtime_bootstrap_integration.py` are **17 failed both with this change and with the file
reverted to HEAD**, and the two failure sets are byte-identical, so none of the 17 is this
change's.  The eight file set that touches the gate is 17 failed / 137 passed, the same 17.  A
full-suite number is deliberately not quoted as evidence: this project's own notes record that
the suite's red count is decided by the content of `learning/` rather than by the code, so only
a same-command, same-order comparison means anything.

**A fixture mistake worth recording.**  The equivalence test's fixture was first written
newest-first.  The real ledger is append-only with rising timestamps (measured: **0 inversions
in 10,179 rows**), and a read that starts at the end of a descending file returns *zero* rows --
so the fixture was quietly testing a different thing.  `_ledger` in the test file now refuses to
write a fixture whose timestamps do not rise with file order, and three other fixtures were
reordered by the same guard.  The monotonicity the early stop rests on is named in the docstring
next to the row and byte caps, which rest on it too.

**Recorded and deliberately not done** (measured, with its number): 40 episodes carry
`goal_id=KEEP_MARCHES_PRODUCTIVE` while `attached_goal_ids=[]` and `goal_progress_by_id={}` --
a row filed under a named goal that nothing measured, so `_step_goal`'s label and
`action_relevant_goal_ids` disagree when `best_goal is None` and the frame's board does not
price the committed goal.  Forcing the label into the attachment set would also start
incrementing that goal's `no_progress_streak` in `goal_utility`, i.e. the same class of
change the 2026-09-18 note declined, and 40 rows are not worth that blast radius on the same
commit as the window.

**Not live-verified.**  AUTO has not run since this change, so a real stalled round has not
been observed to defer.  Do not read this commit as "the stall is fixed in production".
