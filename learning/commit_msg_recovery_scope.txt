fix(model): each recovery must be scoped to the key the server actually named

``_post`` raises ``_RejectedKey`` for exactly two keys, and only when the error body names one::

    if exc.code in (400, 422) and "response_format" in lowered:
        raise _RejectedKey("response_format") from exc
    if exc.code in (400, 422) and "temperature" in lowered:
        raise _RejectedKey("temperature") from exc

The recovery, however, ran the schema downgrade for **either** of them: the ``if
payload[...]== "json_schema"`` branch was unconditional and only the ``temperature`` removal was
keyed.  So a build that complained about ``temperature`` silently took the grammar away as well --
no error, no warning, a well-formed request that still gets answered.

**What that costs is measured, which is why this is a defect and not a tidy-up.**  The anti-prose
design rests entirely on the grammar holding: ``ui_planner`` caps ``reason`` at ``maxLength: 120``,
and ``ui_venus_contract.reason_violation`` then *refuses* a longer one rather than truncating it,
because "a truncated rationale still cost the tokens it was written in".  Measured
2026-10-08T13:51:35Z: the only ``EXECUTE`` in this project's history -- page HOME, element ``E6``, on
``home__control__36e65c39``, the screen that had been asked 84 times across a week -- carried a
**three-sentence reason past 120 characters** and was refused with ``PLAN_REASON_TOO_LONG``.  A
reason that long cannot come out of a grammar that bounds it (llama.cpp's own
``grammars/README.md`` converts ``maxLength: 100`` into ``char{1,100}``), so that call ran
unconstrained, and this branch is one of the ways that happens without a word.

Reverting it was not enough on its own, so the previous commit records which constraint was really
in force (``reply_constraint``); this one stops one of the two ways it was being lost.

**Tests.**  Two cases added to ``tests/test_the_reply_constraint_is_recorded.py``: a rejected
``temperature`` must leave the reply constraint alone, and -- the mirror -- a rejected
``response_format`` must leave the greedy sampler alone, so the scoping cannot be over-applied in
the other direction.  The bite is shown rather than claimed: putting the unconditional branch back
turns **exactly one** test red, ``test_a_rejected_temperature_does_not_cost_the_schema``, with
"removing temperature must not touch the reply constraint", while the mirror stays green.  A/B over
the six suites that touch this module: **1 failed / 186 passed before, 187 passed after**.

**Recorded, not done.**  Each key still gets exactly **one** recovery, so a build that rejects
*both* keys ends the call as a failure rather than degrading twice.  Extending the retry is a
latency change on a path the project measures (about 10 s of every UNKNOWN step is generation), so
it is left as a named question rather than folded into a scoping fix.

**Not verified live.**  AUTO is still paused by the operator and the local model server has exited,
so no real call has carried the new field or exercised this branch since it changed.
