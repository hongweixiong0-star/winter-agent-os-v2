fix(model): record which reply constraint was really in force, because it can degrade silently

The anti-prose design is built on the grammar holding.  ``ui_planner`` caps ``reason`` at
``maxLength: 120`` in the schema, and ``ui_venus_contract.reason_violation`` then *refuses* an
over-long reason rather than truncating it, on the stated grounds that "a truncated rationale still
cost the tokens it was written in -- only a refusal removes it".  That argument is only true while
the decode is actually constrained.

And the constraint can be lost without a word: when the server rejects an optional key, ``_post``
raises ``_RejectedKey`` and the recovery swaps ``json_schema`` for plain ``json_object``, then drops
``response_format`` altogether.  The ledger had **no field saying which one arrived**.

Measured 2026-10-08T13:51:35Z, which is what makes this more than tidy bookkeeping.  The reply on
``home__control__36e65c39`` -- the screen that had been asked 84 times across a week -- is the only
``EXECUTE`` in the project's history, and its reason is::

    "Goal is KEEP_BUILDING_PRODUCTIVE. The screen shows the Wall at level 8 with an 'Upgrade'
     button (E6). Clicking this is a ..."          (three sentences, past 120 characters)

It was refused with ``PLAN_REASON_TOO_LONG``.  llama.cpp's own grammar conversion **does** enforce
``maxLength`` -- its ``grammars/README.md`` worked example turns ``maxLength: 100`` into
``char{1,100}`` -- so a reason of that shape cannot be produced under the schema.  The exact schema
was therefore not in force on that call, and nothing in the ledger could say so.

So ``GUIModelCall`` gains ``reply_constraint``: ``schema`` / ``json_object`` / ``none``, set from the
payload actually posted, updated on the downgrade, and written on every row including the failed
ones.  Telemetry only -- no behaviour changes -- and it is what turns "this refusal looks odd" into
"this refusal is explained".

**Tests.**  ``tests/test_the_reply_constraint_is_recorded.py``, six cases, one per state plus a
failed call, and the bite is shown: deleting the one line that writes the field turns **all six**
red.  A/B over the six suites that touch this module: **7 failed before, 1 after**, and the six that
differ are exactly the new tests.  The one that remains is the pre-existing
``test_the_model_endpoint_is_reachable_from_exactly_one_module``, which is fixed in the next commit
and is byte-identical in both arms here.

**Not verified:** whether the schema degraded on *that* call is deduced, not observed -- the
deduction is that a reason past ``maxLength`` cannot be generated under a grammar that bounds it, and
llama.cpp's README is the source for the grammar claim.  The field exists so the next occurrence is
observed instead.  AUTO is still paused by the operator, so no live call has carried the new field
yet.
