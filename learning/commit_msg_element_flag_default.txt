fix(planner): a record without the executability flag was a screen nothing could ever be named on

``elements_from_request`` read two fields that always travel together, with **opposite** defaults for
their absence:

    kind = str(box.get("element_kind") or "")
    if kind:
        entry["kind"] = kind
        entry["executable"] = bool(box.get("element_executable"))

An absent ``element_kind`` leaves the element untyped -- no ``kind`` and no ``executable`` key -- and
``parse_plan``'s guard tests ``element.get("executable") is False``, so **untyped is permitted**.
An absent ``element_executable`` becomes ``bool(None)`` = False, so **the same record's other default
refuses everything**. One identity, two defaults, opposite directions.

**Measured 2026-10-08 over ``learning/unknown_requests/sweepcase_*.json``** -- every box carries the
kind, none carries the flag:

    case 01  5 boxes   element_executable present: 0   kinds {TEXT_LABEL: 5}
    case 02  5 boxes   present: 0                       {TEXT_LABEL: 5}
    case 03  5 boxes   present: 0                       {TEXT_LABEL: 5}
    case 04  7 boxes   present: 0                       {TEXT_LABEL: 7}
    case 05  40 boxes  present: 0                       {COMPOSITE_CONTROL: 1, TEXT_LABEL: 39}
    case 06  32 boxes  present: 0                       {COMPOSITE_CONTROL: 1, TEXT_LABEL: 31}

So every element of every one of those screens was offered to the model as *not a control*, and a
proposal against them could only ever be refused. Two of the six hold a real registered composite
control, and the model named it -- refused **with its own kind quoted back at it**:

    case 5  PLAN_TARGET_IS_NOT_A_CONTROL: E1 is COMPOSITE_CONTROL
            E1 = 登录好礼, semantic CONTROL[登录好礼]

That is the permanent UNKNOWN blackhole the guard's own note says must not exist, reached through a
default rather than through a decision.

**The fix.** Executability is derived from the kind **only when the flag is absent**, and the kind set
is the project's own ``EXECUTABLE_ELEMENT_KINDS`` -- the declaration §2 states in prose ("Only the
former may be clicked"). An explicit flag is still honoured whatever it says, and a box with no kind
at all is still left untyped rather than defaulted, so nothing of §2's guard is relaxed.

**What was measured, and what was not.** The fresh model benchmark could **not** be re-run: the local
model server is down (see below), so the acceptance is proven by replaying the *recorded* reply
against the repaired element table, which needs no model:

    case 4  E7 = 前往查看 (TEXT_LABEL)   -> still refused, and correctly: that record has no control
    case 5  E1 = 登录好礼 (COMPOSITE)   -> refused before, **ACCEPTED** now
    case 6  E14                          -> INCONCLUSIVE in replay: the benchmark report's own
                                            ``raw`` for that row is truncated, so re-parsing it fails
                                            with PLAN_NOT_JSON before any guard is reached

**Tests.** ``tests/test_a_record_without_the_flag_is_not_a_blackhole.py``, nine cases, and the bite is
shown rather than claimed: restoring the old default turns **three** red -- the two "no flag is still
offered" cases and ``test_the_login_gift_control_is_now_nameable``, which fails with the production
message verbatim, ``PLAN_TARGET_IS_NOT_A_CONTROL: E1 is COMPOSITE_CONTROL``. The six that stay green
are the ones that must not move, including both halves of the guard: a composite with an explicit
``element_executable: False`` is still refused, and a label named while a real control exists is still
refused. A/B over the seven suites that touch the planner: **12 failed before, 9 after**, and the
three that differ are exactly the new tests.
