fix(panel): a dead ADB bridge needs a restart, and a launch cannot give it one

**Measured on the production pin, twice in one evening, 2026-10-09.**  ``mumu-cli info`` reported
``is_android_started: true`` / ``player_state: start_finished`` while every serial in ``adb devices``
read ``offline`` and ``netstat`` showed **nothing listening** on 16384/5555/7555 -- the instance was
healthy and its ADB bridge was gone.  ``adb kill-server`` + ``start-server``, ``adb disconnect`` +
``connect``, and the panel's own ``adb connect`` all failed, because a client cannot dial a port that
is not open.  ``mumu-cli control -v 0 restart`` restored it both times, and the reconnect then
succeeded immediately.

What the panel did instead: the repair vocabulary is ``{"EMULATOR_DOWN": "LAUNCH_EMULATOR"}`` and
``_ensure_device`` runs ``mumu-cli control -v 0 launch -pkg <game>`` **once per process**.  A launch
on an instance that is already running is a no-op, so the bridge stayed gone, the loop spent its
whole 120-second budget retrying ``adb connect`` at a port that was not there, and the run ended as
``error: device offline`` -- which the runtime classifies as a ``SYSTEM_FAILURE``, so AUTO stopped by
design:

    02:01:45  ⚠ 本轮结束：error: device offline
    02:01:58  ⏹ 未进入下一轮：本轮被判定为系统故障：error: device offline

**The escalation.**  ``should_restart_the_emulator`` is a pure predicate in the same shape as the
file's existing ``should_foreground_emulator``: a launch must already have been requested, a restart
must not have been, and the reconnect must have failed three times first.  When it says yes the loop
runs ``mumu-cli control -v 0 restart`` **once per start** and keeps retrying the reconnect inside the
same budget.  One extra attempt, on the one verb this machine was measured to need; the launch stays
first because it is the cheaper repair and it is the right one when the emulator is genuinely stopped.

Nothing was added to the repair *vocabulary*: the predicate is consulted where the launch had already
failed, so ``DEVICE_REPAIRS`` keeps describing what a preflight reason means and the panel keeps
owning how a repair is carried out.

**Tests.**  Four cases in ``tests/test_the_panel_never_runs_on_a_machine_the_operator_holds.py``,
which is where this file's device-ownership and emulator-window semantics already live.  The bite is
shown rather than claimed: making the predicate return ``False`` (the pre-fix behaviour) turns the two
positive cases red and leaves the two negative controls green.  ``check_wiring.py`` still reports its
same seven problems, i.e. no new one.

**Not verified.**  The escalation has not yet fired in production -- it needs the bridge to die again,
which it does roughly hourly on this machine.  What is verified is the state it is written for
(``start_finished`` + all serials offline + nothing listening) and the repair that cleared it twice by
hand.
